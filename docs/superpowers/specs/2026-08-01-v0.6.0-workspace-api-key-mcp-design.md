# 琅嬛 v0.6.0 Workspace API Key、MCP 与程序化访问设计

> 状态：待评审
>
> 目标版本：v0.6.0
>
> 基线：v0.5.0 已完成；本文只规划 v0.6.0，不重复规划 Web Console 工作台能力
>
> 日期：2026-08-01

## 1. 结论摘要

v0.6.0 在现有浏览器 Session、Workspace 隔离、REST 应用服务和检索事实层之上，增加一种明确面向程序的 Workspace 凭证，并把当前空的 `/mcp` 占位服务器接成可用的业务 MCP Server。

本设计作出以下固定决策：

1. 产品统一称为 **Workspace API Key**。已有数据库表名 `workspace_api_tokens` 保留，不为术语变化做无意义重命名。
2. API Key 是 Workspace 级服务凭证，不是用户 PAT，不继承创建者的实时角色，也不允许模拟用户。
3. 明文格式固定为 `lhk_<secret>`：`secret` 由 `crypto/rand` 生成 32 字节随机数，再用无填充 Base64URL 编码。总随机强度为 256 bit。
4. 数据库同时保存两种用途严格分离的 secret 表示：SHA-256 只用于高频鉴权索引；AES-256-GCM 密文只用于 owner/admin 主动 reveal。普通 REST/MCP 鉴权绝不解密。
5. 每个 API Key 创建时必须绑定当前 Workspace 内一个或多个 KnowledgeBase。除创建知识库这一明确例外外，所有读写和检索都只能落在绑定集合内。
6. 到期方式可以选择 30/90/180/365 天或“不限期”。默认仍为 90 天；`expires_at=NULL` 明确表示不限期。
7. v0.6.0 只定义四个无隐式继承的 scope：`knowledge_bases:write`、`documents:read`、`documents:write`、`search:read`。
8. 浏览器继续只用 HttpOnly Session Cookie。允许程序化调用的 REST 路由可以使用 Session 或 Bearer API Key；其它 Workspace、平台管理和 API Key 管理路由仍为 Session-only。
9. `/mcp` 只接受 `Authorization: Bearer <api-key>`，不接受浏览器 Cookie，不进入 `/api/v1/*`，也不进入 SPA fallback。
10. 全局规范地址统一使用 `server.base_url`。Web 为 `${base_url}/`，REST 为 `${base_url}/api/v1`，MCP 为 `${base_url}/mcp`；不再新增 MCP 专用 public URL。
11. MCP 采用流行且仓库已经使用的第三方包 `github.com/mark3labs/mcp-go`，实现时从当前 `v0.55.0` 升级并固定到 `v0.57.0`。不自研 JSON-RPC、Streamable HTTP、schema 生成或协议协商。
12. MCP 保持 stateless Streamable HTTP，并关闭当前版本不需要的 server-initiated streaming。每个 HTTP 请求都重新鉴权，不维护 MCP Session。
13. 六个工具固定为 `knowledge_base_create`、`document_ingest`、`document_status`、`knowledge_search`、`document_delete`、`chunk_get`。其中 `knowledge_search` 可同时查询多个已绑定 KnowledgeBase，按 Embedding 模型快照分组复用 query embedding，再统一合并结果；工具层只做 typed 协议转换。
14. MCP 成功响应同时返回 `structuredContent` 与内容一致的 JSON text fallback；声明并校验 output schema。预期业务失败返回稳定的结构化错误，不泄漏底层错误。
15. API Key 管理和明文 reveal 只允许 Workspace owner/admin。member 看不到入口，直接访问管理路由返回 `403`。
16. v0.6.0 不实现 OAuth、OIDC、JWT、自定义 MCP Client、stdio MCP、动态注册工具、限额计费、Rerank 或 LLM 回答。

## 2. 背景与真实基线

### 2.1 已完成能力

截至 v0.5.0，仓库已经具备：

- email/password 用户、数据库 Session、HttpOnly Cookie。
- Workspace owner/admin/member、跨 Workspace `404` 隐藏和统一 `AuthContext`。
- Workspace-scoped REST：知识库创建、文档导入/查询/删除、Job 查询、Chunk 查询和混合检索。
- File/FAQ/Web 事实模型、Revision/ChunkSet/Generation、pgvector + PostgreSQL FTS + RRF。
- Web Console 完整工作台与 `web_embed` 单二进制交付。
- `/mcp` 独立协议命名空间和一个无业务工具的 `mcp-go` Streamable HTTP 占位服务器。
- `workspace_api_tokens` 预留表，但没有 Repository、签发、鉴权或管理 API。

### 2.2 当前实现约束

- `AuthContext` 当前只表达用户、平台管理员、Workspace 和角色，需要扩展 principal 与 scope 语义。
- 当前所有 Workspace REST 路由先执行 `SessionAuth -> RequireWorkspace -> RequireWorkspaceRole`。
- `/mcp` 当前无鉴权，`NewServer()` 没有注入 application service。
- `DocumentIngestService` 接受 `io.Reader`，适合 REST multipart 和 MCP Base64 两种协议适配器复用。
- `SearchService` 已返回稳定的 evidence DTO，不生成答案。
- `server.public_base_url` 已存在，但名称容易被理解成只服务浏览器邀请链接；v0.6.0 将其升级为全局 `server.base_url`，作为 Web、REST、MCP 和邀请 URL 的唯一事实源。

### 2.3 版本兼容边界

项目在 v1.0.0 前只支持空数据库全新安装，不承诺内部测试数据跨版本迁移。`workspace_api_tokens` 从未正式启用，因此 v0.6.0 迁移可以重建该预留表，不需要为手工插入的内部数据编写兼容回填。迁移仍必须从空数据库完整执行，并通过真实 PostgreSQL + pgvector 测试。

## 3. 目标、成功标准与非目标

### 3.1 目标

- 让外部程序不依赖浏览器 Session 即可安全调用批准的 REST 能力。
- 让 MCP Client 通过同一 `/mcp` endpoint 使用六个稳定工具。
- API Key 可创建、按一个或多个知识库最小授权、后续 reveal/复制、可选到期或不限期、吊销和查看最近使用时间。
- REST 与 MCP 复用相同 application service、Workspace 隔离和领域错误。
- Web Console 提供完整、可恢复、响应式和无障碍的 API Key 管理体验。
- 提供可以直接复制使用的 REST/MCP 接入文档，同时不把 key 固化进配置示例。

### 3.2 成功标准

一个 Workspace admin 可以：

1. 在 Web Console 创建一个绑定“产品文档”和“客服 FAQ”、默认 90 天、仅含“读取文档 + 检索”scope 的 API Key。
2. 创建后或以后从该 Key 的详情页主动 reveal，并复制明文 key、REST/MCP endpoint 或完整 MCP 配置。
3. 用该 key 初始化 `/mcp`，`tools/list` 只看到 scope 允许的工具。
4. 一次调用 `knowledge_search` 同时查询两个已绑定 KnowledgeBase；同模型只生成一次 query embedding，并获得与 REST 相同、带 KnowledgeBase 来源的合并 evidence。
5. 因 scope 不足无法看到或调用写工具。
6. 创建新 key、替换客户端配置、吊销旧 key；旧 key 的下一次 HTTP 请求立即得到 `401`。

### 3.3 非目标

- 不把浏览器 Session、Cookie 或用户密码用于 MCP。
- 不实现用户级 PAT、Agent 身份、用户 impersonation 或 service account 用户记录。
- 不实现 OAuth 2.0 Authorization Server、OIDC、JWT、JWKS 或 refresh token。
- 不把可恢复密文用于鉴权；`token_secret_ciphertext` 只服务 owner/admin reveal，普通请求始终只查 hash。
- 不允许从 query、URL、multipart 字段或 MCP arguments 传 API Key。
- 不实现 key 自动轮换、重叠期调度或定时吊销；本版本采用“新建 -> 替换 -> 吊销”的显式轮换流程。
- 不把 API Key 扩展到成员、邀请、模型连接、平台管理、Generation 管理或 Chunk Revision 写入。
- 不实现 MCP Resources、Prompts、Sampling、Elicitation、Tasks 或通知。
- 不实现 stdio MCP；琅嬛仍只有一个 `cmd/langhuan`，对外 MCP transport 只有同进程 `/mcp`。
- 不在 MCP 内下载任意远程 URL，不引入新的 SSRF 面。
- 不返回 LLM 生成答案，不把检索 score 包装成质量百分比。

## 4. 方案比较与推荐

### 4.1 身份方案

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| Workspace opaque API Key + 数据库状态 | 可立即吊销；天然绑定 Workspace；scope 清晰；与现有表和单体架构一致 | 每个请求需要一次索引查询 | **采用** |
| 用户 PAT，实时继承 membership | 审计可落到用户 | 自动化随用户离职/降权意外中断；混淆人和服务；不符合 Workspace 服务凭证定位 | 不采用 |
| 自包含 JWT | 无需查库，验证快 | scope/吊销/角色变化不能立即生效；需要签名密钥轮换、`jti` 黑名单后仍回到数据库 | 不采用 |
| OAuth 2.0 Client Credentials | 标准化、适合大型生态 | 需要 Authorization Server、client secret 生命周期、metadata 和更多运维面，超过 v0.6.0 真实需求 | 延后到出现外部 IdP/委托授权需求后再评估 |

推荐 opaque API Key。琅嬛当前是单体服务，PostgreSQL 本来就是请求链路的 Workspace 事实源。一次唯一索引查询换来即时到期、即时吊销和清楚的租户边界，是更合适的取舍。

### 4.2 MCP 实现方案

| 方案 | 现状与优点 | 风险/成本 | 结论 |
|---|---|---|---|
| `github.com/mark3labs/mcp-go` | 仓库已使用；约 9k GitHub stars（2026-08-01 快照）；支持 Streamable HTTP、typed tool、input/output schema、tool filter、recovery 和 structured content | 仍是 `v0.x`，升级必须锁版本并跑合同测试 | **采用 `v0.57.0`** |
| `github.com/modelcontextprotocol/go-sdk` | 官方 SDK，约 4.9k stars；长期规范对齐优势明显 | 更换现有占位实现没有当期产品收益，会扩大 v0.6.0 变更面 | 本版本不迁移；v1.0.0 稳定合同前可重新评估 |
| 自研 JSON-RPC/MCP | 完全可控 | 重复实现协议协商、transport、schema、错误与兼容性；测试成本和安全风险最高 | 禁止 |

选择 `mcp-go v0.57.0` 的原因不是只看 stars，而是它已在仓库中通过 `/mcp` 占位验证，所需能力完整，并能最小化变更。实现必须：

- 在 `go.mod` 固定精确版本，不跟随 `main` 或伪版本。
- 启用 `WithRecovery()`、`WithStrictInputSchemaDefault()`、`WithOutputSchemaValidation()` 和 `WithToolFilter(...)`。
- 保持 `WithStateLess(true)`，并启用 `WithDisableStreaming(true)`。
- 通过 `WithHTTPContextFunc` 或进入 handler 前替换 `request.Context()`，把已经验证的 `AuthContext` 传入 tool filter 和 handler；不得把原始 Bearer 值继续传到工具层。
- 用合同测试固定 `initialize`、`tools/list`、每个 input/output schema、structured output、错误和 HTTP transport 行为。
- 未来升级 minor 版本时，先在独立提交中升级并跑全部 MCP 合同测试，不把依赖升级夹在业务修复中。

## 5. 产品权限与 scope 合同

### 5.1 管理权限

| 操作 | owner | admin | member | API Key |
|---|---:|---:|---:|---:|
| 查看 API Key 列表 | 是 | 是 | 否 | 否 |
| 查看 API Key 详情与知识库范围 | 是 | 是 | 否 | 否 |
| 创建 API Key | 是 | 是 | 否 | 否 |
| 吊销 API Key | 是 | 是 | 否 | 否 |
| reveal/复制完整明文 key | 是 | 是 | 否 | 否 |
| 查看 hash | 否 | 否 | 否 | 否 |

platform_admin 不因平台身份自动获得任意 Workspace 的 API Key 管理权限；仍必须拥有该 Workspace 的 owner/admin membership。

### 5.2 KnowledgeBase 资源范围

每个 API Key 必须绑定当前 Workspace 中一个或多个未删除 KnowledgeBase。绑定集合是 key 的不可变资源边界；创建后若需改变范围，管理员创建新 key、切换客户端并吊销旧 key，避免运行中的凭证被静默扩大权限。

创建时服务端必须：

1. 对 `knowledge_base_ids` 去重并要求至少一个。
2. 在 Workspace-bound transaction 中验证每个 ID 都属于当前 Workspace 且未删除。
3. 原子创建 key 与全部绑定；任何一个知识库无效时不创建 key。

调用时按以下规则执行：

- 带 `knowledge_base_id` 的 REST/MCP 操作先检查绑定，再进入 application service。
- `document_status`、`document_delete` 等以 Document/Job 为入口的操作也必须要求或解析 KnowledgeBase lineage，并在 Repository 查询中同时限制 `workspace_id + knowledge_base_id`，不能先读出跨范围对象再在响应层隐藏。
- 不在绑定集合内统一返回 `404 not_found`，不暴露该知识库或资源是否存在。
- Session principal 不受 API Key 的知识库绑定限制，继续按 membership/role 访问 Workspace。
- 带 `knowledge_bases:write` 的 key 调用 `knowledge_base_create` 时，新建 KnowledgeBase 与“把新 KnowledgeBase 加入该 key 绑定集合”必须处于同一 transaction。该 scope 明确允许 key 通过自己创建新知识库扩展范围；没有此 scope 的 key 不能扩展。

普通 UI/API 返回知识库的 `id + name` 摘要，界面只显示可读名称。删除知识库沿用现有软删除合同；其绑定保留用于审计，但鉴权视为不可用。

### 5.3 scope 定义

scope 是精确集合，不存在 `write` 自动包含 `read` 的隐式规则。UI preset 只是一次选择多个 scope，服务端仍保存展开后的明确集合。

| Scope | 允许的程序化操作 |
|---|---|
| `knowledge_bases:write` | 创建 KnowledgeBase，并把新建项原子加入当前 key 的知识库范围 |
| `documents:read` | 读取 Document 状态、Job 状态和 Chunk |
| `documents:write` | 导入和软删除 Document |
| `search:read` | 对指定 KnowledgeBase 执行混合检索 |

至少选择一个 scope。未知 scope、重复 scope、空字符串一律返回 `400 validation_error`。持久化前排序并去重，保证响应、审计和测试稳定。

### 5.4 UI preset

| Preset | 展开后的 scope | 用途 |
|---|---|---|
| 读取与检索（默认） | `documents:read`, `search:read` | 检索 Agent、只读集成 |
| 导入与检索 | `documents:read`, `documents:write`, `search:read` | 内容同步程序 |
| 完整程序化访问 | 四个 scope 全部 | 需要创建知识库的部署/集成流程 |

用户可以在 preset 后继续逐项调整。表单必须展示最终 scope，不只展示 preset 名称。

### 5.5 REST 与 MCP 映射

| 操作 | REST | MCP | Scope |
|---|---|---|---|
| 创建知识库 | `POST /api/v1/workspaces/:workspace_slug/knowledge-bases` | `knowledge_base_create` | `knowledge_bases:write` |
| 导入文档 | `POST /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/documents` | `document_ingest` | `documents:write` |
| Document 状态 | `GET /api/v1/workspaces/:workspace_slug/documents/:document_id` | `document_status` | `documents:read` |
| Job 状态 | `GET /api/v1/workspaces/:workspace_slug/jobs/:id` | `document_status` 的可选 `job_id` | `documents:read` |
| 单知识库混合检索（保留） | `POST /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/search` | — | `search:read` |
| 多知识库混合检索 | `POST /api/v1/workspaces/:workspace_slug/search` | `knowledge_search` | `search:read` |
| 删除文档 | `DELETE /api/v1/workspaces/:workspace_slug/documents/:document_id` | `document_delete` | `documents:write` |
| 获取 Chunk | `GET /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/chunks/:chunk_id` | `chunk_get` | `documents:read` |

其它现有 REST 路由仍为 Session-only。API Key 即使带上所有 v0.6.0 scope，也不能访问成员、邀请、模型凭证、模型管理、KnowledgeBase 设置、Generation 写入或 Chunk Revision 写入。

## 6. API Key 密码学与生命周期

### 6.1 明文格式

```text
lhk_<43-char-base64url-secret>
```

- 固定前缀：`lhk_`，便于用户识别、日志脱敏规则和 secret scanner 发现。
- secret：`crypto/rand.Read` 生成 32 字节，`base64.RawURLEncoding` 编码，无 `=` padding。
- 完整长度：47 个 ASCII 字符。
- 示例只使用不可用占位值：`lhk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`。
- 不增加环境标记；开发和生产的信任边界由部署 endpoint 决定，key 本身不携带可伪造声明。

生成步骤固定为：

```text
crypto/rand 32 bytes
        |
        v
Base64URL without padding (43 chars)
        |
        v
"lhk_" + secret
        |
        +--> plaintext: creation/reveal response
        |
        +--> SHA-256(full plaintext) -> lowercase hex -> authentication index
        |
        +--> HKDF purpose key + AES-256-GCM -> recoverable ciphertext
        |
        +--> first 12 chars -> token_prefix -> list display
```

不得使用 UUID、`math/rand`、时间戳、用户 ID、Workspace ID 或哈希后的可预测数据作为 secret。

### 6.2 为什么用 SHA-256，不用 Argon2id

API Key 含 256 bit 均匀随机熵，不存在人类密码的低熵字典攻击问题。SHA-256 允许服务端对请求 key 做一次固定成本哈希并使用唯一索引 O(1) 查询；Argon2id 会显著增加每个 API/MCP 请求的 CPU/内存成本，却不增加有意义的离线破解阻力。

数据库泄漏但 `credentials.encryption_key` 未泄漏时，hash 仍面对 256-bit 随机空间，密文也不能被直接恢复。普通鉴权不依赖解密，因此主密钥不可用或某条密文损坏时，已有 key 的 REST/MCP 调用仍可按 hash 工作；只有 create/reveal 返回通用 `internal_error`。

### 6.3 可恢复 reveal 与加密边界

- 创建 API 可以返回明文；此后 owner/admin 可通过专用 reveal endpoint 再次取得。
- 鉴权只使用 `token_hash`，绝不为每个请求解密 `token_secret_ciphertext`。
- 从现有 `credentials.encryption_key` 通过 HKDF-SHA-256、info=`langhuan/workspace-api-key/v1` 派生 API Key 专用 32-byte 子密钥，不和 Model Provider 直接共用 AEAD key。
- `credentials.encryption_key` 继续要求 Base64 编码的 32-byte 主密钥，服务启动时解码失败立即退出。v0.6.0 不新增第二个需要单独备份的 API Key 主密钥。
- 使用 AES-256-GCM、每次随机 nonce；密文格式包含版本字节。AAD 固定绑定 `workspace-api-key:v1:<workspace_id>:<api_key_id>`，复制密文到另一条 key 或 Workspace 后必须解密失败。
- reveal endpoint 是 Session-only owner/admin 敏感操作，使用 `POST`，响应包含 `Cache-Control: no-store`、`Pragma: no-cache`，不接受 API Key 自己 reveal 自己。
- list/detail/revoke、日志、错误、Toast、Query cache 和诊断 payload 永远不返回明文、hash 或 ciphertext。
- reveal 响应只进入当前详情页 secret panel 的局部内存；route 卸载、切换 key 或刷新时立即清空引用，不进入 TanStack Query Cache、URL、Zustand、localStorage 或 sessionStorage。
- revoked/expired key 仍允许 owner/admin reveal，但界面同时显示“此 Key 已失效”；这样每条历史记录都满足可复制合同，复制不会恢复授权。
- 丢失 `credentials.encryption_key` 会导致历史 key 无法 reveal，但不会使 hash 鉴权自动失效。生产轮换主密钥前必须先完成所有 recoverable secret 的重加密；v0.6.0 不提供多主密钥在线轮换。

### 6.4 到期与状态

配置新增：

```yaml
auth:
  api_key:
    default_lifetime_seconds: 7776000     # 90 天
    max_lifetime_seconds: 31536000        # 365 天
    last_used_touch_interval_seconds: 300 # 5 分钟

mcp:
  inline_ingest_max_file_size_bytes: 8388608 # 8 MiB
```

创建请求使用显式 union：

```json
{"expiration":{"type":"days","days":90}}
```

或：

```json
{"expiration":{"type":"never"}}
```

`days` 接受 1 到 `max_lifetime_seconds / 86400`。未提供 `expiration` 时使用默认 90 天；`type=never` 时 `expires_at=NULL`。状态不单独存列，按以下顺序派生：

```text
revoked_at != null       -> revoked
expires_at == null       -> active（界面到期时间显示“不限期”）
expires_at <= now        -> expired
expires_at - now <= 7d   -> expiring
otherwise                -> active
```

`expiring` 只是 UI 提醒，鉴权上仍为 active。时间统一存 UTC，响应使用 RFC 3339。

### 6.5 吊销和轮换

- `DELETE .../api-keys/:id` 表示吊销，不物理删除记录。
- 重复吊销同一 key 返回 `204`，保证操作幂等。
- 不提供恢复吊销。
- 不缓存鉴权结果；到期或吊销从下一次 HTTP 请求起失效。
- 已经进入 application service 的请求不会因中途吊销被强制取消；其 Context 仍只受客户端断开或服务端超时控制。UI 和文档必须使用“下一次请求失效”，不声称中断正在执行的请求。
- 安全轮换顺序固定为：创建新 key -> 更新并验证客户端 -> 吊销旧 key。

### 6.6 `last_used_at`

成功鉴权后以条件更新写入：只有 `last_used_at IS NULL` 或距当前时间至少 5 分钟才更新。更新失败只记录不含 secret 的 warning，不让一个本来有效的请求失败。不得启动脱离请求生命周期的 goroutine；条件更新直接使用当前 Context。

### 6.7 全局 `server.base_url`

v0.6.0 将现有 `server.public_base_url` 破坏性改名为 `server.base_url`，不增加 `mcp.public_url`，也不保留旧 alias。项目在 v1.0.0 前只支持全新安装，因此宁可让旧配置启动时报未知字段，也不同时维护两个事实源。

```yaml
server:
  http_addr: ":8080"
  base_url: "https://langhuan.example.com"
```

合同固定为：

```text
规范化 base_url = 校验绝对 http/https URL，并去掉末尾斜杠
Web               = ${base_url}/
REST              = ${base_url}/api/v1
MCP               = ${base_url}/mcp
邀请链接等绝对 URL = ${base_url} + 对应应用路径
```

`base_url` 是必填配置；空值启动失败。本地可用 `http://127.0.0.1:8080`，生产部署检查必须要求 HTTPS。它可以含部署前缀，例如 `https://example.com/langhuan`，此时 REST 为 `/langhuan/api/v1`、MCP 为 `/langhuan/mcp`。不得包含 userinfo、query 或 fragment。后端 URL builder 是唯一派生点，REST DTO、Web 复制区、邀请链接和文档共用它；前端不读取 `window.location.origin` 猜测公开地址。

## 7. 数据模型与迁移

### 7.1 领域模型

新增纯领域模型 `model.WorkspaceAPIKey`：

```text

TokenHash / TokenPrefix
Scopes / KnowledgeBaseIDs
ExpiresAt? / LastUsedAt? / RevokedAt?
```

### 7.3 Repository 与事务

接口定义在 application 使用方，DB 实现在 `internal/infrastructure/db`，每个方法接收 `context.Context`：

```go
CreateWithKnowledgeBaseBindings(ctx, key, secretCiphertext, knowledgeBaseIDs) error
Get(ctx, workspaceID, keyID) (*model.WorkspaceAPIKey, error)
List(ctx, workspaceID) ([]*model.WorkspaceAPIKey, error)
FindByTokenHashWithBindings(ctx, tokenHash) (*model.WorkspaceAPIKey, error)
RevealSecretCiphertext(ctx, workspaceID, keyID) ([]byte, error)
Revoke(ctx, workspaceID, keyID, actorID, now) error
TouchLastUsed(ctx, keyID, now, minInterval) error
AddKnowledgeBaseBinding(ctx, keyID, workspaceID, knowledgeBaseID) error
```

- 创建在同一 Workspace-bound transaction 内验证知识库并写 key 与全部绑定；任一步失败整体回滚。
- 鉴权查询只选择鉴权字段和绑定 ID，不选择密文；状态由 service 判断。
- `RevealSecretCiphertext` 是唯一读取密文的方法，按 `workspace_id + id` 查询，不复用 `SELECT *`。
- 管理查询、吊销和绑定查询始终显式带 `workspace_id`；GORM not found 映射为领域 `ErrNotFound`。
- Repository 是薄封装，不生成 key、不判断角色、不做 scope 业务决策。

### 7.4 Application service 与 cipher

新增聚焦的 `APIKeyService`：

```text
Create(ctx, workspaceID, actorID, actorRole, name, knowledgeBaseIDs, scopes, expiration)
Get(ctx, workspaceID, actorRole, keyID)
List(ctx, workspaceID, actorRole)
Reveal(ctx, workspaceID, actorRole, keyID)
Revoke(ctx, workspaceID, actorID, actorRole, keyID)
Authenticate(ctx, plaintextKey)
```

依赖显式注入：Repository、Workspace-bound transaction runner、`APIKeySecretCipher`、`io.Reader` 随机源、UUID generator、Clock、全局 URL builder 和配置。`APIKeySecretCipher` 接口定义在 application 使用方；基础设施实现 HKDF-SHA-256 与 AES-256-GCM。它与 Provider credential cipher 分开实现，禁止误用 Provider 专用 AAD。

创建顺序固定为：生成 key ID 与 secret -> hash -> 使用 ID/Workspace 组成 AAD 加密 -> transaction 验证所有知识库 -> 保存 key、密文、绑定。任何加密或持久化失败都不得返回明文成功响应。

`Authenticate` 严格校验格式、计算 hash、按唯一 hash 查记录和绑定、判断吊销/到期、确认绑定非空，再构造不含明文/hash/密文的 principal。格式错误、查无记录、已吊销、已到期统一返回 `ErrUnauthorized`；成功后 best-effort 触碰 `last_used_at`。

`Reveal` 检查 Session owner/admin，以 Workspace + key ID 读取密文，用同一 AAD 解密，并校验明文格式、prefix 与 hash 一致。解密或一致性失败统一映射 `api_key_secret_unavailable`；日志只含 key/workspace ID。

## 8. 统一认证上下文与 HTTP 路由

### 8.1 `AuthContext` 与资源边界

```go
type PrincipalKind string

const (
    PrincipalUser   PrincipalKind = "user"
    PrincipalAPIKey PrincipalKind = "workspace_api_key"
)

type AuthContext struct {
    PrincipalKind    PrincipalKind
    PrincipalID      uuid.UUID
    UserID           uuid.UUID
    IsPlatformAdmin  bool
    WorkspaceID      uuid.UUID
    Role             WorkspaceRole
    Scopes           []APIScope
    KnowledgeBaseIDs []uuid.UUID
}
```

- Session principal 的 Role 来自 membership，Scopes/KnowledgeBaseIDs 为空；它不受 API Key 范围限制。
- API Key principal 的 UserID 为空，Workspace/Scopes/KnowledgeBaseIDs 来自 key，绑定集合必须非空。它不继承创建者身份或实时角色。
- 需要真实用户的操作明确要求 `PrincipalKind=user`。
- application 使用协议中立的 `ResourceAccess{WorkspaceID, Unrestricted, AllowedKnowledgeBaseIDs}`。API Key 查询把允许范围下推到 SQL，不能先查跨范围对象后再隐藏。

### 8.2 凭证优先级

允许两类凭证的 REST 路由上，存在 `Authorization` 时 Bearer 是权威凭证；无效 Bearer 直接 `401`，不回退有效 Cookie。仅没有 Authorization 时尝试 Session。拒绝多 header、空 credential、Basic 或逗号拼接值。

### 8.3 路由分组

```text
/api/v1/workspaces/:workspace_slug
  +-- Session-only: members, invitations, models, settings,
  |                  generations/chunk revisions write, api-keys
  +-- Session-or-API-Key allowlist: KB create, document ingest/status/delete,
                                     job status, search, chunk get

/mcp
  +-- API-Key-only
```

程序化 REST middleware 顺序：

```text
SessionOrAPIKeyAuth
  -> RequireWorkspace
  -> RequireWorkspaceRole(member)
  -> RequireScopeForAPIKey(requiredScope)
  -> RequireKnowledgeBaseForAPIKey(route/input knowledge_base_id)
  -> handler
```

Session 直接通过后两个 API-Key 专用检查。API Key 的 Workspace 不匹配、知识库未绑定以及其下 Document/Job/Chunk 越界都统一 `404`。Document/Job URL 没有 KB ID 时，application/Repository 用 `workspace_id + allowed_knowledge_base_ids + resource_id` 单次查询。

管理路由固定为：

```text
GET    /api/v1/workspaces/:workspace_slug/api-keys
POST   /api/v1/workspaces/:workspace_slug/api-keys
GET    /api/v1/workspaces/:workspace_slug/api-keys/:api_key_id
POST   /api/v1/workspaces/:workspace_slug/api-keys/:api_key_id/reveal
DELETE /api/v1/workspaces/:workspace_slug/api-keys/:api_key_id
```

全部只走 `SessionAuth -> RequireWorkspace -> RequireWorkspaceRole(admin)`。

### 8.4 `/mcp` 鉴权

`POST /mcp` 只接受 `Authorization: Bearer lhk_...`。验证后的 AuthContext 写入请求 Context，原始 Bearer 不传入 tool 层。缺失/无效/过期/吊销返回 HTTP `401` 和 `WWW-Authenticate`，不进入 JSON-RPC。scope 不足的工具从 `tools/list` 移除，并在 call-time 再检查。知识库范围依赖工具参数，必须在每次调用时检查；越界统一 `not_found`。Cookie、CORS 放宽与 OAuth metadata 都不进入本版本。

```http

```

```json

  "base_url": "https://langhuan.example.com",
```

- 只允许 Session owner/admin；API Key 不能 reveal 自己。

### 9.5 稳定错误

| HTTP | Code | 场景 |
|---:|---|---|
| 400 | `validation_error` | 名称、知识库集合、scope、到期方式或 JSON 无效 |
| 401 | `unauthorized` | Bearer 缺失/无效/过期/吊销 |
| 403 | `forbidden` | member 访问 key 管理 API |
| 403 | `insufficient_scope` | 合法 key 调用未授权 operation |
| 404 | `not_found` | Workspace、key、知识库或其下资源不存在/越界 |
| 409 | `api_key_limit_reached` | active key 达上限 |
| 500 | `api_key_secret_unavailable` | reveal 无法恢复，响应不暴露密码学原因 |
| 500 | `internal_error` | 其它未预期错误 |

```json
      "knowledge_base_id": "uuid-faq",
      "knowledge_base_name": "客服 FAQ",
      "chunk_id": "uuid",
      "chunk_revision_id": "uuid",
      "document_id": "uuid",
      "document_kind": "faq",
      "document_name": "账号 FAQ",
      "content": "在登录页选择重置密码……",
      "source_anchor": {"source_type": "faq"},

      "vector_score": 0.84,
      "keyword_score": 0.61,

```

- `knowledge_base_ids` 必填、去重后 1..`search.multi_knowledge_base_limit` 个，默认上限 20；每个 ID 都必须属于 key 绑定集合。只要一个越界，整个调用返回统一 `not_found`，不返回部分结果。
- REST 同步新增 `POST /api/v1/workspaces/:workspace_slug/search` 使用完全相同的 input/output DTO；原有单知识库 route 保留并可委托给多库 service 的单元素输入。
- 新增 `MultiKnowledgeSearchService`，MCP/REST 都只调用它，不在 adapter 自己循环或合并。
- 返回完整 evidence，不生成总结，不截断 content，不静默改写 structured content。
- text fallback 是同一对象的 JSON，不是另造一份 Markdown 结果。

#### 10.6.1 按 Embedding 模型分组

协调器先在一次 Workspace-scoped 读取中加载所有选中 KnowledgeBase 的 active Generation 快照，再按以下不可变模型身份分组：

```text
EmbeddingGroupKey =
  embedding_model_id
  + provider_id
  + model_name
  + embedding_dimension
  + model_config_hash
```

组键任一字段不同都不得复用向量。每组只调用一次 Embedding Provider，把同一 query 转成一个 query vector；该向量只用于组内知识库。不能因为维度相同就跨模型复用，也不能拿 A 模型的向量查询 B 模型索引。

```text
选中的 KnowledgeBase
        |
        v
读取各自 active Generation + 校验 key 绑定
        |
        +----------------------+----------------------+
        |                                             |
        v                                             v
Embedding Group A                              Embedding Group B
model/config hash A                            model/config hash B
KB: 产品文档、客服 FAQ                          KB: 内部制度
        |                                             |
        v                                             v
query embed 1 次                               query embed 1 次
        |                                             |
        v                                             v
组内各 KB Vector + FTS 候选                    组内各 KB Vector + FTS 候选
        |                                             |
        v                                             v
每 KB 使用同一 merge_rrf_k 做混合 RRF           每 KB 使用同一 merge_rrf_k 做混合 RRF
        +----------------------+----------------------+
                               |
                               v
                    合并所有 KB 的 model-agnostic RRF score
                               |
                               v
                    全局排序、截取 final_top_k、加载 evidence
```

#### 10.6.2 合并与排序

- 每个 KnowledgeBase 仍按其 active Generation 的 `fts_config` 与候选 top-k 默认值检索；请求里的 `vector_top_k/keyword_top_k` 覆盖值对所有选中库一致生效。
- 多库协调器统一使用 `search.multi_merge_rrf_k`（默认 60）对每个 KB 的 vector/keyword 排名做 RRF。最终 `score` 只来自排名，不直接混用不同 Embedding 模型的 cosine/distance。
- 合并所有 KB 的 fused candidates 后按 `score DESC, knowledge_base_id ASC, chunk_id ASC` 排序，再应用全局 `final_top_k`。`vector_score`/`keyword_score` 仅作证据诊断，不参与跨模型二次比较。
- `final_top_k` 是全局结果数，不是“每个知识库各返回 N 条”。结果必须带 `knowledge_base_id/name`，调用方能追溯来源。
- 所有选中库权重相同，v0.6.0 不开放每库 boost，避免 API surface 先于真实需求膨胀。

#### 10.6.3 并发、快照与失败

- 使用 `errgroup.WithContext` 按模型组并发 embedding、按配置限制组内查询并发；默认 `search.multi_concurrency=4`，所有 goroutine 都受请求 Context 取消。
- 开始检索前记录每个 KB 的 active Generation ID；加载 evidence 前再次确认未切换。任一变化返回 `generation_stale`，不混合两个代次。
- v0.6.0 采用 all-or-nothing：任一知识库无 ready Generation、Provider 失败、维度不匹配或查询失败，整个调用返回稳定错误，不静默少查一个库。错误不泄露其它库名称或 Provider 配置。
- 配置新增：

```yaml
search:
  multi_knowledge_base_limit: 20
  multi_concurrency: 4
  multi_merge_rrf_k: 60
```

### 10.7 `document_delete`

输入：

```json
{"knowledge_base_id": "uuid", "document_id": "uuid"}
```

两个字段都必填。调用受 `workspace_id + knowledge_base_id` 约束的现有软删除 application service。成功输出：

```json
{"document_id": "uuid", "deleted": true}
```

工具描述必须说明：Document 会立即退出检索，事实与原始对象仍按现有恢复/保留合同处理。重复删除按现有 application service 的幂等语义实现；不得在 MCP adapter 自己伪造成功。

### 10.8 `chunk_get`

输入：

```json
{
  "knowledge_base_id": "uuid",
  "chunk_id": "uuid"
}
```

调用 `ChunkRevisionService.Get`。输出保留定位和内容所需字段：`id`、`document_id`、`sequence`、`source_content`、typed `source_anchor`、allowlist metadata、active revision 的 `id/revision_no/content/context_header/enabled/status/edit_source/editor_display_name/created_at/indexed_at`。

不输出 `editor_user_id`、Workspace ID、storage key 或任意 hash。

### 10.9 MCP 错误合同

分三层处理：

1. HTTP 鉴权失败：HTTP `401`，不构造 JSON-RPC tool result。
2. JSON/schema 错误：由 mcp-go 返回标准 JSON-RPC `INVALID_PARAMS`。
3. application 预期错误：返回 `isError=true` 的 CallToolResult，`structuredContent` 和 text JSON 都为：

```json
{
  "error": {
    "code": "generation_not_ready",
    "message": "知识库当前没有可用索引",
    "retryable": true
  }
}
```

`retryable` 由明确 allowlist 映射，不根据字符串猜测。validation/not_found/forbidden/insufficient_scope 为 false；generation building/not ready、rate limited、provider timeout 可按现有错误类型设 true。

未预期错误只记录服务端结构化日志，工具返回 `internal_error` + “服务器内部错误”。禁止把 `%v` 的数据库、Redis、对象存储、Provider 或 stack 内容返回客户端。

## 14. 安全、日志与隐私

### 14.1 必须脱敏

以下内容不得进入日志、错误、metrics label、trace attribute、DOM 持久区域、诊断复制或 Job payload：

- `Authorization` header。
- 完整 API Key。
- `token_hash`。
- `token_secret_ciphertext`、nonce、派生密钥和 `credentials.encryption_key`。
- `content_base64`。
- 完整检索 query 或完整文档内容。
- Provider credential。

允许记录：`api_key_id`、`token_prefix`、`workspace_id`、principal kind、scope code、MCP tool name、HTTP route template、status/outcome、耗时。不要记录原始 URL query string。

### 14.2 结构化日志

成功和失败日志使用 key-value 字段：

```text
principal_kind=workspace_api_key
api_key_id=<uuid>
workspace_id=<uuid>
transport=rest|mcp
operation=<route-name|tool-name>
outcome=ok|unauthorized|forbidden|error
duration_ms=<number>
```

无效 key 无 `api_key_id` 时只记录 `credential_kind=api_key` 和结果，不记录猜测 prefix，避免把攻击输入写入日志。

### 14.3 请求安全

- API Key 只通过 TLS 上的 Authorization header 使用；生产文档明确要求 HTTPS。
- 服务本身保持现有反向代理部署方式，不在应用内新增 TLS 终止方案。
- `/mcp` 不允许浏览器 Cookie，不放宽 CORS。
- reveal 只允许 Session owner/admin，并固定 `no-store/no-cache`；普通鉴权路径用测试证明不调用 decrypt。
- 密文使用随机 nonce、版本格式和绑定 Workspace/key ID 的 AAD；跨行、跨 Workspace 复制密文必须失败。
- MCP Base64 导入先检查编码长度上界，再解码到有界 reader/临时文件，避免超大分配。
- API Key 名称是用户输入，输出由 React 转义，日志中作为结构化字段前限制长度。
- 鉴权和 scope 判断全部在进入业务 handler 前完成，tool handler 内再做 scope 防御检查。

## 15. 错误、取消与并发

- 所有 Repository、鉴权、MCP tool 和 application service 透传请求 `context.Context`。
- 客户端断开 `/mcp` 时，检索 embedding HTTP 请求和数据库查询必须收到取消。
- 多知识库检索使用 `errgroup.WithContext` 和配置化并发上限；任一组失败会取消剩余工作，不返回静默残缺结果。
- 同模型组只生成一次 query embedding；不同模型组绝不共享向量。跨模型合并只比较统一 RRF score，不比较原始向量相似度。
- `document_ingest` 只在当前请求内完成解码、持久化和入队；worker 后续按现有独立生命周期运行。
- 并发吊销使用条件更新；两个管理员同时吊销都得到幂等成功。
- 并发创建使用 active count + transaction/锁保证 100 个上限，不用“先 count、后无约束 insert”的竞态实现。
- `last_used_at` 触碰不影响主请求结果。
- tool schema/output validation failure 是开发错误：测试必须捕获，生产只返回 generic internal error。

## 16. 测试策略

所有需要数据库的自动化测试只使用运行期临时 `pgvector/pgvector:pg16` 容器，严禁读取 `config.yaml` 或连接本机长期 PostgreSQL。需要 Redis 的 E2E 同样使用一次即弃容器或既有隔离 helper。

### 16.1 API Key 单元测试

- 生成值严格匹配 `^lhk_[A-Za-z0-9_-]{43}$`，解码为 32 字节。
- 可控随机源失败时创建失败且不持久化。
- hash 与 prefix 正确；plaintext 不进入领域 DTO/日志。
- HKDF info 固定且与 Provider cipher 域分离；AES-GCM 每次随机 nonce，同一明文产生不同密文。
- AAD 篡改、密文篡改、错误主密钥、跨 key/Workspace 密文复制都解密失败。
- 鉴权成功与失败路径都不调用 decrypt；只有 create/reveal 需要 cipher。
- reveal 后校验格式、prefix/hash 一致；错误只映射安全错误。
- scope 排序、去重、未知值、空值。
- KnowledgeBase ID 去重、空集合、跨 Workspace/已删除项；key 与绑定原子创建。
- 默认/最短/最长/超长/不限期，使用固定 Clock；NULL expiry 永不因时间变为 expired。
- owner/admin/member 权限。
- invalid/not-found/revoked/expired 统一为 `ErrUnauthorized`。
- `last_used_at` 5 分钟节流和 fail-open。
- 100 active key 并发上限。
- `server.base_url` 尾斜杠、部署前缀、非法 URL、生产 HTTP 拒绝及 Web/REST/MCP 派生。

### 16.2 Repository/迁移集成测试

- 从空库执行全部迁移，最终表、constraint、index 正确。
- hash 唯一、可空 expiry、ciphertext 非空、Workspace cascade、created/revoked user `SET NULL`。
- 每 key 至少一个绑定由 service/transaction 保证；复合外键拒绝跨 Workspace KnowledgeBase。
- key 创建或任一绑定失败时全部回滚；删除 key/Workspace 的 cascade 正确。
- 普通 List/Get/Auth SQL projection 不读取 ciphertext；Reveal 是唯一读取路径。
- 跨 Workspace list/get/reveal/revoke 返回 not found。
- revoke 幂等且保留行。
- expired/revoked 行仍可由 hash 查到，状态由 service 判断。
- `TouchLastUsed` 条件更新时间。

### 16.3 REST handler/middleware 测试

- Session-only、Bearer-only、两者同时存在时 Bearer 优先。
- 无效 Bearer 不回退有效 Cookie。
- API Key 只可访问 allowlist routes。
- 每个 scope 的正向/负向矩阵。
- 跨 Workspace slug 为统一 `404`。
- member 无法 list/create/get/reveal/revoke key；platform_admin 无 membership 也不能管理。
- create/reveal 可返回明文；list/detail/revoke/错误不包含明文/hash/ciphertext。
- reveal 响应包含 `Cache-Control: no-store`、`Pragma: no-cache`；API Key 自己调用失败。
- active/expired/revoked 都可 reveal，且 reveal 不改变状态。
- 每个知识库范围正向通过；未绑定 KB 及其 Document/Job/Chunk 统一 404。
- `knowledge_base_create` 成功时原子增加调用 key 绑定，失败时两者都不落库。
- 多知识库 REST search 拒绝空集、重复后超限、任一越界，并与 MCP DTO 一致。
- `server.base_url` 同时派生 base/rest/mcp URL；不存在 MCP 专用 URL fallback。
- Authorization header 不出现在日志捕获中。

### 16.4 MCP 合同测试

- `initialize` 报告真实 build version、tools capability 和支持协议。
- `tools/list` schema golden：六个工具名称、description、input/output schema、annotations。
- 不同 scope 的 tool list 精确过滤。
- 直接调用被过滤工具仍失败，不能绕过 list。
- 六个 tool 的 typed input、structuredContent、JSON text fallback 完全一致。
- `document_status/delete` schema 强制 `knowledge_base_id`；所有 KB 入参做绑定检查。
- `knowledge_search` schema 强制 1..limit 个 `knowledge_base_ids`，结果带 KnowledgeBase 来源。
- 两个 KB 使用同一模型快照时只调用一次 embedding；不同 model/config hash 分成不同组。
- 不同维度/模型的 query vector 不串用；合并只用统一 RRF score，最终排序和 tie-break 稳定。
- 请求 top-k 对所有库一致覆盖，`final_top_k` 是全局上限。
- 任一库 not-ready/provider/query/stale 失败时 all-or-nothing；errgroup 取消其它调用。
- output schema validation 开启且真实执行。
- 领域错误映射为稳定 `isError`，未预期错误不泄漏。
- `/mcp` 缺 key、invalid、expired、revoked 为 HTTP 401。
- stateless 模式不依赖 `Mcp-Session-Id`；GET streaming 返回 405。
- context cancellation 能到达 fake embedding/repository。
- 8 MiB MCP inline limit 与 REST 50 MiB limit 相互独立。

### 16.6 真实 E2E

用真实单二进制、临时 PostgreSQL/pgvector、临时 Redis：

1. admin 在整页表单创建绑定两个 KB、四 scope、不限期的 API Key；刷新详情后仍可 reveal/复制。
2. 用 Bearer REST 创建 KB，证明新 KB 原子加入调用 key 范围；再导入、轮询、获取 Chunk、删除。
3. 建立“两个 KB 共用模型 A、一个 KB 使用模型 B”的真实索引；REST/MCP 多库检索证明 A 只 embed 一次、B 单独 embed、结果合并且带 KB 来源。

6. 分别创建 90 天和不限期 key，固定/推进时钟验证状态；吊销后下一次 REST/MCP 都 `401`。
7. 浏览器覆盖列表 -> 创建 -> 详情 reveal -> 刷新 -> 再 reveal -> 复制 MCP 配置 -> 吊销的桌面与移动流程。
8. 证明 reveal/header/query/log 中不泄漏 secret，`/mcp` 与 `/api/v1/*` 不落入 SPA fallback。

## 18. 验收标准

v0.6.0 只有同时满足以下条件才可标记完成：

1. owner/admin 能创建、列出、查看、重复 reveal/复制和吊销 Workspace API Key；member 不能管理。
2. key 使用 32-byte `crypto/rand` 与 `lhk_` 格式；hash 只用于鉴权，域隔离的 AES-GCM 密文只用于 reveal，普通鉴权不解密。
3. 每个 key 原子绑定至少一个 KnowledgeBase；未绑定范围和其下资源统一 404；创建 KB 时新绑定原子加入。
4. scope、默认 90 天、最大 365 天、不限期、到期、吊销和最近使用合同全部生效。
5. Browser Session 与 machine Bearer 边界明确；无效 Bearer 不回退 Cookie。
6. `server.base_url` 是 Web/REST/MCP/邀请 URL 的唯一事实源，支持部署前缀且生产 HTTPS。
7. `/mcp` 由 `mcp-go v0.57.0` 提供 stateless Streamable HTTP，API-Key-only，不进入 SPA fallback。
8. 六个工具使用 typed schema；`knowledge_search` 支持多个绑定 KB，按 Embedding 模型快照分组、组内复用 query embedding、统一 RRF 后确定性合并。
9. REST/MCP Search 返回一致且带 KnowledgeBase 来源的 evidence，不生成答案，不直接比较不同模型的向量分数。
10. 错误、日志、缓存、常驻 DOM、诊断和测试输出中不存在完整 API Key、hash、密文、Provider credential 或完整文档 payload。
11. Web Console 的列表/创建/详情都是完整 AppShell 整页 route；桌面、移动、键盘、焦点、重复 reveal 流程通过测试与 E2E。
12. 数据库测试只使用临时 pgvector 容器；完整 Go/Web/集成/E2E/单二进制验证通过。
13. 接入文档能让新客户端从全局 Base URL 和任一仍可 reveal 的 API Key 跑通 REST 与 MCP 主链路。
