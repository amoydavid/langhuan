# v0.8.0 可靠性与运维能力设计规格

## 1. 目标与范围

让琅嬛具备长期内部运行和进入 v1.0.0 发布验收所需的可观测、可恢复和资源保护能力。本版本在已交付的 REST/MCP/Web 消费闭环、飞书同步、MinerU PDF、混合检索之上，补齐"运维侧"的地基，使导入失败可自助恢复、性能可观测、队列可治理、资源可保护。

本版本覆盖：

- **失败可恢复**：提供 Document/Revision 失败重试入口与 Generation reindex 入口，保证幂等。
- **asynq 任务治理**：明确重试次数、退避策略、超时、并发上限，引入 Inspector 提供队列可见性与死信管理。
- **可观测性**：导入主链路分阶段耗时与关键计数、结构化日志字段统一与敏感信息脱敏、`/readyz` 真实依赖探活、Prometheus metrics（HTTP 与导入阶段）。
- **资源保护**：受限批量导入的配置化上限（文件大小、图片数量/大小、解压大小、chunk 数量、embedding batch 与并发）；failed/staging/retired 投影的定时清理收敛。
- **备份恢复演练**：数据库、对象存储与配置的备份/恢复 runbook 与可重复的 smoke。

本版本不覆盖：

- Chat/Agent/LLM 回答生成、Rerank 新模型、新 parser 格式。
- 将 FTS/向量读写拆分为 `adapters/index/` 独立 port（ROADMAP 明确：等出现可替换后端再拆）。
- PostgreSQL AGE 图查询、GraphRAG。
- 改变现有协议命名空间（REST `/api/v1/*`、MCP `/mcp`、SPA `/`）。

## 2. 当前实现约束

实现必须遵守以下既有合同，不因运维能力新增而破坏：

- 资源属于 `workspace`，所有 DB 操作进入 `WithinWorkspace`；跨 workspace 统一 404。
- `domain` 不依赖 HTTP/MCP/数据库/第三方 SDK；`application` 不持有 `*gorm.DB`。
- Repository 是 GORM 薄封装，只做持久化，不放置业务规则；worker handler 只解码 payload 并调用 application service。
- 所有任务幂等：执行前检查状态，`completed/deleted` 直接跳过；入队使用稳定 TaskID（`queue.DocumentTaskID` 等）保证 asynq 端去重。
- `DocumentRevision` 不可变，更新必须创建新 revision；`retrieval_entries` 是可重建投影。
- HNSW 部分索引：查询侧表达式必须与 `000001_init` 预建索引完全一致（`embedding::halfvec(N)` + `WHERE dimension = N`）。
- 测试数据库只能用测试运行期临时拉起的 pgvector/zhparser docker 容器，严禁连 `config.yaml` 的库（AGENTS.md 5.10）。
- 日志不记录 API key、token、完整用户文档内容、Provider credential。

当前代码中的以下行为在本版本明确补齐（现状为缺失）：

- asynq `Server.Config` 仅配 `Queues`（`cmd/langhuan/main.go:294`），`Concurrency`/`RetryDelayFunc`/`Logger`/`ErrorHandler` 全部走库默认；入队侧 `adapters/queue/asynq/queue.go:24` 不设 `MaxRetry`/`Timeout`/`Retention`。
- 不存在 `asynq.Inspector`，无队列可见性与手动重试/归档能力。
- 不存在任何 reindex / retry / rebuild 的对外入口；手动上传文档失败后只能重新上传。
- `/healthz`（`http/health.go`）不探任何依赖；无 `/readyz`；无 `/metrics`；`go.mod` 无 prometheus 依赖。
- `logger.New`（`logger/logger.go`）无脱敏机制（仅 mineru/embedding 错误消息局部脱敏）；无统一字段约定。
- 导入主链路（parse/chunk/embed/index/publish）无阶段耗时记录（仅 DB 时间戳，非度量）；search 链路已有 `total_duration_ms` 范式可参考。

## 3. 失败重试入口

### 3.1 语义

为"失败"状态的 Document/Revision 提供用户可触发的重试，重置该 revision 回 `pending` 并重新入队 `document_parse_start`，完整重跑 parse→chunk→index→publish。重试必须幂等：重复请求不产生重复 revision、chunk、asset 或 retrieval_entries。

支持两类粒度（底层复用同一 service 方法）：

- **Document 重试**：按 `document_id` 重试其最新 revision（典型：手动上传文档在 embedding/index 阶段失败）。
- **Job 重试**：按 `job_id` 重试该 job 关联的 revision（覆盖 source_sync 之外的 failed job）。

### 3.2 通用化 ResetFailedRevision

现状 `SourceSyncDBStore.RetrySourceRevision`（`source_sync_store.go:654`）已实现完整的失败复位逻辑（锁 Document + 锁 Revision + revision→pending + 复位/新建 parse Job + 复活 document），但耦合飞书上下文（`SHA256`、`Title`、`ParentNodeID`、软删恢复）。

本版本**不破坏飞书路径**，新增一个通用方法 `DocumentTaskStore.ResetFailedRevision`（接口定义在 `application/service`，实现 `internal/infrastructure/db`）：

```go
// ResetFailedRevisionRequest 复位一个 failed revision 以重跑 parse。
type ResetFailedRevisionRequest struct {
    WorkspaceID     uuid.UUID
    KnowledgeBaseID uuid.UUID
    DocumentID      uuid.UUID
    RevisionID      uuid.UUID
    // Optionals：飞书重抓时内容可能变化，手动重试场景全部留空。
    SHA256   string // 非空则刷新 revision hash
    Title    string // 非空则更新 document.title
    Revive   bool   // true 则清空 deleted_at（飞书删除恢复）；手动重试默认 false
}

// ResetFailedRevisionResult 返回复位后的 job id（供调用方入队）。
type ResetFailedRevisionResult struct {
    JobID uuid.UUID
}
```

实现语义（在 `WithinWorkspace` 事务内）：

1. 锁定 Document + Revision（FOR UPDATE）。
2. 校验 revision 状态为 `failed`（非 failed 返回 `domainerrors.ErrConflict`，不静默成功）。
3. 复位 revision：`status`→`pending`、清空 `error_class`/`error_message`、`completed_at`→nil；可选刷新 `sha256`。
4. parse Job：找该 revision 最近的 `document_parse_start` job，存在则重置为 `pending`（清 error），不存在则新建。
5. document：`status`→`pending`；可选更新 `title`；`Revive=true` 时清空 `deleted_at`。

> 不动飞书路径：飞书 `RetrySourceRevision` 内部改为**委托** `ResetFailedRevision`（传入 SHA256/Title/Revive=true），保留其签名以避免大面积改动调用方；或保留原实现并在 spec 中记录两者关系。决策：**保留飞书 `RetrySourceRevision` 原样**（它已稳定且有覆盖测试），新增 `ResetFailedRevision` 供手动重试专用，二者共享"复位 revision + 复位/新建 job"的语义但物理独立，避免为去重而引入回归风险。这是与 5.7「避免盲目复杂化」一致的折中。

### 3.3 Application service

新增 `DocumentRetryService`（`internal/application/service/document_retry.go`）：

```go
type DocumentRetryServiceDeps struct {
    Store  DocumentRetryStore   // 提供 ResetFailedRevision + GetLatestRevisionForDocument/GetJob
    Queue  queue.JobQueue
    Logger *slog.Logger
}

// RetryDocument 重试文档最新 revision；返回 {job_id, revision_id}。
func (s *DocumentRetryService) RetryDocument(ctx, workspaceID, documentID, actorRole) (*RetryResult, error)
// RetryJob 重试 job 关联的 revision。
func (s *DocumentRetryService) RetryJob(ctx, workspaceID, jobID, actorRole) (*RetryResult, error)
```

职责：

1. 校验 admin/owner 角色（member 拒绝 `ErrForbidden`）。
2. 定位 revision（RetryDocument：最新 revision；RetryJob：job 关联 revision）+ 校验 active Generation 存在。
3. 事务内调 `ResetFailedRevision`（Revive=false）。
4. 事务外入队 `document_parse_start`，TaskID 用 `queue.DocumentTaskID("document_parse_start", ws, rev, activeGen)`。

入队失败处理：参考 `IndexGenerationService.Create` 的模式（`RecordFailure` 把 job 标 failed + 返回 cause），但此处 job 刚被复位为 pending，入队失败时标记 job failed + error_class=`enqueue_error`，不破坏 revision（仍可再次重试）。

### 3.4 入队 helper 下沉

worker 包 `createAndEnqueueWithJobPayloadAndExtra`（`document_tasks.go:493`）与 source_sync `enqueueParseJob`（`source_sync.go:1057`）是两处入队实现。重试路径在 application service 入队，需要可复用 helper。

新增 `DocumentRetryService.enqueueParseStart(ctx, ws, kb, doc, rev, gen)`，封装 JobRequest 构造 + 稳定 TaskID。worker 与 source_sync 的入队**暂不强制改造**（避免回归），重试路径独立使用新 helper；后续可在另一次重构中统一。这与 5.7 一致：不为去重而冒回归风险。

## 4. Generation Reindex（复用双缓冲）

### 4.1 语义

reindex = 用当前 active Generation 的**相同配置**（embedding model / chunking / retrieval / rerank 全部继承）创建一个新的 building Generation，构建完成后由用户显式激活。**不做 active generation 的就地重跑**，确保重跑期间检索始终可用、可回退。

### 4.2 实现路线（复用现有零件）

探查确认：`IndexGenerationService.Create`（`index_generation.go:91`）在 `EmbeddingModelID==Nil`、`ChunkingConfig==nil`、`RetrievalConfig==nil`、`Rerank==nil` 时，**全部继承 active base 配置**（见 `generationChunkingConfig`/`generationRetrievalConfig` 的 nil 分支，line 123-130）。reindex 是 `Create` 的特例。

新增 `IndexGenerationService.Reindex`：

```go
func (s *IndexGenerationService) Reindex(ctx context.Context, workspaceID, knowledgeBaseID uuid.UUID, actorRole value.WorkspaceRole) (*dto.IndexGeneration, error) {
    if !actorRole.AtLeast(value.RoleAdmin) {
        return nil, domainerrors.ErrForbidden
    }
    // 直接委托 Create，入参全部传零值/nil，强制走继承分支。
    return s.Create(ctx, CreateIndexGenerationInput{
        WorkspaceID:      workspaceID,
        KnowledgeBaseID:  knowledgeBaseID,
        ActorRole:        actorRole,
        // EmbeddingModelID / ChunkingConfig / RetrievalConfig / Rerank 全部零值 → 继承 base
    })
}
```

复用带来的正确性保证：

- `Create` 会计算 `modelHash`/`configHash`，配置相同时新 Generation 的 `ConfigHash` == active 的 `ConfigHash`（正确：reindex 不改变配置，只重建投影）。
- `CreateIndexGeneration` 的"禁止两个 building 并存"约束（`index_generation_store.go:150` 返回 `ErrGenerationBuildInProgress`）天然防止重复 reindex。
- 用户后续通过现有 `POST .../index-generations/:id/activate` 激活，旧 active 由 `ActivateIndexGeneration` 退役。

### 4.3 不需要新增的能力

- **不需要** 新增"按 generation 删除 retrieval_entries"方法（双缓冲路线下，旧 active entries 在 activate 切换时由现有 `ActivateIndexGeneration` 退役，cleanup 周期清理）。
- **不需要** 放开 `IndexGenerationBuildService.Run` 的 "必须 building" 约束。
- **不需要** 新迁移表结构。

## 5. asynq 任务治理

### 5.1 配置化策略

`internal/infrastructure/config/config.go` 新增 `QueueConfig`：

```yaml
queue:
  concurrency: 8              # worker 并发数
  retry:
    max_attempts: 5           # 含首次执行的总尝试次数（覆盖库默认 25）
    min_backoff_seconds: 30
    max_backoff_seconds: 3600
  task_timeout_seconds: 1800  # 单任务最大执行时长
```

`QueueConfig` 提供 `Defaults()` 方法，确保零值字段回退到上述默认，避免空配置导致 asynq 用库默认（MaxRetry=25）。

### 5.3 Server 侧（`cmd/langhuan/main.go` worker 初始化，line 294）

`hibikenasynq.NewServer` 的 `Config` 补齐：

```go
serverCfg := hibikenasynq.Config{
    Queues:       map[string]int{"default": 1},
    Concurrency:  cfg.Queue.Concurrency,
    RetryDelayFunc: retryDelayFunc(cfg.Queue.Retry),  // 指数退避，min/max 封顶
    ErrorHandler: asynqErrorHandler(log),             // 终态回调
    Logger:       asynqSlogAdapter{log},              // 接 slog
    LogLevel:     asynq.LogLevelInfo,
}
```

- `retryDelayFunc`：`asynq.RetryDelayFunc`，基于 `min_backoff * 2^n`，封顶 `max_backoff`。
- `asynqSlogAdapter`：实现 asynq 的 `Logger` 接口，转发到 slog，避免 asynq 默认 logger 输出非结构化日志。
- `asynqErrorHandler`：`asynq.ErrorHandler`，在任务到达 `MaxRetry` 终态时记录结构化日志（task type / task id / error），与 worker handler 内现有 `failPipelineRun` 的业务侧终态落库互补（ErrorHandler 是 asynq 层兜底，覆盖 handler 未捕获的 panic 等）。

## 6. 可观测性

### 6.1 结构化日志统一与脱敏

**统一字段约定**：新增 `internal/infrastructure/logger/attrs.go`，固化字段名：

- lineage：`workspace_id`、`knowledge_base_id`、`document_id`、`revision_id`、`job_id`、`index_generation_id`。
- 运维：`request_id`、`transport`、`principal_kind`、`event`、`stage`、`status`、`duration_ms`、`error_class`、`attempt`。

各模块（worker `lineageAttrs`、search allowlist、新导入耗时）统一引用，消除命名分歧。提供 helper：`logger.LineageAttrs(ws, kb, doc, rev, job, gen) []any`。

**脱敏层**：扩展 `logger.New(level, opts ...Option)`，新增 `WithRedact()` 选项，在 `slog.HandlerOptions.ReplaceAttr` 中对 value 含敏感特征的字符串字段 mask（→ `***`）：

- 字段名匹配：`authorization`、`bearer`、`api_key`、`token`、`password`、`secret`、`dsn`（不区分大小写）。
- 值内容匹配：`Bearer `、`lhk_`（API key 前缀）、看起来像 base64 32-byte key 的长串。
- 配置开关 `log.redact`（默认 true），可关闭用于本地 debug。

> 现状 grep 确认日志目前未直接打 token/password（API key 服务只记 `api_key_id`）。脱敏层是**防御性机制**，防止未来新增的 `slog.Any(err)` 或 debug 日志泄漏，不改变现有打点。

### 6.2 /readyz

新增 `GET /api/v1/readyz`（无鉴权，供 readiness probe），`internal/interfaces/http/readyz.go`：

- ping PostgreSQL（`gormDB.Exec("SELECT 1")`，超时 2s）。
- ping Redis（`redisClient.Ping`，超时 2s）。
- 可选：查 asynq Inspector 的 pending 总数，超阈值（`observability.readiness.queue_pending_threshold`）返回 not ready。
- 任一失败返回 503 + `{"status":"not_ready","checks":{"db":"ok|fail","redis":"ok|fail",...}}`，全成功返回 200。

`/healthz` 保持现状（轻量存活探针，不探依赖），二者职责分离。readyz handler 通过依赖注入接收 DB/Redis/Inspector（避免 handler 直接持有全局）。

### 6.3 Prometheus metrics

引入 `github.com/prometheus/client_golang`。新增 `internal/infrastructure/metrics` 包：

**HTTP 指标**（Gin 中间件，挂全局中间件链）：

- `langhuan_http_requests_total{method,route,status}` counter。
- `langhuan_http_request_duration_seconds{method,route,status}` histogram。

**导入链路指标**：

- `langhuan_document_stage_duration_seconds{stage,status}` histogram，`stage` ∈ `parse|chunk|embed|index|publish`。
- `langhuan_document_stage_total{stage,status}` counter。
- `langhuan_embedding_calls_total{provider,status}` counter。

**队列指标**（Inspector 周期采集，可选）：

- `langhuan_asynq_queue_size{queue,state}` gauge，`state` ∈ `pending|retry|active|dead`。

**Recorder 接口**（定义在 application 层，避免 application→prometheus 硬依赖）：

```go
// internal/application/observability/recorder.go（或 ports）
type StageRecorder interface {
    ObserveStage(ctx context.Context, stage string, status string, duration time.Duration)
}
```

实现 in `infrastructure/metrics`，注入到 worker 驱动层。

**端点**：`GET /metrics`（`promhttp.Handler()`），挂在 `/api/v1` 之外，无鉴权（便于 Prometheus scrape，网络层隔离）。配置 `observability.metrics.enabled`（默认 true）、`observability.metrics.path`（默认 `/metrics`）。

### 6.4 导入主链路阶段耗时

参考 `search_observability.go` 的 allowlist + terminal event 模式，新增 `application/pipeline/pipeline_observability.go`（或 worker 层）。**决策：在 worker 驱动层打点**（`document_tasks.go` 的 `HandleDocumentParseStart/Index` 已持有完整 lineage），原因：

- pipeline stage（`parse_stage.go` 等）保持纯净，不引入 metrics 依赖。
- worker 层天然知道每个 stage 的开始/结束边界。
- metrics observe 通过注入的 `StageRecorder` 接口完成，不引入 application→metrics 硬依赖。

terminal event：`pipeline.stage.completed` / `pipeline.stage.failed`，带 lineage + `stage`/`duration_ms`/`error_class`。worker 现有 `lineageAttrs`/`jobAttrs`（`document_tasks.go:86`）复用统一 attrs helper。

## 7. 资源保护

### 7.1 配置化上限

`config.go` 已有 `Ingest.MaxFileSizeBytes`、`Storage.Assets`、`MinerU.MaxZipImageBytes`。本版本收敛并补齐：

```yaml
ingest:
  max_file_size_bytes: 104857600        # 已有
  allowed_file_types: [...]             # 已有
  max_chunks_per_document: 50000        # 新增：单文档 chunk 上限
embedding:
  batch_size: 64                        # 新增：单次 embedding batch
  max_concurrency: 4                    # 新增：并发 embedding 调用上限
```

落地：

- **chunk 限制**：分块后（`chunk_stage.go`）校验 chunk 数量超限 → terminal failed（`error_class=chunk_limit_exceeded`），不继续 embed/index。
- **embedding 并发**：`index_stage.go` 的 embedding 调用用 `errgroup` + semaphore 限制并发为 `embedding.max_concurrency`，batch 按 `embedding.batch_size` 切分（确认现状分批逻辑并配置化）。

### 7.2 投影清理收敛

现状已有 `RetrievalCleanupService`（`retrieval_cleanup.go`）+ `source_cleanup`。本版本确保：

- `failed`/`staging`/`retired` 三态投影都在定时清理覆盖内（现状 cleanup 按 `failed_staging_retention`/`retired_generation_retention` 删，确认 failed Generation 的 staging entries 也被覆盖）。
- 清理周期配置化（现状在 `RetrievalConfig`，确认有调度触发，必要时补 `CleanupIntervalSeconds` 与定时 goroutine）。

> 评估：现状 `RetrievalCleanupRepository.Cleanup`（`retrieval_cleanup_repository.go:26`）按时间删 staging/failed/retired，但需确认是否有**定时触发**（asynq 定时任务或 goroutine）。若无，本版本补一个轻量定时清理（asynq scheduler 或 `time.Ticker` goroutine + context 取消），保证投影不无限增长。

## 9. 数据库变更

本版本**尽量不新增迁移**。jobs 表现状字段（`attempts`/`error_class`/`error_message`/`updated_at`）足够定位业务侧失败；死信的运维细节（`last_failed_at`、完整失败历史）交 asynq Inspector（Redis 侧）。

不新增迁移的依据：

- reindex 复用双缓冲（新 building Generation 走现有表）。
- 重试复位现有 jobs/document_revisions 字段。
- metrics 是运行期数据，不入库。
- 配置项不入库。
- 死信可见性由 asynq Redis 提供，jobs 表无需 `last_attempt_at`。

> 若实施中发现确需持久化 dead-letter 标记或清理审计，才新增迁移（版本号严格递增、幂等、带 down），并同步更新本节。

## 10. REST 与 MCP 变更

### 10.1 REST 新增

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| POST | `/api/v1/workspaces/:slug/knowledge-bases/:id/reindex` | admin/owner | 触发 reindex（建 building gen + 入队），返回 `{generation_id, job_id}` |
| POST | `/api/v1/workspaces/:slug/knowledge-bases/:id/documents/:document_id/retry` | admin/owner | 重试失败文档最新 revision，返回 `{job_id, revision_id}` |
| POST | `/api/v1/workspaces/:slug/jobs/:job_id/retry` | admin/owner | 重试失败 job 关联的 revision |
| GET | `/api/v1/readyz` | 无 | 依赖就绪探活 |
| GET | `/metrics` | 无 | Prometheus 指标 |
| GET | `/api/v1/admin/queues` | platform admin | 队列可见性 |
| GET | `/api/v1/admin/queues/:queue/dead` | platform admin | 死信列表 |
| POST | `/api/v1/admin/queues/:queue/dead/:task_id/retry` | platform admin | 手动重试死信 |
| DELETE | `/api/v1/admin/queues/:queue/dead/:task_id` | platform admin | 归档死信 |

错误结构复用现有稳定错误合同（`error_class` + message），reindex/retry 在非 failed 状态返回 409 Conflict（`error_class=not_retryable`），越界返回 404。

### 10.2 MCP 新增

- `document_retry`：按 `document_id` 重试失败文档（程序化消费场景：外部触发重试后 poll `document_status`）。复用现有 Bearer + scope 校验，需 `documents:write` scope。
- **不在 MCP 暴露** reindex、队列管理（这些是 admin 运维操作，非程序化消费）。

### 10.3 Web Console

- **Indexes 页**：failed Generation 行增加"重试"/"reindex"入口；building 中 Generation 显示进度（复用现有 job 状态轮询）。
- **Document 详情/列表**：failed 文档行增加"重试"按钮，提交后乐观更新 + 轮询 job 状态。
- **平台管理**：新增队列监控页（pending/retry/dead 计数 + 死信列表 + 手动重试/归档），platform admin 可见。
- 所有新操作走 TanStack Query mutation + invalidate，统一 loading/error/toast。

## 14. 验收标准（对照 ROADMAP v0.8.0）

- **可定位**：可定位导入慢、解析失败、embedding 失败、索引失败和发布失败发生在哪个阶段，并关联 workspace/document/revision/job/generation。（✅ 阶段耗时 metrics + 统一日志 lineage + asynq ErrorHandler）
- **资源不无限占用**：大文件、压缩炸弹、异常图片、慢 Provider 和积压任务不会无限占用 worker 资源。（✅ task timeout + concurrency + chunk/embedding 限制）
- **失败可安全重试**：失败文档可安全重试，重复请求和 worker 重启不破坏 active Generation。（✅ 幂等重试 + 双缓冲 reindex）
- **空库可安装/备份/恢复/smoke**：在空数据库与空对象存储上可重复完成安装、备份、恢复和单二进制 smoke。（✅ 备份恢复 runbook + smoke）
- **测试全绿**：`go test ./...`、集成测试、`go vet ./...`、`pnpm check/test/build`、MCP E2E 全部通过。

## 15. 安全注意

- 日志脱敏默认开启（`log.redact: true`），覆盖 authorization/bearer/api_key/token/password/secret/dsn 及 `lhk_` 前缀。
- 死信列表端点不返回 task payload 正文（可能含文档片段/文件路径）。
- 队列管理端点限 platform admin；REST reindex/retry 限 workspace admin/owner；MCP retry 复用现有 Bearer + scope 校验。
- 备份 runbook 强调 encryption_key 与 config.yaml 的独立保管，不入版本库。
- `config.yaml` 中现有明文 `encryption_key`/`client_secret` 属遗留风险，本版本同步建议改为环境变量注入并轮换（若涉及 OIDC client_secret 则单独评估，不在本 spec 强制）。
- metrics 端点无鉴权，依赖网络层隔离（部署文档说明）；不暴露敏感 label（不放 document 内容、只放聚合维度）。
