# 琅嬛 v0.1.0 工程骨架与基础运行设计规格

## 1. 背景

琅嬛是 RAG 工程中的知识转化与检索服务。它负责把文档、文本和表格内容转成可追溯、可索引、可向量检索的结构，并通过 REST 与 MCP 对外提供能力。

v0.1.0 只建立工程骨架、运行时入口、基础依赖连接、领域模型和端口边界。它不实现文档导入流水线、不调用 MinerU Cloud、不做 embedding、不写 pgvector 索引，也不实现图查询。

## 2. 目标

v0.1.0 交付一个可启动、可测试、可演进的 Go 1.26 服务骨架：

- 单一二进制入口 `cmd/langhuan`。
- 同一进程内挂载 REST、MCP 和 asynq worker 的 wiring。
- 接入 YAML 配置、日志、PostgreSQL、Redis、GORM、asynq。
- 定义核心领域模型：`KnowledgeBase`、`Document`、`Chunk`、`Asset`、`Job`。
- 定义当前已确认需要的 ports：`DocumentParser`、`AssetStore`、`EmbeddingClient`、`VectorIndex`、`KeywordIndex`、`JobQueue`。
- 提供基础 REST：
  - `GET /healthz`
  - `POST /api/v1/knowledge-bases`
  - `GET /api/v1/knowledge-bases/:id`
- 提供基础 MCP server 挂载点，但 v0.1.0 不要求暴露完整业务工具。

## 3. 非目标

v0.1.0 明确不做：

- 文档上传、解析、分块、索引。
- MinerU Cloud API 调用。
- OSS 图片归档。
- embedding API 调用。
- pgvector 向量写入和检索。
- PostgreSQL FTS 检索。
- PostgreSQL AGE、GraphRAG 或图查询接口。
- Chat、Agent、LLM 答案生成。
- 前端管理台。
- 多租户权限模型。

## 4. 架构决策

### 4.1 单入口进程

琅嬛只有一个命令入口：

```text
cmd/langhuan/main.go
```

该进程负责：

- 加载 YAML 配置。
- 初始化日志。
- 连接 PostgreSQL。
- 连接 Redis。
- 初始化 GORM repositories。
- 初始化 asynq client/server。
- 注册 REST routes。
- 挂载 MCP HTTP endpoint。
- 注册 worker handlers。

v0.1.0 可以通过配置控制是否启动 HTTP server 或 worker，但不拆成 `langhuan-server`、`langhuan-worker`、`langhuan-mcp` 多个命令。

配置从 YAML 文件读取。默认读取当前工作目录下的 `config.yaml`，也允许通过命令行参数指定配置文件路径。环境变量不作为主配置入口。

### 4.2 分层边界

```text
cmd/
  langhuan/

internal/
  interfaces/
    http/
    mcp/
    worker/

  application/
    service/
    dto/

  domain/
    model/
    value/
    errors/

  ports/
    parser/
    storage/
    embedding/
    index/
    queue/

  adapters/
    queue/
      asynq/

  infrastructure/
    config/
    db/
    logger/
    migrate/
```

依赖方向：

- `domain` 不依赖外部框架。
- `ports` 定义业务需要的外部能力接口。
- `application` 依赖 `domain` 和 `ports`。
- `interfaces` 依赖 `application`。
- `adapters` 实现 `ports`。
- `infrastructure` 提供配置、数据库、日志和迁移基础设施。

v0.1.0 可以只实现必要 adapter，例如 asynq queue adapter。parser、storage、embedding、index adapter 可先只定义接口，不写空实现。

### 4.3 领域模型

#### KnowledgeBase

表示一个知识库。v0.1.0 需要支持创建和读取。

字段：

- `ID`
- `Name`
- `Description`
- `EmbeddingDimension`
- `ChunkingConfig`
- `Metadata`
- `CreatedAt`
- `UpdatedAt`

约束：

- `Name` 必填。
- `EmbeddingDimension` 必须大于 0。
- 一个知识库固定一个 embedding 维度。
- v0.1.0 不验证具体 embedding model。

#### Document

表示导入文档。v0.1.0 只定义模型和表结构，不提供导入 API。

字段：

- `ID`
- `KnowledgeBaseID`
- `Title`
- `FileType`
- `SourceType`
- `Status`
- `SHA256`
- `NormalizedMarkdown`
- `Metadata`
- `ErrorMessage`
- `CreatedAt`
- `UpdatedAt`

初始状态枚举预留：

- `pending`
- `parsing_submitted`
- `parsing`
- `parsed`
- `indexing`
- `completed`
- `failed`
- `deleting`
- `deleted`

v0.1.0 只需定义枚举和值对象，不需要状态机执行逻辑。

#### Chunk

表示文档分块。v0.1.0 只定义模型和表结构。

字段：

- `ID`
- `DocumentID`
- `Sequence`
- `Content`
- `ContextHeader`
- `SourceAnchor`
- `Metadata`
- `CreatedAt`

约束：

- `Content` 保存原文片段。
- `ContextHeader` 用于未来 embedding 输入，不破坏原文定位。
- `SourceAnchor` 使用 JSON 保存页码、sheet、行列、offset 等锚点。

#### Asset

表示文档解析产生或引用的图片等资产。v0.1.0 只定义模型和表结构。

字段：

- `ID`
- `DocumentID`
- `OriginalRef`
- `StorageKey`
- `PublicURL`
- `MimeType`
- `SHA256`
- `SizeBytes`
- `Metadata`
- `CreatedAt`

#### Job

表示异步任务记录。v0.1.0 需要表结构和基础类型，为后续 asynq 任务链做准备。

字段：

- `ID`
- `DocumentID`
- `Type`
- `Status`
- `Attempts`
- `ExternalJobID`
- `Payload`
- `ErrorMessage`
- `CreatedAt`
- `UpdatedAt`

状态：

- `queued`
- `running`
- `succeeded`
- `failed`
- `cancelled`

## 5. Port 设计

v0.1.0 要定义端口，但只实现当前需要 wiring 的部分。

### DocumentParser

```go
type DocumentParser interface {
    Parse(ctx context.Context, input ParseInput) (*ParsedDocument, error)
    Supports(fileType string) bool
}
```

v0.1.0 不实现 MinerU Cloud adapter。

### AssetStore

```go
type AssetStore interface {
    Put(ctx context.Context, object ObjectInput) (*StoredObject, error)
    Delete(ctx context.Context, key string) error
}
```

v0.1.0 不实现 OSS adapter。

### EmbeddingClient

```go
type EmbeddingClient interface {
    Embed(ctx context.Context, texts []string) ([][]float32, error)
    Dimension() int
}
```

约束：

- 实现方必须校验返回向量维度。
- v0.1.0 不实现外部 API adapter。

### VectorIndex

```go
type VectorIndex interface {
    UpsertChunks(ctx context.Context, records []VectorRecord) error
    DeleteDocument(ctx context.Context, documentID string) error
}
```

v0.1.0 不实现 pgvector 写入逻辑，但数据库迁移需要启用 `vector` extension。

### KeywordIndex

```go
type KeywordIndex interface {
    UpsertChunks(ctx context.Context, records []KeywordRecord) error
    DeleteDocument(ctx context.Context, documentID string) error
}
```

v0.1.0 不实现 FTS 写入逻辑。

### JobQueue

```go
type JobQueue interface {
    Enqueue(ctx context.Context, job JobRequest) (*JobHandle, error)
}
```

v0.1.0 需要提供 asynq adapter 的最小实现和 worker 注册能力。

## 6. REST API

### GET /healthz

返回服务健康状态。

响应：

```json
{
  "status": "ok",
  "service": "langhuan"
}
```

v0.1.0 不要求深度检查 PostgreSQL/Redis，但允许包含可选详情。

### POST /api/v1/knowledge-bases

创建知识库。

请求：

```json
{
  "name": "产品文档",
  "description": "内部产品知识库",
  "embedding_dimension": 1536,
  "chunking_config": {
    "chunk_size": 512,
    "chunk_overlap": 80
  },
  "metadata": {}
}
```

响应：

```json
{
  "id": "uuid",
  "name": "产品文档",
  "description": "内部产品知识库",
  "embedding_dimension": 1536,
  "chunking_config": {
    "chunk_size": 512,
    "chunk_overlap": 80
  },
  "metadata": {},
  "created_at": "2026-06-17T00:00:00Z",
  "updated_at": "2026-06-17T00:00:00Z"
}
```

校验：

- `name` 必填。
- `embedding_dimension` 必须大于 0。
- `chunk_size` 和 `chunk_overlap` 可选；未传时使用默认值。

### GET /api/v1/knowledge-bases/:id

读取知识库。

响应同创建接口。

错误：

- 不存在返回 404。
- 非法 UUID 返回 400。

## 7. MCP

v0.1.0 只要求 MCP endpoint 能挂载在同一 HTTP server 中，并能返回基础 server 信息或空工具列表。业务 MCP tools 从 v0.6.0 开始进入完整交付范围。

约束：

- MCP 不能使用独立命令入口。
- MCP 和 REST 共享 application service。
- MCP handler 不直接访问数据库。

## 8. Worker 与 asynq

v0.1.0 需要完成 asynq 基础接入：

- Redis client 配置。
- asynq client 初始化。
- asynq server 初始化。
- worker mux 注册。
- 至少注册一个内部 smoke task，例如 `system_smoke`。

`system_smoke` 只用于证明 worker 能接收任务和执行 handler，不进入业务 API。

v0.1.0 不实现：

- `document_parse_start`
- `document_parse_poll`
- `document_index`

这些任务属于 v0.2.0。

## 9. 数据库迁移

v0.1.0 需要提供可执行迁移，至少包含：

- `knowledge_bases`
- `documents`
- `chunks`
- `document_assets`
- `jobs`
- `chunk_embeddings`
- `chunk_keywords`

PostgreSQL extension：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

表约束：

- 主键使用 UUID。
- 外键表达父子关系。
- 常用查询字段建立索引。
- JSON 字段使用 `jsonb`。

v0.1.0 不需要创建 AGE extension。

## 10. 配置

v0.1.0 使用 YAML 文件作为主配置入口。默认配置文件名为 `config.yaml`，可通过命令行参数指定其他路径。

本地开发环境已存在 PostgreSQL 数据库 `langhuan`，默认开发配置应连接该数据库。

建议配置结构：

```yaml
server:
  http_addr: ":8080"
  run_http: true
  run_worker: true

database:
  driver: postgres
  dsn: "postgres://localhost:5432/langhuan?sslmode=disable"

redis:
  addr: "127.0.0.1:6379"
  password: ""
  db: 0

log:
  level: info
```

v0.1.0 不配置 MinerU、OSS、embedding API。

约束：

- 不使用环境变量作为主配置方式。
- 配置加载失败时服务应启动失败并输出明确错误。
- 配置中的密钥后续必须避免写入日志；v0.1.0 先建立 redaction 约定。

## 11. 错误处理

统一错误响应：

```json
{
  "error": {
    "code": "validation_error",
    "message": "embedding_dimension must be greater than 0"
  }
}
```

错误码建议：

- `validation_error`
- `not_found`
- `conflict`
- `internal_error`

## 12. 测试要求

v0.1.0 需要覆盖：

- `KnowledgeBase` 创建参数校验。
- `KnowledgeBaseService` 创建和读取。
- HTTP `GET /healthz`。
- HTTP `POST /api/v1/knowledge-bases`。
- HTTP `GET /api/v1/knowledge-bases/:id`。
- YAML 配置加载、默认路径和命令行指定路径。
- asynq worker handler 注册 smoke test。
- 迁移 SQL 至少可被测试解析或在集成测试环境执行。

最低验证命令：

```bash
go test ./...
go vet ./...
git diff --check
```

如果提供 Docker Compose，则增加：

```bash
docker compose up -d postgres redis
go test ./... -tags=integration
```

## 13. 验收标准

v0.1.0 完成时必须满足：

- `go test ./...` 通过。
- `go vet ./...` 通过。
- `git diff --check` 通过。
- 服务可以启动并监听 HTTP 地址。
- 服务从 YAML 配置文件读取 HTTP、PostgreSQL、Redis 和 worker 开关。
- `GET /healthz` 返回 200。
- 可以创建知识库。
- 可以读取已创建知识库。
- 数据库迁移可执行。
- asynq worker 可启动并注册 handler。
- 代码中没有图查询、MinerU、OSS、embedding 或文档导入的业务实现。

## 14. 风险与约束

- Go 1.26 是明确技术基线，工程初始化时应使用 `go 1.26.0`。
- pgvector 的 `vector` extension 要求目标 PostgreSQL 已安装 pgvector。
- 本地开发默认使用已存在的 PostgreSQL 数据库 `langhuan`。
- asynq 依赖 Redis，开发环境需要明确提供 Redis。
- 配置必须通过 YAML 文件管理，不应在 v0.1.0 引入环境变量配置分支。
- v0.1.0 的 port 不应被写成空壳过度抽象；接口应只表达已确认的边界。
- MCP server 的库选择应和后续工具实现兼容，避免先做临时协议实现。

## 15. 后续版本衔接

v0.1.0 完成后，v0.2.0 将在当前基础上实现：

- 文档导入 API。
- document/job 状态机。
- `document_parse_start`、`document_parse_poll`、`document_index` 任务。
- 任务幂等和失败记录。

v0.3.0 再接入 MinerU Cloud PDF 解析和资产归档。
