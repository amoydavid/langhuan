- 实现计划：[`docs/superpowers/plans/2026-10-27-v1.4.0-telemetry-freshness.md`](../plans/2026-10-27-v1.4.0-telemetry-freshness.md)

- 前置调研结论（形成本稿的裁决依据）：
  - **裁决 1（本稿立足点）**：维护回路的缺口不是"检测"，而是"信号露出"。仓库核查确认——web 源已有 content_hash 三级变更检测、ETag/Last-Modified 条件请求、cron 定时同步与 force 全量重爬（v1.3.0）；飞书源已有 obj_edit_time 增量 cursor、content_hash 与删除软删检测；本地文件/FAQ 的用户变更（重传、chunk 修订、树移动、软删）全部已落库。**本版本不新建任何检测机制，只把已发生的事实变成可看、可行动、可验证的回路。**

  - **裁决 3（隐私边界）**：v0.9.0 合同「SearchRun 不保存 query 明文」**不破**——明文记录另立 opt-in 表（D1，草案建议开启能力但默认关闭），SearchRun 行为零改动。

## 1. 目标与范围

为琅嬛补上维护回路的另一半：检索已经发生、同步已经发生、内容变更已经发生，但没有任何聚合面回答「这个库的知识现在健康吗、哪里缺内容、哪些内容该清退」。本版本建立**记录 → 洞察 → 行动 → 验证**的最小闭环：

- **记录**：新增 chunk 级引用遥测 `search_citations`（每次检索返回了哪些 chunk、排第几），异步写入、不拖慢检索路径；新增按知识库 opt-in 的查询原文日志 `search_query_log`（D1）。
- **洞察**：工作台新增「健康」tab——空召回率（北极星指标）、零召回查询 Top N、沉睡内容（长期零引用文档）Top N、内容动态 feed（同步/更新/删除统一时间线，覆盖 web、飞书、本地文件、FAQ 四类来源）。
- **行动**：全部挂接既有能力，不新增写路径——零召回→创建 FAQ（预填问题）、沉睡内容→查看/软删、源变更→立即同步/强制重爬（补 UI 按钮）、检索测试→带查询跳转。
- **验证**：行动前后的空召回率对比（同一面板可见），作为离线 eval harness 的在线对应物。
- **护栏**：文档删除前展示近 30 天引用摘要，防止误删仍在被依赖的内容。
- **透出**：检索结果（REST/MCP/检索测试）新增新鲜度元数据字段（文档更新时间、来源抓取时间），纯增量、不改排序。

本版本不覆盖：

- 查询明文默认记录（opt-in，默认关闭，见 D1）；
- 文件树移动/改名的历史日志（D2，本版不做）；
- freshness 参与排序加权、检索结果去重与矛盾检测（LLM judge）；
- 沉睡内容的自动清退（只提示，删除永远是人工动作 + 引用预警）;
- 新增 MCP 工具（现有工具的响应增量字段除外）；
- 跨知识库聚合的健康视图（workspace 级仪表盘留待后续）；
- 图表库引入（环比用文字表达，与全站现状一致）。

## 3. 决策点（2026-10-27 评审已裁决，均采纳草案建议）

- **D1 查询原文 opt-in**（草案建议：做，默认关闭）：只有 hash 的零召回列表几乎没有行动价值——不知道用户问了什么就无法补内容。方案：新增独立 `search_query_log` 表，按知识库显式开启（默认 false），仅 owner/admin 可读，独立保留期（默认 30 天），写入路径与日志输出全程不含明文。SearchRun 本体合同零改动。若评审否决，§4.3/§7 的明文相关面降级为"仅次数与趋势"，健康页交互相应简化（零召回行无「创建 FAQ」入口）。
- **D2 移动/改名日志**（草案建议：本版不做）：file_tree_nodes 原地 PATCH 不留痕，追踪组织漂移需要新的 append-only 日志表挂在现有写路径上。位置移动不影响检索正确性（结果中的文件名取当前树节点），优先级远低于内容变更与删除；留待健康面板真实使用后按需补。
- **D3 遥测表不建跨表级联 FK**（草案建议：不建）：`search_citations.search_run_id`、`document_id` 存 uuid 但不加 FK——引用表是遥测投影而非事实层，search_run 过期清理、文档硬清理都不应级联删除它（删除预警恰恰需要"文档已删但引用历史还在"）；生命周期由自身保留期统一清理。workspace 隔离靠 `(workspace_id, kb_id)` 列与查询侧显式过滤（RLS 就绪形态），迁移内注释说明。

## 4. 核心设计

### 4.1 回路模型

```text
记录（旁路，异步）              洞察（只读聚合）              行动（全部复用既有能力）
┌──────────────────┐   ┌──────────────────────────┐   ┌────────────────────────────┐
│ search_citations │   │ 健康 tab                  │   │ 零召回 → 创建 FAQ（预填）   │
│ search_query_log │ → │ · 空召回率（北极星）       │ → │ 沉睡内容 → 查看 / 软删      │
│ （检索完成处      │   │ · 零召回查询 Top N        │   │ 源变更   → 立即同步/强制重爬│
│   投递，批量落库）│   │ · 沉睡内容 Top N          │   │ 任意行   → 检索测试带查询   │
└──────────────────┘   │ · 内容动态 feed            │   └────────────────────────────┘
                       └──────────────────────────┘              │
                                  ↑ 验证：行动前后空召回率对比 ←──┘
```

- 采集侧零新机制：检索记录复用 SearchRun 流程（v0.9.0），内容变更读既有表，同步结果读 `sync_last_result` 与 jobs。
- 行动侧零新写路径：创建 FAQ / 软删 / 同步 / 重爬 / 检索测试全部是既有端点；本版新增的写入口只有一个——`PUT insights/query-log-settings`（D1 开关）。
- 验证闭环在查询层不在文档层：本地文件"改内容"的常见方式是删了重传，会产生**新 document 身份**，文档级引用历史会断；因此北极星指标必须是查询级的空召回率，而不是文档被引用次数。

### 4.2 `search_citations`（chunk 级引用遥测）

```text
search_citations (
  id                bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  workspace_id      uuid        NOT NULL,
  kb_id             uuid        NOT NULL,
  search_run_id     uuid        NOT NULL,          -- 不加 FK（D3）
  document_id       uuid        NOT NULL,          -- 不加 FK（D3）
  chunk_revision_id uuid        NOT NULL,
  rank              int         NOT NULL,          -- 在本次结果中的序号（1 起）
  retrieval_status  text        NOT NULL,          -- available | degraded（empty 无行可记）
  created_at        timestamptz NOT NULL DEFAULT now()
)
-- 索引：
--   idx_citations_doc_window (workspace_id, kb_id, document_id, created_at DESC)  -- 文档引用计数/最近引用/删除预警
--   idx_citations_run (search_run_id)                                             -- 回放/排查
-- 隔离：查询侧一律显式 workspace_id 过滤；不加跨表级联 FK（D3）
```

- 记录范围：多库检索按各 KB 分别记行（与 v0.6.0 多库语义一致）；`detail=lean/full` 两档同记录（行粒度一致）。
- 只记最终返回给调用方的结果行（RRF 合并与截断之后），不记中间通道候选——遥测回答"什么被用了"，不是排序调试器。

### 4.3 `search_query_log`（opt-in 查询原文，D1）

```text
search_query_log (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  workspace_id     uuid        NOT NULL,
  kb_id            uuid        NOT NULL,
  search_run_id    uuid        NOT NULL,
  query_text       text        NOT NULL,           -- 明文，仅开启时写入
  query_hash       text        NOT NULL,           -- 与 search_runs.query_hash 同源，便于关联
  query_chars      int         NOT NULL,
  retrieval_status text        NOT NULL,
  created_at       timestamptz NOT NULL DEFAULT now()
)
-- 索引：idx_query_log_kb_time (workspace_id, kb_id, created_at DESC)
--       零召回聚合用 (workspace_id, kb_id, retrieval_status, created_at) 或查询侧过滤
```

- 开关载体：`knowledge_bases` 新增列 `query_log_enabled boolean NOT NULL DEFAULT false`；经 `PUT .../insights/query-log-settings` 切换（Session owner/admin）。
- 开启前的历史检索不回填（SearchRun 只有 hash）；开启即从当下开始积累。
- 读取面收敛：明文只出现在 `GET insights/queries` 响应中，且仅当该 KB `query_log_enabled=true`；任何日志输出、错误信息、MCP 响应不得包含 `query_text`。

### 4.4 内容动态读模型（零新表，三源 UNION）

feed = 既有事实的只读 UNION（SQL 层实现，Go 侧归并排序截断）：

| 事件 | 来源表 | 展示文案要点 |
|---|---|---|
| 源同步完成 | jobs（type=source_sync）+ `sync_last_result` / KB 级飞书同步结果 | 「产品文档站 同步：新增 4 · 更新 12 · 删除 1」（仅显示非零项，复用 web-source 卡片文案惯例） |
| 内容新版本 | document_revisions（reason=crawl/upload/edit…） | 「安装指南 上传了新版本（v3）」/「FAQ 编辑了回答（v5）」 |
| 内容删除 | documents.deleted_at 非空且近窗 | 「2024 报销制度 已移出检索」（含删除前近 30 天引用数，见 §7 citation-summary 复用） |
| chunk 人工修订/启停 | chunk revisions | 「安装指南 修订了 1 个分块」 |

- 每条事件携带 `kind`（file/faq/web）与来源标识（kb_source_id 有则附源名），前端按类型跳既有详情。
- D2 裁决下，树移动/改名不产生事件。

### 4.5 北极星指标与口径

- **空召回率** = `retrieval_status='empty'` 的 run 数 ÷ 完成的 run 数（available + empty + degraded；failed 不计入分母）。
- **口径过滤**：聚合默认排除管理台「检索测试」流量（按 SearchRun 既有 `transport` 字段过滤；若当前取值不区分管理台来源，检索测试入口补记 `transport=console`）。动机：管理员调试性查询会污染消费侧信号。面板注明口径（"不含管理台检索测试"）。
- 展示：近 7/14/30 天窗口的比率 + 与上一窗口的差值（pp），文字表达，无图表。

### 4.6 检索结果新鲜度元数据（纯增量）

- 单库/多库 REST 与 MCP `knowledge_search`：每条结果 metadata 增 `document_updated_at`（RFC3339）与 web 文档的 `source_last_fetch_at`（取自 `source_meta`，无则省略字段）。数据在检索取标题的同一次 join 内获得，无额外查询。
- MCP `document_get` / `document_list`：响应增同样字段。
- 排序零改动；`detail=lean` 的 ≤15000 字符合同需重跑断言（新增字段极小，预期无影响）。

## 6. 写入路径与资源保护

- **异步、有界、可丢弃**：检索完成处在 application 层把引用行投递进 `CitationRecorder`（进程内有界 buffered channel），后台 goroutine 按 `flush_interval` / `batch_size` 批量 INSERT；缓冲满时丢弃该批 + 计数器 + 结构化日志（含 workspace_id/kb_id 与丢弃行数，不含任何查询内容）。动机：遥测是旁路，任何拥塞都不得反压检索路径；standalone（无 Redis）模式同样工作，因此不用 asynq 承载单次检索的遥测（高频小任务会制造队列噪音）。
- **生命周期**：flusher goroutine 随 server 启停管理（优雅退出时 flush 残量）；worker 侧重启无恢复语义——丢一批遥测可接受，不需要持久化投递。
- **幂等与一致性**：引用行以 `(search_run_id, chunk_revision_id)` 天然幂等（重放检索是新的 run，不冲突）；批量 INSERT 冲突时整批降级为逐行 `ON CONFLICT DO NOTHING`。
- **保留期清理**：扩展 `search_run_cleanup` 定时任务，按两张遥测表各自的保留期删除过期行；独立于 search_run 的 `expires_at`（D3）。
- **隐私**：`query_log_enabled=false` 的 KB 不写明文（写入入口处判断，非事后过滤）；引用行本身不含查询信息；日志/指标不含 query_text（铁律 9）。

## 7. REST 设计

全部挂 `/api/v1/workspaces/:workspace_slug` 下。

**洞察组（Session owner/admin，与 source-connections 同级权限位；API Key 不可见）**：

- `GET .../knowledge-bases/{kb}/insights/overview?window_days=14`
  ```json
  { "window_days": 14,
    "runs": { "total": 1284, "available": 1142, "empty": 67, "degraded": 75, "failed_excluded": 12 },
    "empty_recall_rate": 0.052,
    "previous_empty_recall_rate": 0.074,
    "sleeping_documents_count": 37,
    "recent_changes_count": 12 }
  ```
- `GET .../insights/queries?window_days=14&status=empty&limit=10`
  按 `query_hash` 聚合的零召回查询组；`query_log_enabled=true` 时每组附 `latest_query_text`（该 hash 最近一次原文）与 `first_seen_at`；false 时仅有 `query_chars`/次数/时间分布。
- `GET .../insights/documents?window_days=30&limit=10`
  沉睡内容：窗口起点前已索引、窗口内零引用、未删除的文档（anti-join citations），附 `kind`、`title`、`indexed_at`、`chunk_count`。**样本下限护栏**：窗口内完成 run 数低于具名下限（默认 10）时返回 `insufficient_sample: true` 且不返回清单——防止零流量知识库把全部内容误报为沉睡；前端显示「检索样本不足」提示而非列表。
- `GET .../insights/activity?limit=20`
  §4.4 的 UNION feed，按时间倒序，含事件类型、目标文档/源标识与文案参数（前端 i18n 组装）。
- `PUT .../knowledge-bases/{kb}/insights/query-log-settings` `{"enabled": bool}`（D1 开关，返回当前状态与保留期）。

**引用摘要（prog 组，与 document 删除同权限位，供删除预警与 MCP agent 使用）**：

- `GET .../knowledge-bases/{kb}/documents/{document_id}/citation-summary?window_days=30`
  ```json
  { "window_days": 30, "citation_count": 23, "last_cited_at": "2026-10-25T09:14:00Z" }
  ```

- 跨 workspace 一律 404（既有惯例）；窗口/limit 超上限（31 天 / 50 条）按 validation error 拒绝。

## 8. MCP

不新增工具。`knowledge_search` / `document_get` / `document_list` 响应按 §4.6 增量新鲜度字段。引用摘要不暴露给 MCP（agent 侧暂无消费场景，避免扩大工具面）。

### 9.1 信息架构

- 工作台 tab 数组新增「健康」（zh：健康 / en：Health），位于「索引」与「设置」之间；路由为单文件 `routes/_authenticated/workspaces/$workspaceSlug/kb/$kbId/health.tsx`（与 `search.tsx` 同构：`validateSearch`（zod：`window` 参数）+ loader 预取 + `staticData.breadcrumb`）。

- 无任何检索数据时显示全站一致空态。

### 9.2 交互明细

- **窗口选择**：页头 Select（近 7 / 14 / 30 天，写入 URL search param），作用于计数卡与零召回面板；沉睡内容固定 30 天口径（文案注明）。
- **零召回行动作**：`创建 FAQ` → 跳 `/content/faq/new?question=<原文>&source=insight`（仅 `query_log_enabled=true` 且 owner/admin）；`检索测试` → 跳 `/search?q=<原文>`（明文不可用时按钮隐藏）。
- **沉睡行动作**：`查看` → 既有内容详情；不提供一键删除（删除必须走内容侧既有删除流 + 引用预警，见下）。
- **删除预警**：既有 `DeleteDialog`（文件树/内容列表共用模式）在打开时并行请求 citation-summary，`citation_count > 0` 时在节点信息块下方插入警示块；请求失败静默降级为现状（预警是增强，不是闸门——不改变删除语义与权限）。
- **强制重爬**：web 源列表卡片与源详情操作区新增 `强制重爬`（owner/admin），点击弹确认（说明忽略变更检测、全量重抓的成本），确认后调既有 `sync {"force":true}`；`立即同步` 保持 force=false 不变。
- **检索测试新鲜度行**：结果卡底部分数行上方新增一行灰字「更新于 {{document_updated_at}} · 来源抓取于 {{source_last_fetch_at}}」（web 文档两项都显示，其它文档只显示前项）。
- **i18n**：全部新文案进 `locales/zh` + `locales/en`（en 用 `satisfies` 对齐），无硬编码中文。

3. `query_log_enabled=false` 时：任何 API 响应、日志、前端界面均不出现查询原文；开启后仅 owner/admin 的 insights 端点返回明文；
4. 零召回 → 创建 FAQ（预填）→ 保存 → 检索该问题可命中新 FAQ → 健康页空召回率环比可见下降（手动验收剧本）；

6. 强制重爬触发既有 force 同步链路（hash 未变也建新 revision），配额与在飞上限不受影响；

## 13. 明确取舍

1. **只做露出不做检测**（本版立足裁决）：web/飞书/本地的变更检测在 v1.3.0 及更早已完备，重复建设检测是最大范围陷阱；本版全部新代码都在"读既有事实 + 旁路记录检索引用"两侧。
2. **北极星定在查询级空召回率**而非文档引用增长：删了重传会换 document 身份，文档级指标在常见维护动作下断裂；查询 hash 是唯一跨内容变更稳定的锚。
3. **遥测表不加跨表级联 FK**（D3）：引用历史必须活过 run 过期与文档清理（删除预警依赖），生命周期独立 + 自身保留期是唯一自洽方案；代价是孤儿行靠清理任务兜底。
4. **异步缓冲可丢弃**而非持久化投递：遥测的价值在趋势不在单条，为单条引用引入 asynq 任务/重试链路的复杂度不成比例；丢弃有计数可观测。
5. **明文 opt-in 另立表**而非放宽 SearchRun 合同：v0.9.0 的隐私承诺是对外验收标准，破合同再补文档的成本高于新表；默认关闭把选择权交给对数据负责的角色。
6. **洞察端点不给 API Key**：健康信号是运营者视角，agent 消费场景（新鲜度字段）已通过检索响应满足；缩小明文的可达面。
7. **环比文字而非图表**：全站无图表库，为两个百分比引入依赖不符合 5.7；趋势足够时图表永不进来。
8. **删除预警是增强不是闸门**：引用数高不代表不能删（可能正是清退目标），只改变知情条件，不新增阻塞状态机。
9. **沉睡内容不提供一键删除**：清退动作必须经过带预警的既有删除流，健康面板保持纯只读 + 跳转，避免面板变成第二个写入口。
10. **移动/改名不进本版**（D2）：不影响检索正确性且无日志载体，待健康面板真实使用证明组织漂移值得追踪后再补 append-only 日志。
