# 琅嬛 v0.2.0 Workspace、文档导入与 Pipeline 骨架设计规格

> 历史说明（2026-07-30）：本文记录 v0.2.0 当时的设计与版本预测，正文中“v0.3.0 接 MinerU、v0.4.0 接多格式解析与分块”的表述不再代表当前路线。实际 v0.3.0 已实现 Markdown、TXT、CSV、XLSX、DOCX 的本地解析、version 1 parse manifest 与结构化分块；PDF/MinerU 和图片资产归档已推迟到 v0.8.0。当前合同以 `2026-07-30-v0.3.0-multi-format-parsing-chunking-design.md` 与 `ROADMAP.md` 为准。

## 1. 背景

v0.1.0 建立了琅嬛的单进程运行入口、基础 REST、MCP 挂载点、asynq worker、数据库迁移、领域模型和端口边界。v0.2.0 在这个基础上进入文档导入主链路，但仍不实现真实解析、资产归档、embedding 或索引写入。

v0.2.0 的核心不是做一个临时导入演示，而是提前落定后续版本共用的 workspace 作用域、导入合同和 `application/pipeline` 骨架。v0.3.0 接 MinerU Cloud、v0.4.0 接多格式解析与分块、v0.5.0 接 embedding 与 pgvector/FTS 时，都应沿用 v0.2.0 的 REST API、document/job 状态机、任务名、raw file 输入和 pipeline 阶段边界。

## 2. 目标

v0.2.0 交付真实文档导入入口和可恢复的异步 pipeline 骨架：

- 引入 `Workspace` 作为顶层资源作用域，知识库必须归属 workspace。
- 预留 workspace API token 模型：token 归属 workspace，未来可以操作该 workspace 下的全部资源。
- 实现 workspace-scoped 知识库 API：
  - `POST /api/v1/workspaces`
  - `GET /api/v1/workspaces/:workspace_id`
  - `POST /api/v1/workspaces/:workspace_id/knowledge-bases`
  - `GET /api/v1/workspaces/:workspace_id/knowledge-bases/:id`
- 实现 `POST /api/v1/workspaces/:workspace_id/knowledge-bases/:id/documents`，支持 `multipart/form-data` 文件上传。
- 保存上传原始文件，计算 `sha256`、文件大小、content type 和 file type。
- 创建 `Document` 与首个 `Job`，返回 `document_id` 和 `job_id`。
- 支持请求参数 `dedupe=true`，在同一知识库内按 `sha256` 复用非失败、非删除态文档。
- 实现 `GET /api/v1/workspaces/:workspace_id/documents/:id`。
- 实现 `GET /api/v1/workspaces/:workspace_id/jobs/:id`。
- 新增 `application/pipeline`，定义 parse、asset、chunk、index 阶段的编排边界。
- 新增 raw document storage port，并提供 local adapter。
- 导入时先在受限临时文件中计算 hash，再决定是否复用已有 document 或写入正式 raw storage。
- 实现 asynq 任务链：
  - `document_parse_start`
  - `document_parse_poll`
  - `document_index`
- 使用 stub parser 产出 deterministic `normalized_markdown`。
- 使用 minimal chunk stage 写入 deterministic chunk，验证任务幂等。
- 失败时记录 document/job 错误信息，worker 重启后可依赖 PostgreSQL 状态继续推进。

## 3. 非目标

v0.2.0 明确不做：

- MinerU Cloud API 调用。
- OSS 或正式对象存储接入。
- Markdown/TXT/CSV/XLSX/DOCX/PDF 的真实解析。
- 图片资产扫描、下载、转存或 Markdown 图片地址替换。
- 真实 chunker 策略，例如 heading-aware split、table-aware split、overlap。
- embedding API 调用。
- pgvector 写入或查询。
- PostgreSQL FTS 写入或查询。
- MCP 业务工具。
- 文档删除接口。
- workspace 成员、角色、细粒度权限或 token scope。
- workspace API token 的签发、轮换和完整鉴权中间件。
- Chat、Agent 或 LLM 答案生成。

## 4. 版本衔接原则

v0.2.0 必须为 v0.3.0 留出稳定衔接点：

- REST 导入 API 在 v0.3.0 不重做，只扩展可选参数和校验。
- workspace 路由和 `workspace_id` 边界在 v0.3.0 不重做，MinerU、资产归档和后续索引都必须在 workspace 内执行。
- workspace API token 的默认授权语义是操作所属 workspace 下的全部资源；后续只扩展 token 签发、校验和细粒度 scope，不改变资源归属模型。
- raw file storage key 是 parser 阶段的稳定输入。v0.3.0 MinerU adapter 从该 key 读取原始 PDF。
- `document_parse_start` 和 `document_parse_poll` 是 MinerU 异步流程的固定任务位置。v0.2.0 即使使用 stub，也必须保留 start/poll 两段。
- `application/pipeline.ParseStage` 在 v0.3.0 替换为 MinerU parser adapter，不改变 worker handler 的主要编排。
- `AssetStage` 在 v0.2.0 可以是 no-op，但接口和阶段位置必须存在，v0.3.0 在这里接入图片资产归档。
- `document_index` 在 v0.2.0 只写 minimal chunk；v0.4.0 替换 chunk stage，v0.5.0 再接 embedding、vector index 和 keyword index。

## 5. 架构增量

v0.2.0 在 v0.1.0 分层基础上增加以下模块：

```text
internal/
  application/
    pipeline/
      document_pipeline.go
      parse_stage.go
      asset_stage.go
      chunk_stage.go
      index_stage.go
    service/
      workspace.go
      knowledge_base.go
      document_ingest.go
      job.go
    dto/
      workspace.go
      knowledge_base.go
      document.go
      job.go

  interfaces/
    http/
      workspace.go
      knowledge_base.go
      document.go
      job.go
    worker/
      document_tasks.go

  ports/
    storage/
      raw_document.go

  adapters/
    storage/
      local/
        raw_document_store.go
    parser/
      stub/
        parser.go
```

依赖方向保持不变：

- HTTP handler 只做协议适配、文件接收和响应转换。
- HTTP handler 必须从路径中解析 `workspace_id`，并传入 application 层做资源边界校验。
- worker handler 只解码 asynq payload，并调用 application service 或 pipeline。
- application service 负责编排用例和事务边界。
- pipeline 阶段依赖 domain 和 ports，不直接依赖 HTTP、MCP、asynq 或具体第三方 SDK。
- local raw document store 是 port adapter，不进入 domain。
- v0.2.0 不再暴露 v0.1.0 非 workspace 知识库接口；默认 workspace 只用于承接既有数据回填。所有知识库、导入、状态查询和未来 token-facing API 必须使用 workspace-scoped 路由。

## 6. REST API

### 6.1 POST /api/v1/workspaces

创建 workspace。

请求：

```json
{
  "name": "默认工作区",
  "metadata": {}
}
```

响应：

```json
{
  "id": "workspace-uuid",
  "name": "默认工作区",
  "metadata": {},
  "created_at": "2026-06-17T00:00:00Z",
  "updated_at": "2026-06-17T00:00:00Z"
}
```

### 6.2 GET /api/v1/workspaces/:workspace_id

读取 workspace。不存在返回 404，非法 UUID 返回 400。

### 6.3 POST /api/v1/workspaces/:workspace_id/knowledge-bases

在 workspace 下创建知识库。请求和响应沿用 v0.1.0 knowledge base 字段，并新增 `workspace_id`。

### 6.4 GET /api/v1/workspaces/:workspace_id/knowledge-bases/:id

读取 workspace 下的知识库。

约束：

- `workspace_id` 和 `id` 必须同时匹配。
- 知识库存在但不属于该 workspace 时返回 404，不泄露跨 workspace 资源存在性。

### 6.5 POST /api/v1/workspaces/:workspace_id/knowledge-bases/:id/documents

上传文档并启动异步处理。

请求：

```http
POST /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents?dedupe=true
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `file` | 是 | 上传文件 |
| `title` | 否 | 文档标题；未传时使用文件名 |
| `source_type` | 否 | 默认 `upload` |
| `metadata` | 否 | JSON object 字符串 |

查询参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `dedupe` | `false` | 为 `true` 时，同一知识库内按 `sha256` 复用非失败、非删除态文档 |

成功创建响应：

```json
{
  "document": {
    "id": "document-uuid",
    "workspace_id": "workspace-uuid",
    "knowledge_base_id": "knowledge-base-uuid",
    "title": "example.pdf",
    "file_type": "pdf",
    "source_type": "upload",
    "status": "pending",
    "sha256": "hex",
    "raw_storage_key": "raw-documents/kb/document/original.pdf",
    "size_bytes": 12345,
    "content_type": "application/pdf",
    "metadata": {},
    "created_at": "2026-06-17T00:00:00Z",
    "updated_at": "2026-06-17T00:00:00Z"
  },
  "job": {
    "id": "job-uuid",
    "document_id": "document-uuid",
    "type": "document_parse_start",
    "status": "queued",
    "attempts": 0,
    "payload": {
      "raw_storage_key": "raw-documents/kb/document/original.pdf",
      "sha256": "hex",
      "file_type": "pdf"
    },
    "created_at": "2026-06-17T00:00:00Z",
    "updated_at": "2026-06-17T00:00:00Z"
  },
  "deduped": false
}
```

`dedupe=true` 命中已有文档时：

```json
{
  "document": {
    "id": "existing-document-uuid",
    "workspace_id": "workspace-uuid",
    "status": "completed",
    "sha256": "hex"
  },
  "job": {
    "id": "active-or-last-job-uuid",
    "status": "succeeded"
  },
  "deduped": true
}
```

注意：为了让 `dedupe=true` 命中时不创建新的 raw file、document 或 job，导入流程必须先把上传流写入受限临时文件并计算 `sha256`，完成 dedupe 判断后再决定是否调用 `RawDocumentStore.Put` 写入正式位置。临时文件必须在请求结束前清理。

错误：

- workspace 或 knowledge base 不存在：404 `not_found`
- knowledge base 不属于 workspace：404 `not_found`
- 非法 UUID：400 `validation_error`
- 未上传文件：400 `validation_error`
- `metadata` 不是 JSON object：400 `validation_error`
- 文件超过配置上限：413 `validation_error`
- raw file 保存失败：500 `internal_error`
- 入队失败：500 `internal_error`

### 6.6 GET /api/v1/workspaces/:workspace_id/documents/:id

查询文档处理状态。

响应：

```json
{
  "id": "document-uuid",
  "workspace_id": "workspace-uuid",
  "knowledge_base_id": "knowledge-base-uuid",
  "title": "example.pdf",
  "file_type": "pdf",
  "source_type": "upload",
  "status": "completed",
  "sha256": "hex",
  "raw_storage_key": "raw-documents/kb/document/original.pdf",
  "size_bytes": 12345,
  "content_type": "application/pdf",
  "normalized_markdown": "# example.pdf\n\n...",
  "metadata": {},
  "error_message": "",
  "created_at": "2026-06-17T00:00:00Z",
  "updated_at": "2026-06-17T00:00:00Z"
}
```

v0.2.0 可以返回 `normalized_markdown`，但应避免在日志中记录其完整内容。后续如果内容过大，可在 v0.3+ 拆成详情参数或单独接口。

约束：

- document 必须通过所属 knowledge base 反查到同一个 workspace。
- document 存在但不属于该 workspace 时返回 404。

### 6.7 GET /api/v1/workspaces/:workspace_id/jobs/:id

查询异步任务状态。

响应：

```json
{
  "id": "job-uuid",

  "document_id": "document-uuid",
  "type": "document_parse_start",
  "status": "succeeded",
  "attempts": 1,
  "external_job_id": "",
  "payload": {
    "raw_storage_key": "raw-documents/kb/document/original.pdf",
    "sha256": "hex",
    "file_type": "pdf"
  },
  "error_message": "",
  "created_at": "2026-06-17T00:00:00Z",
  "updated_at": "2026-06-17T00:00:00Z"
}
```

约束：

- job 必须通过 document -> knowledge base 反查到同一个 workspace。
- job 存在但不属于该 workspace 时返回 404。

## 7. 数据模型增量

v0.1.0 已定义 `knowledge_bases`、`documents` 和 `jobs`。v0.2.0 需要引入 workspace 作用域，并补齐导入链路字段。字段命名以实际 v0.1.0 迁移为准；如果 v0.1.0 已包含同义字段，优先复用，不重复建列。

### 7.1 workspaces

新增表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `name` | text | workspace 名称 |
| `metadata` | jsonb | 扩展信息 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 更新时间 |

v0.2.0 需要提供默认 workspace 迁移策略，用于承接 v0.1.0 已有 knowledge bases。默认 workspace 可以由迁移创建，名称建议为 `default`。

### 7.2 workspace_api_tokens

新增表或预留迁移：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `workspace_id` | uuid | 所属 workspace |
| `name` | text | token 名称 |
| `token_hash` | text | token hash，不保存明文 |
| `token_prefix` | text | 可展示前缀，用于排查 |
| `last_used_at` | timestamptz | 最近使用时间 |
| `revoked_at` | timestamptz | 撤销时间 |
| `created_at` | timestamptz | 创建时间 |

v0.2.0 不要求实现 token 签发和鉴权中间件，但数据模型和 application 鉴权上下文必须按 workspace token 语义设计：一个 workspace token 默认可操作该 workspace 下所有资源，不能跨 workspace。

### 7.3 knowledge_bases

建议新增或确认字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `workspace_id` | uuid | 所属 workspace，必填 |

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_knowledge_bases_workspace_id
ON knowledge_bases (workspace_id);
```

约束：

- 新建 knowledge base 必须指定 workspace。
- v0.1.0 已存在 knowledge base 需要回填到默认 workspace。
- 同一个 knowledge base 只能属于一个 workspace。

### 7.4 documents

建议新增或确认字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `raw_storage_key` | text | 原始上传文件在 raw document store 中的 key |
| `size_bytes` | bigint | 原始文件大小 |
| `content_type` | text | 上传时识别的 MIME type |
| `metadata` | jsonb | 用户传入元数据 |
| `error_message` | text | 最近失败错误 |

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_documents_kb_sha256
ON documents (knowledge_base_id, sha256);

CREATE INDEX IF NOT EXISTS idx_documents_status
ON documents (status);
```

`idx_documents_kb_sha256` 用于 `dedupe=true` 查询，但不应做唯一约束，因为默认允许重复导入。

workspace 归属通过 `documents.knowledge_base_id -> knowledge_bases.workspace_id` 判定。v0.2.0 不要求在 documents 冗余 `workspace_id`，但所有查询必须显式校验 workspace 边界。

### 7.5 jobs

建议确认字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | text | 任务类型 |
| `status` | text | `queued/running/succeeded/failed/cancelled` |
| `attempts` | int | 执行次数 |
| `external_job_id` | text | v0.3.0 MinerU batch/job id 的存放位置 |
| `payload` | jsonb | 阶段输入 |
| `error_message` | text | 失败原因 |

索引：

```sql
CREATE INDEX IF NOT EXISTS idx_jobs_document_id
ON jobs (document_id);

CREATE INDEX IF NOT EXISTS idx_jobs_type_status
ON jobs (type, status);
```

workspace 归属通过 `jobs.document_id -> documents.knowledge_base_id -> knowledge_bases.workspace_id` 判定。

### 7.6 chunks

v0.2.0 复用 v0.1.0 `chunks` 表。`document_index` 只写 minimal deterministic chunk：

- `sequence = 0`
- `content` 来自 stub `normalized_markdown` 的正文
- `context_header` 使用文档标题或空字符串
- `source_anchor` 至少包含：

```json
{
  "type": "stub",
  "document_id": "document-uuid"
}
```

## 8. 配置

v0.2.0 继续只使用 YAML 作为主配置入口。

新增配置：

```yaml
storage:
  raw_document_dir: "./data/raw-documents"

ingest:
  max_file_size_bytes: 52428800
  allowed_file_types:
    - pdf
    - docx
    - markdown
    - md
    - txt
    - csv
    - xlsx
```

约束：

- `raw_document_dir` 只用于 v0.2.0 local adapter。
- 保存路径必须防止 path traversal，不能直接拼接用户上传文件名作为完整路径。
- 文件大小限制在 HTTP 接收和 storage 写入前后都要校验。
- 后续 v0.3.0 可增加 MinerU 和 asset store 配置，但不改变 raw file 配置语义。

## 9. Port 与 Adapter

### 9.1 RawDocumentStore

`RawDocumentStore` 是原始上传文件存储端口，不等同于 v0.3.0 的 `AssetStore`。前者保存用户导入的源文件，后者保存解析产生或引用的图片等资产。

建议接口：

```go
type RawDocumentStore interface {
    Put(ctx context.Context, input RawDocumentInput) (*RawDocumentObject, error)
    Open(ctx context.Context, key string) (io.ReadCloser, error)
    Delete(ctx context.Context, key string) error
}
```

输入：

```go
type RawDocumentInput struct {
    WorkspaceID     uuid.UUID
    KnowledgeBaseID uuid.UUID
    DocumentID      uuid.UUID
    FileName        string
    ContentType     string
    Reader          io.Reader
    SizeBytes       int64
}
```

输出：

```go
type RawDocumentObject struct {
    Key         string
    SizeBytes   int64
    SHA256      string
    ContentType string
}
```

local adapter 规则：

- 以 `workspace_id/knowledge_base_id/document_id/` 组织目录。
- 原始文件名只作为展示或后缀来源，必须清理危险字符。
- 写入时计算 SHA256。
- 使用临时文件 + rename，避免部分写入被读取。
- 如果写入失败，应清理临时文件并返回明确错误。

### 9.2 Stub DocumentParser

v0.2.0 的 stub parser 只用于 pipeline 连通性验证。

输入来自：

- `document_id`
- `raw_storage_key`
- `title`
- `file_type`
- `sha256`

输出：

```go
type ParsedDocument struct {
    NormalizedMarkdown string
    Metadata           map[string]any
}
```

stub `normalized_markdown` 必须 deterministic，便于测试和幂等验证。示例：

```markdown
# example.pdf

Imported by Langhuan stub parser.

- document_id: ...
- sha256: ...
- file_type: pdf
```

v0.3.0 用 MinerU parser adapter 替换或扩展该阶段，不改变 worker 任务名。

## 10. Application Service

### 10.1 WorkspaceService

职责：

- 创建 workspace。
- 读取 workspace。
- 提供默认 workspace 查询能力，服务既有数据回填和内部兜底，不暴露非 workspace HTTP 入口。
- 后续 token 鉴权中间件可以通过该 service 或 repository 解析 token 所属 workspace。

### 10.2 KnowledgeBaseService

职责：

- 在指定 workspace 下创建 knowledge base。
- 读取指定 workspace 下的 knowledge base。
- 只接受显式 workspace 下的知识库创建和读取。
- 保证 knowledge base 查询带 workspace 条件，跨 workspace 返回 `not_found`。

### 10.3 DocumentIngestService

职责：

- 校验 workspace 存在。
- 校验 knowledge base 存在且归属该 workspace。
- 校验上传文件、大小、类型和 metadata。
- 将上传流写入受限临时文件，同时计算 hash、大小和 content type。
- 处理 `dedupe=true`：
  - 查询同一 workspace、同一 knowledge base 内同 `sha256` 文档。
  - 只复用状态不是 `failed/deleting/deleted` 的文档。
  - 命中后返回已有 document 和 active/latest job，不创建新 document。
- 为新 document 分配 UUID。
- 调用 `RawDocumentStore.Put` 从临时文件读取并保存原始文件。
- 创建 document：
  - `status = pending`
  - 保存 `sha256/raw_storage_key/size_bytes/content_type/file_type`
- 创建 `document_parse_start` job：
  - `status = queued`
  - `payload` 包含 raw file key、sha256、file type、content type、size bytes。
- 入队 asynq `document_parse_start`。

workspace 边界：

- service 入参必须包含 `workspace_id`。
- 任何 document/job 查询都必须通过 workspace 过滤或反查校验。
- 跨 workspace 访问返回 `not_found`，不返回 `forbidden`，避免暴露资源存在性。

事务边界：

- document 和 job 创建应在同一数据库事务中。
- 上传临时文件不进入数据库事务，必须有大小上限和请求结束清理。
- raw file 正式写入发生在 document/job 创建前；写入失败时不能留下已提交 document。
- 如果 document/job 创建失败，应尽力删除刚写入的 raw file。
- 如果 DB 创建成功但 asynq 入队失败，应把 job 标记为 `failed` 或返回错误并保留可诊断状态。实现计划需要选定一种策略并测试。

### 10.4 JobService

职责：

- 查询 job。
- worker 开始执行时把 job 标记为 `running` 并增加 attempts。
- worker 成功时标记 `succeeded`。
- worker 失败时保存 `failed/error_message`。
- 为下一阶段创建新的 job 记录，并把新 job id 写入 asynq payload。
- 根据 document 查询 active/latest job，供 dedupe 命中响应使用。

## 11. Pipeline 设计

v0.2.0 建立以下阶段：

```text
DocumentPipeline
  -> ParseStage
  -> AssetStage
  -> ChunkStage
  -> IndexStage
```

### 11.1 ParseStage

职责：

- 从 document 和 raw file key 构建 parse input。
- 调用 parser adapter。
- 保存 `documents.normalized_markdown`。
- 推进 document 状态到 `parsed`。

v0.2.0 使用 stub parser。v0.3.0 在该阶段接 MinerU Cloud。

### 11.2 AssetStage

职责：

- 接收 `ParsedDocument` 或 normalized markdown。
- 归档解析产生或引用的资产。
- 产出可保存的 assets 与 rewritten markdown。

v0.2.0 为 no-op，直接返回原 markdown。v0.3.0 实现 Markdown 图片、HTML img、base64/data URI、zip 相对路径和远程图片归档。

### 11.3 ChunkStage

职责：

- 从 normalized markdown 生成 chunks。
- 写入 `chunks` 表。

v0.2.0 只生成 minimal deterministic chunk。重复执行时，按 document_id 先清理旧 chunks，再写入新 chunks。

v0.4.0 替换为真实 chunker。

### 11.4 IndexStage

职责：

- 接收 chunks 并写入索引。

v0.2.0 不调用 embedding、pgvector 或 FTS。它只作为阶段存在，确认 chunks 已写入后允许 document 进入 `completed`。

v0.5.0 在该阶段接 embedding、vector index 和 keyword index。

## 12. Asynq 任务链

### 12.1 document_parse_start

payload：

```json
{
  "document_id": "uuid",
  "job_id": "uuid"
}
```

行为：

- 读取 document 和当前 `document_parse_start` job。
- 当前 job 标记为 `running`，成功后标记为 `succeeded`。
- 若 document 是 `failed/completed/deleting/deleted`，跳过。
- 若 document 已经 `parsed/indexing`，创建或找到 active `document_index` job 并补发 `document_index`。
- 若 document 已经 `parsing_submitted/parsing`，创建或找到 active `document_parse_poll` job 并补发 `document_parse_poll`。
- 否则把 document 推进到 `parsing_submitted`。
- v0.2.0 不提交外部解析任务，但保留保存 `external_job_id` 的位置。
- 创建新的 `document_parse_poll` job，并入队 `document_parse_poll`。

上述跳过或补发分支命中后，当前任务应直接成功结束，不继续执行后续状态推进。

### 12.2 document_parse_poll

payload：

```json
{
  "document_id": "uuid",
  "job_id": "uuid"
}
```

行为：

- 读取 document 和当前 `document_parse_poll` job。
- 当前 job 标记为 `running`，成功后标记为 `succeeded`。
- 若 document 已经 `parsed`，不重复写 markdown，创建或找到 active `document_index` job 并补发 `document_index`。
- 若 document 已经 `indexing/completed/deleting/deleted`，跳过，不重复写 markdown。
- 若 document 已经 `failed`，跳过并返回当前失败状态。
- 把 document 推进到 `parsing`。
- 调用 `ParseStage`。
- `ParseStage` 成功后 document 进入 `parsed`。
- 创建新的 `document_index` job，并入队 `document_index`。

上述跳过或补发分支命中后，当前任务应直接成功结束，不继续调用 `ParseStage`。

v0.2.0 stub parser 可一次完成，但必须通过 poll 任务完成 parse，以保留 v0.3.0 MinerU 轮询位置。

### 12.3 document_index

payload：

```json
{
  "document_id": "uuid",
  "job_id": "uuid"
}
```

行为：

- 读取 document 和当前 `document_index` job。
- 当前 job 标记为 `running`，成功后标记为 `succeeded`。
- 若 document 是 `failed/deleting/deleted`，跳过。
- 若 document 是 `completed` 且 chunks 存在，可跳过。
- 若 document 是 `completed` 但 chunks 缺失，可补写 chunks。
- 把 document 推进到 `indexing`。
- 调用 `AssetStage` no-op。
- 调用 `ChunkStage` 写 deterministic chunk。
- 调用 `IndexStage` no-op。
- 把 document 推进到 `completed`。

上述跳过分支命中后，当前任务应直接成功结束，不继续写 chunks 或推进状态。

## 13. 状态机

Document 状态：

```text
pending
  -> parsing_submitted
  -> parsing
  -> parsed
  -> indexing
  -> completed
```

失败可从以下状态进入：

```text
pending/parsing_submitted/parsing/parsed/indexing -> failed
```

保留但 v0.2.0 不开放入口：

```text
completed/failed -> deleting -> deleted
```

状态推进原则：

- 状态推进必须单调，不能从较新阶段回退到旧阶段。
- worker 每次执行前先读取 document 当前状态。
- `completed/deleting/deleted` 状态下跳过无效 parse 任务。
- `failed/deleting/deleted` 不参与 `dedupe=true` 复用。
- 所有失败保存到 document 和 job。

Job 状态：

```text
queued -> running -> succeeded
queued -> running -> failed
```

v0.2.0 不需要实现取消任务，但保留 `cancelled` 枚举。

## 14. 幂等策略

### 14.1 导入幂等

- 默认 `dedupe=false`：同一文件重复上传也创建新的 document/job。
- `dedupe=true`：
  - 同一 workspace、同一 knowledge base 内按 `sha256` 查找已有 document。
  - 状态为 `failed/deleting/deleted` 的 document 不复用。
  - 命中处理中或成功文档时，返回已有 document 和 active/latest job。
  - 不创建新正式 raw file、document 或 job。
  - 为计算 hash 产生的临时文件必须清理。

### 14.2 任务幂等

- `document_parse_start` 不重复提交同一解析阶段。
- `document_parse_poll` 不重复覆盖已完成 parse 的 document。
- `document_index` 对 chunks 采用先删后写，保证重复执行结果一致。
- 已 `completed` 且 chunks 存在时，重复 `document_index` 可直接成功返回。
- 每个 pipeline 阶段有自己的 job 记录，asynq payload 中的 `job_id` 指向当前阶段 job。
- worker 重启后，以 PostgreSQL document/job 状态为准继续推进。

### 14.3 错误幂等

- 任务失败应记录当前阶段、错误码和错误信息。
- 同一任务重试时增加 `attempts`。
- 可重试错误由 asynq 重试机制处理，最终失败写入 `failed`。
- 不把完整文档内容写入 job payload 或日志。

## 15. 错误处理

继续使用 v0.1.0 统一错误响应：

```json
{
  "error": {
    "code": "validation_error",
    "message": "file is required"
  }
}
```

新增建议错误码：

- `file_too_large`
- `unsupported_file_type`
- `storage_error`
- `queue_error`
- `pipeline_error`

日志约束：

- 可以记录 document_id、job_id、knowledge_base_id、file_type、size_bytes、sha256。
- 可以记录 workspace_id，但不能记录未来 workspace API token 明文。
- 不记录完整 `normalized_markdown`。
- 不记录上传文件内容。
- 不记录未来配置中的 API key 或对象存储密钥。

## 17. 验收标准

v0.2.0 完成时必须满足：

- 上传文件后立即返回 `document_id` 和 `job_id`。
- workspace 可以创建和读取。
- knowledge base 必须归属 workspace。
- 原始文件被保存到 local raw document store。
- document 记录包含 `sha256/raw_storage_key/size_bytes/content_type/file_type`。
- `GET /api/v1/workspaces/:workspace_id/documents/:id` 可查询状态。
- `GET /api/v1/workspaces/:workspace_id/jobs/:id` 可查询任务状态。
- 跨 workspace 不能读取或操作 knowledge base、document、job。
- worker 可执行 `document_parse_start -> document_parse_poll -> document_index`。
- 每个任务阶段都有独立 job 记录，job 状态可查询。
- document 最终进入 `completed`。
- `documents.normalized_markdown` 有 deterministic stub 内容。
- `chunks` 表有 deterministic minimal chunk。
- 重复执行任务不会重复创建 chunks。
- `dedupe=true` 可以复用非失败、非删除态同 hash 文档。
- `failed/deleting/deleted` 文档不会被 dedupe 复用。
- v0.2.0 没有 MinerU、OSS、embedding、pgvector/FTS 写入或真实多格式解析实现。

## 18. 风险与约束

- pipeline 雏形优先会引入更多接口和文件，必须避免把 v0.3.0-v0.5.0 的真实能力提前实现。
- workspace 是 v0.2.0 新增顶层边界，所有 repository 查询都要避免遗漏 workspace 校验。
- raw document store 和 asset store 语义相近但职责不同，命名必须清楚，避免后续资产归档混入原始文件存储。
- `dedupe=true` 按 hash 复用会返回处理中 document；调用方必须通过状态查询继续跟踪。
- workspace API token 只预留模型和语义，不应在 v0.2.0 里做半成品明文 token 或不完整鉴权。
- DB 创建成功但 asynq 入队失败的策略需要在实现计划中明确，否则会出现孤儿 job。
- local raw document store 只适合开发和 v0.2.0 骨架验证，生产对象存储策略留到后续版本。
- stub parser 产物不能被误认为真实解析结果，响应和文档应明确其 v0.2.0 性质。

## 19. 后续版本衔接

以下内容保留为 v0.2.0 设计时的历史预测，不作为当前版本计划执行；当前路线变更见本文开头的历史说明。

v0.3.0 应直接基于本规格扩展：

- 实现 MinerU Cloud parser adapter。
- MinerU 提交、轮询、结果下载和资产归档都必须携带 workspace 上下文，并校验 document 所属 workspace。
- `document_parse_start` 申请上传地址、上传 raw file、保存 MinerU external job id。
- `document_parse_poll` 轮询 MinerU 结果，下载 Markdown 或 zip。
- `AssetStage` 实现图片归档和 Markdown 地址替换。
- `AssetStore` 接入 OSS 或正式对象存储。
- 保存真实 `normalized_markdown` 和 `document_assets`。

v0.4.0 扩展：

- 替换 minimal chunk 为真实 chunker。
- 接入 Markdown/TXT/CSV/XLSX/DOCX parser adapter。
- 完善 source anchor。

v0.5.0 扩展：

- 在 `IndexStage` 接 embedding adapter。
- 写入 pgvector 和 PostgreSQL FTS。
- 校验知识库 embedding 维度。

v0.6.0 扩展：

- 暴露 REST search、chunk get、document delete。
- 暴露 MCP 业务 tools。
