# 琅嬛 v0.5.0 Web Console 整体使用体验设计

**日期：** 2026-08-01

**状态：** 待审核

**目标版本：** v0.5.0

**范围：** 首次使用引导、知识库工作台、内容浏览与编辑、检索测试、Chunk Revision、Index Generation、异步状态反馈、权限提示、响应式与无障碍

## 1. 结论

v0.5.0 应把 Web Console 从“按接口分散展示资源”升级为“围绕知识库运营闭环组织任务”的工作台。用户不需要先理解 Document Revision、ChunkSet 或 Generation，便能完成：

```text
配置可用模型
  -> 创建知识库
  -> 上传文件或创建 FAQ
  -> 等待真实异步处理状态
  -> 检索验证
  -> 定位来源与 Chunk
  -> 修订或停用 Chunk
  -> 调整配置并构建新 Generation
  -> 检查后激活
```

推荐采用“知识库五区工作台 + 统一内容入口下的分类型视图”方案：

- 知识库内固定为“概览 / 内容 / 检索测试 / 索引 / 设置”五个任务区。
- “内容”统一承载 File、FAQ 和已有 Web Document，但不伪造统一的数据模型或展示控件：只有 File 视图使用真实 File Tree；全部内容、FAQ 和 Web 使用桌面表格/移动端卡片。
- 文档查看不再离开知识库上下文。来源预览、Chunk、修订历史和任务状态在同一工作面内联动。
- FAQ 使用完整页面编辑器，而不是把多个问题和长回答塞进小弹窗。
- Embedding、分块或检索参数变化通过“构建新索引版本”创建 Generation；新 Generation 就绪前继续使用当前 active Generation。
- 所有分数、状态、进度和统计只显示后端真实数据。v0.5.0 不虚构处理阶段、百分比、可靠度或业务统计。

## 2. 背景与现状依据

### 2.1 当前已具备的基础

当前 `main` 已完成：

- Session 认证、Workspace、owner/admin/member 角色与跨 Workspace 隔离。
- Provider、Embedding Model、KnowledgeBase、Document、Job、成员和邀请的真实 REST 接入。
- File/FAQ/Web Document、File Tree、Chunk Revision、Index Generation 和混合检索的后端事实模型与主要接口。
- React 19、TanStack Router/Query、RHF + Zod、Tailwind CSS v4、shadcn/ui、Biome 的前端基线。
- `web_embed` 单二进制交付和 Vite HMR 开发模式。

### 2.2 当前用户闭环断点

现有知识库详情是概览卡片、文档表格、原始 metadata 和高级 ID 的纵向堆叠。用户可以建库、上传，却不能在 Web Console 中完成以下关键任务：

- 运行混合检索并理解命中来源。
- 从检索结果定位到文档、来源锚点和 Chunk。
- 按文档查看当前有效 Chunk，修订或停用错误 Chunk。
- 查看 Generation 历史，构建并激活新的索引配置。
- 使用 File Tree 组织文件。
- 创建和编辑 FAQ。
- 在返回知识库后看见真实准备状态、处理中的内容和最近失败。

现有页面还直接输出 metadata、payload 和 normalized markdown 的原始 `<pre>`，并在 Query 尚未返回时 `return null`。这对调试有用，但不是稳定的管理体验。

### 2.3 对参考截图的取舍

参考截图提供了两个值得保留的模式：

- 文件总量、完成、处理中、失败状态一眼可见。
- FAQ 明确表达“一组问题变体 + 一个回答”。

本设计不直接复制以下模式：

- 不在全局侧边栏按 Files、Text、Q&A 拆散同一知识库的内容。琅嬛的首要上下文是 Workspace -> KnowledgeBase，内容类型是库内事实。
- 不用小弹窗编辑长 FAQ。问题组、Markdown 回答、预览、校验与异步状态需要完整工作面。
- 不使用 `Trained` 一词。琅嬛不训练模型，准确状态是“可检索”“处理中”“失败”或具体 Generation 状态。
- 不把索引大小或存储配额作为 v0.5.0 装饰性指标；当前没有真实配额合同。

## 3. 目标与成功标准

### 3.1 产品目标

1. 新用户无需阅读内部架构文档即可找到下一步。
2. 普通 Workspace 成员可在浏览器完成导入、FAQ 编辑、内容组织、删除和检索验证。
3. owner/admin 可在浏览器完成 Chunk 修订/启停和 Generation 构建/激活。
4. 用户从检索结果最多一次跳转即可看到命中 Chunk 和来源上下文。
5. 异步操作完成后，相关页面自动反映结果，无需手动刷新。
6. 页面在桌面、窄屏和移动端保持同一任务语义，而不是简单压缩桌面表格。

### 3.2 版本验收场景

使用真实单二进制、临时 PostgreSQL + pgvector 与临时 Redis，通过浏览器完成：

```text
初始化首个账号
  -> 配置 Provider 与可用 Embedding Model
  -> 创建 KnowledgeBase
  -> 新建文件夹并上传文件
  -> 创建一条多问一答 FAQ
  -> 等待内容进入 ready
  -> 运行检索测试
  -> 打开一个命中来源和 Chunk
  -> admin 修订并停用/启用一个非 FAQ Chunk
  -> 检索结果在异步更新后反映修订
  -> 修改分块或模型配置并构建候选 Generation
  -> 检查差异并激活候选 Generation
```

### 3.3 非目标

- 不实现 Workspace API Token、MCP 业务工具或 CLI。
- 不实现 PDF/MinerU、crawler、网页抓取配置或新文档类型。
- 不实现 Rerank、LLM 回答生成、Chat、Agent 或检索质量自动评分。
- 不实现失败任务原地重试、dead-letter 管理、分阶段耗时或完整运维面板；这些属于 v0.8.0。
- 不新增持久化的“引导已完成”标记、行为埋点或虚构的完成率。
- 不引入富文本持久化格式。FAQ 回答继续是 Markdown 字符串。
- 不重写通用 Design System，不替换现有技术栈。
- 不承诺 v1.0.0 前内部测试数据的跨版本迁移兼容。

## 4. 产品原则

### 4.1 围绕任务，而不是围绕表或接口

Document、Revision、ChunkSet、ChunkRevision 和 Generation 是必须保持精确的后端事实；导航和首屏不要求用户先理解这些术语。高级术语只在需要做索引和修订决策时出现，并配一行直接解释。

### 4.2 统一入口，使用分类型视图

File、FAQ 和 Web 都从“内容”进入，但不能为了视觉统一改变事实：

- 只有 File 进入并使用 File Tree；File Tree 组件不接收 FAQ/Web Document，也不创建代表 FAQ/Web 的虚拟节点。
- 全部内容、FAQ 和 Web 使用传统列表：桌面为表格，移动端为卡片。
- FAQ 是版本化的问题集合与回答，不能通过通用 Chunk 编辑器修改。
- Web 仅展示已有数据合同；没有 crawler 时不展示“添加网站”按钮。

### 4.3 不伪造进度

当前后端没有 upload/parse/chunk/embed/publish 的持久化阶段与百分比。v0.5.0 显示真实的 Document/Job/Generation 状态、更新时间、尝试次数和错误，不把预计阶段包装成事实。

### 4.4 生效配置由 Generation 证明

影响索引的设置不能直接宣称已经生效：

- 当前查询继续使用 active Generation。
- 修改模型、分块或检索配置会创建 building Generation。
- ready Generation 经用户检查后显式激活。
- stale/failed Generation 不可激活。

### 4.5 URL 是工作状态

知识库当前区域、内容类型、选中文档和编辑页面必须使用独立路由；选中 Chunk、筛选条件和检索参数使用 typed search params。临时表单草稿可以保留在组件状态，其余决定页面内容的状态不得只存在于 `useState`、Dialog 状态或 TanStack Query 内存缓存。

路由父级使用 `<Outlet />` 承载子页面。每个可复制链接的叶子路由必须能在一次全新浏览器会话中独立执行 loader/query、完成权限检查并渲染内容；不得要求用户先从上一级页面点击进入。F5 刷新、地址栏直达、前进后退和复制链接后都必须恢复同一业务上下文。

### 4.6 稳定 ID 用于寻址，可读名称用于展示

- UUID、config hash 和内部 lineage ID 可以存在于 API、路由、Query key、日志和诊断载荷中，但普通页面不得直接渲染这些值。
- Workspace 显示名称，User 显示 `nickname`（必要时辅以 email），KnowledgeBase 显示名称，Document 显示 File Tree node name 或 title，Job 显示可读动作与目标名称，Generation 显示创建时间、模型和状态组成的标签。
- 资源名称缺失时显示“未命名知识库”“未命名文档”等明确占位，不得退化为 UUID。
- 普通用户确需向支持人员提供内部标识时，页面只提供“复制诊断信息”动作；ID 可进入剪贴板中的结构化诊断载荷，但不在页面展开或裸露显示。
- metadata 只按 typed、可读字段展示。不得用完整 JSON dump 重新把内部 ID、hash 或无意义字段暴露给普通用户。

## 5. 用户与权限

沿用现有后端权限，不在前端重新定义授权。

| 能力 | member | admin | owner |
|---|---:|---:|---:|
| 查看概览、内容、任务、Chunk、Generation | 是 | 是 | 是 |
| 上传文件、创建/编辑 FAQ | 是 | 是 | 是 |
| 新建/重命名/移动 File Tree 节点 | 是 | 是 | 是 |
| 删除 Document | 是 | 是 | 是 |
| 运行检索测试 | 是 | 是 | 是 |
| 修订、启用或停用非 FAQ Chunk | 否 | 是 | 是 |
| 创建、激活 Generation | 否 | 是 | 是 |
| 修改知识库名称和描述 | 否 | 是 | 是 |

规则：

- 不可用动作优先隐藏；在相关只读区保留一句说明，例如“索引配置由 Workspace 管理员维护”。
- 深链接进入无权限写操作时展示 403，不伪装成 404；跨 Workspace 资源仍按后端合同返回 404。
- 任何显示/隐藏只是体验，服务端继续做最终授权。
- platform_admin 不自动获得某个 Workspace 的内容写权限；仍以该 Workspace 的 AuthContext 为准。

## 6. 全局信息架构

### 6.1 一级导航

```text
AppSidebar
├─ WorkspaceSwitcher
│  ├─ 琅嬛 Logo
│  ├─ 当前 Workspace 名称
│  ├─ 角色：admin | owner | member
│  └─ Workspace 切换菜单；platform_admin 额外可见“创建工作区”
├─ Workspace
│  ├─ 概览
│  ├─ 知识库
│  ├─ 模型
│  ├─ 成员
│  └─ 邀请                 admin/owner 可见
├─ 平台管理                platform_admin 可见
│  └─ 平台模型
└─ NavUser
   ├─ nickname + email
   └─ 外观设置 / 退出登录
```

v0.5.0 必须直接复用现有 `AuthenticatedLayout`、`AppSidebar`、`AppHeader`、`SidebarInset` 和 `SidebarProvider`，不得为知识库工作台另造全局页面壳。桌面结构固定为左侧 `AppSidebar`，右侧 `SidebarInset` 内依次为 sticky `AppHeader` 与页面 `<Outlet />`：

```text
AuthenticatedLayout
├─ AppSidebar                               collapsible="icon", variant="sidebar"
│  ├─ SidebarHeader  -> WorkspaceSwitcher
│  ├─ SidebarContent -> Workspace / 平台管理导航组
│  └─ SidebarFooter  -> NavUser
└─ SidebarInset
   ├─ AppHeader
   │  └─ SidebarTrigger / 面包屑 / 弹性空白 / 搜索 / 主题 / ProfileDropdown
   └─ main#content
      └─ <Outlet />
```

`AppHeader` 不再重复 Logo、Workspace 切换器、角色、nickname 或 email；它只显示现有折叠按钮、路由面包屑、桌面搜索入口、主题按钮和头像菜单。头像菜单与 `NavUser` 复用同一用户操作，但顶部只显示头像，不额外占用名称空间。外观设置存在于两个用户菜单中，不是独立的“个人”侧栏分组。

知识库不是全局侧边栏下无限展开的树。用户进入一个知识库后，仍由全局“知识库”项保持选中，页面内二级导航承载具体工作区，避免大量知识库挤占全局导航。

后文 ASCII 原型统一使用最常见的“当前 Workspace 的普通 admin”视角，并严格按现有组件顺序完整画出 `SidebarHeader / WorkspaceSwitcher` -> `SidebarContent / Workspace` 导航组 -> `SidebarFooter / NavUser`。图中不画仅 platform_admin 可见的“平台管理 / 平台模型”条件分组，避免把两种权限状态拼成一个并非常态的侧栏；platform_admin 登录后只是在 `Workspace` 组下方追加该分组，不改变页面骨架。owner 与图中结构相同；member 不显示“邀请”。左栏底部的 `林墨 / lin@example.com` 是 `NavUser`，不是导航分组；原型中的 `[林墨]` 表示 `AppHeader` 与 `NavUser` 按当前实现取 nickname 前两个字符生成的头像。左右区域间的竖线同时表示现有 `SidebarRail`。

### 6.2 知识库内二级导航与路由

每个视图采用独立可深链路由：

| 区域 | 路由 |
|---|---|
| 概览 | `/workspaces/:workspaceSlug/kb/:kbId` |
| 全部内容 | `/workspaces/:workspaceSlug/kb/:kbId/content/all` |
| File Tree | `/workspaces/:workspaceSlug/kb/:kbId/content/files` |
| File 详情 | `/workspaces/:workspaceSlug/kb/:kbId/content/files/:documentId` |
| FAQ 列表 | `/workspaces/:workspaceSlug/kb/:kbId/content/faq` |
| FAQ 新建 | `/workspaces/:workspaceSlug/kb/:kbId/content/faq/new` |
| FAQ 详情 | `/workspaces/:workspaceSlug/kb/:kbId/content/faq/:documentId` |
| FAQ 编辑 | `/workspaces/:workspaceSlug/kb/:kbId/content/faq/:documentId/edit` |
| Web 列表 | `/workspaces/:workspaceSlug/kb/:kbId/content/web` |
| Web 详情 | `/workspaces/:workspaceSlug/kb/:kbId/content/web/:documentId` |
| 检索测试 | `/workspaces/:workspaceSlug/kb/:kbId/search` |
| 索引 | `/workspaces/:workspaceSlug/kb/:kbId/indexes` |
| 设置 | `/workspaces/:workspaceSlug/kb/:kbId/settings` |

`/content` 使用 route-level redirect（`replace`）进入 `/content/all`，不渲染一套额外页面。内容类型 Tabs/移动端 Select 使用 `<Link>` 导航到 `all/files/faq/web`，不以本地 Tab state 切换页面。

现有 `/workspaces/:workspaceSlug/documents/:documentId` 页面改为兼容入口：读取 Document 后 `replace` 到新的知识库内 canonical route。v1.0.0 前不承诺该旧 Web 路由长期保留。

二级导航在桌面显示为标题下方 Tabs，在移动端显示为可访问的 Select；两者操作相同路由。

### 6.3 Outlet 分层与刷新恢复

路由层级固定为：

```text
AuthenticatedLayout                         # AppSidebar + AppHeader + <Outlet />
└─ WorkspaceRoute                           # Workspace loader + <Outlet />
   └─ KnowledgeBaseRoute                    # KB loader + Workbench header + <Outlet />
      ├─ OverviewRoute
      ├─ ContentRoute                       # 类型导航 + <Outlet />
      │  ├─ AllContentRoute
      │  ├─ FilesRoute                      # File Tree + <Outlet />
      │  │  ├─ FileIndexRoute
      │  │  └─ FileDetailRoute
      │  ├─ FAQListRoute
      │  ├─ FAQCreateRoute
      │  ├─ FAQDetailRoute
      │  ├─ FAQEditRoute
      │  ├─ WebListRoute
      │  └─ WebDetailRoute
      ├─ SearchRoute
      ├─ IndexesRoute
      └─ SettingsRoute
```

约束：

- `KnowledgeBaseRoute` 只负责 KB loader、404 映射、公共页头、权限上下文和 `<Outlet />`，不同时实现某个具体 Tab。
- `ContentRoute` 只负责类型导航与 `<Outlet />`；`FilesRoute` 才加载 File Tree，并以 `<Outlet />` 承载空选择或 File 详情。
- 每个叶子路由用 `loader`/`beforeLoad` 调用 `queryClient.ensureQueryData` 获取自身首屏必需数据。loader 不依赖用户之前访问形成的 Query Cache；缓存命中只是优化。
- URL search params 使用 Zod/typed validator。检索查询、筛选、排序、选中 Chunk 均可由 URL 重建；无效参数回退到明确默认值或路由错误，不导致空白页面。
- route pending/error/notFound component 在 F5 和客户端导航中保持一致，不使用 `if (!data) return null`。
- `routeTree.gen.ts` 由 TanStack Router 生成，禁止手改。
- Vite dev server 与 `web_embed` SPA fallback 必须对上述所有嵌套路由返回 `index.html`，同时继续排除 `/api/v1/*`、`/mcp` 和保留协议路径。

### 6.4 面包屑

```text
Workspace / 知识库 / 客服知识 / 内容 / 退款政策.md
```

面包屑只展示真实资源层级。File Tree 路径只在 File 视图内展示，不把每层虚拟文件夹都塞进全局面包屑。

### 6.5 命令菜单

命令菜单主动加载当前 Workspace 的知识库列表，不依赖“恰好已在 Query Cache 中”。除导航外增加权限感知的快捷动作：

- 创建知识库。
- 上传文件到当前知识库。
- 创建 FAQ。
- 打开当前知识库检索测试。

命令菜单不是业务数据搜索器；v0.5.0 不在其中搜索全文或 Chunk。

## 7. Workspace 准备状态

Workspace 概览由装饰性资源卡改为“下一步 + 真实状态 + 常用入口”。准备状态完全由后端资源事实派生，不保存 tutorial completion。

### 7.1 状态步骤

| 步骤 | 完成条件 | 未完成动作 |
|---|---|---|
| 配置模型连接 | 存在当前 Workspace 可见且 active 的 Provider | 去模型页配置连接 |
| 创建 Embedding Model | 存在可选择、维度受支持的 active Embedding Model | 创建模型 |
| 创建知识库 | 至少存在一个活动知识库 | 创建知识库 |
| 添加内容 | 至少存在一个非 deleted Document | 打开最近知识库的内容区 |
| 等待内容可检索 | 至少一个 ready Document；若仅有 processing 则等待；有 failed 则优先处理失败 | 查看处理中/失败内容 |
| 验证检索 | active Generation 有可检索内容 | 打开检索测试 |

“验证检索”表示系统已具备验证条件，不声称用户曾经执行过搜索。v0.5.0 不为此新增行为审计表。

### 7.2 ASCII 原型：Workspace 概览

```text

│   角色：admin         │                                                                                      │
├──────────────────────┼──────────────────────────────────────────────────────────────────────────────────────┤
│ Workspace            │ 下一步：为「产品文档」运行一次检索测试                            [开始检索]     │
│ ● 概览               ├──────────────────────────────────────────────────────────────────────────────────────┤
│   知识库             │ 准备状态                                                                             │
│   模型               │ ✓ 模型连接       OpenAI Compatible                                                   │
```

## 10. 内容区

### 10.1 内容导航与视图模型

内容区顶部使用类型 Tabs/移动端 Select 切换视图：

```text
全部内容    -> Document 表格 / 移动端卡片
文件        -> 真实 File Tree + File 预览/Chunk
FAQ         -> FAQ 表格 / 移动端卡片
Web         -> Web 表格 / 移动端卡片
```

- “全部内容”合并展示 Document，但显示明确类型图标和类型文案；它不展示 File Tree。
- “文件”视图才请求并挂载 File Tree。树节点只来自 `file_tree_nodes`，只表示 root/folder/file；不得把 FAQ、Web、状态筛选或快捷入口塞进树节点数组。
- File Tree 的组件职责止于 File 的层级列表、选择和组织。文件预览与 Chunk Inspector 是选中 File 后打开的相邻面板，不属于树节点渲染职责。
- “FAQ”和“Web”是 Document 列表筛选视图，不是 UI 虚拟目录或虚拟树节点。
- Web Tab 只有存在 Web Document 时才显示；没有 crawler 时不提供创建动作。
- File 的当前展示名和路径以 File Tree node 为准；`documents.title` 不覆盖树节点名称。FAQ/Web 使用 Document title。
- deleting/deleted 只通过列表筛选查看，不作为 File Tree 目录。

### 10.2 列表与筛选

工具栏：

- 搜索标题。
- 类型：全部/File/FAQ/Web。
- 状态：全部/可检索/处理中/失败。
- 排序：最近更新/名称。
- 添加内容菜单：上传文件、创建 FAQ；不显示未实现的 URL 抓取。

v0.5.0 继续复用现有 KnowledgeBase Document 列表和完整 File Tree 响应，在前端对标题、类型和状态做筛选；本版本不为尚未出现的规模问题提前更改 Document 列表响应形状。Job 和 Chunk 因数据量、上下文语义不同，使用后文定义的游标分页接口。

“全部内容”桌面表格列为名称、类型、状态、更新时间、操作；FAQ 表格增加问题变体数量，Web 表格增加来源 URL。移动端统一改为对应类型卡片，不能依赖横向滚动才能看到状态和主操作。

### 10.3 File Tree 操作

- 新建文件夹：在当前选中目录创建。
- 上传文件：默认上传到当前选中目录，并允许更改目标目录。
- 重命名：文件夹和文件节点均支持，使用内联表单或小 Dialog。
- 移动：使用目标目录选择器，不把完整树塞进下拉菜单。
- 删除文件夹：非空时直接解释“请先移动或删除其中内容”，映射 `file_tree_not_empty`。
- 删除文件：确认后删除对应 Document；文案明确“会从检索中移除，后台完成软删除”。
- 拖拽移动不是 v0.5.0 验收要求。按钮/菜单移动先保证键盘和触屏可用。

### 10.4 分类型视图的响应式行为

File 视图：

- `>= 1280px`：File Tree + File 预览 + Chunk Inspector 三栏。
- `768–1279px`：File Tree + File 预览两栏；Chunk 在 Sheet 中打开。
- `< 768px`：File Tree 与文件详情单栏逐级进入；顶部返回当前目录，操作放入底部或右上菜单。

全部内容、FAQ 和 Web 视图：

- `>= 768px`：传统数据表格。
- `< 768px`：卡片列表，保留名称、类型特有摘要、状态、更新时间和主操作。
- 这些视图不挂载 File Tree，也不为保持桌面三栏布局留空树栏。

面板宽度不持久化到服务端；桌面可用本地 UI 状态记忆。

### 10.7 文档预览

File/Web Document：

- 默认渲染 sanitized Markdown 预览。
- 可切换“原始 Markdown”，使用等宽文本，但不把它作为默认体验。
- 搜索 deep link 带精确行号或 offset 时，切换到能可靠定位的原始 Markdown 并高亮范围；无法精确映射到渲染节点时不得伪造预览高亮。
- 表格类来源显示 source anchor 能表达的 sheet、行、列。
- 文件信息结构化显示类型、MIME、大小、Revision、原始文件名、更新时间。
- metadata 只显示已知、安全且对用户可读的 typed 字段；页面不提供完整 JSON dump。

FAQ Document：

- 默认显示问题变体和 Markdown 回答。
- member 及以上显示“编辑 FAQ”。
- FAQ 的唯一 Chunk 只读；引导用户通过 FAQ 编辑器创建新 FAQ Revision。

### 10.8 Document Chunk 列表

列表必须展示当前 active Generation 配置对应的有效 ChunkSet，而不是任意历史 Chunk：

- 每项展示 sequence、context header、正文摘要、enabled、是否人工修订、状态与 source anchor。
- 默认同时显示启用和停用 Chunk；可筛选“仅启用”。
- FAQ Chunk 标记“由 FAQ 内容生成”，没有通用编辑/启停入口。
- deep link 使用 `?chunk=:chunkId&anchor=1`，打开后聚焦并滚动到对应 Chunk。

## 11. FAQ 创建与编辑

### 11.1 表单合同

- 标题：必填。
- 问题：至少一个；支持添加、删除和键盘排序；trim 后不能为空；前端按后端规范提示重复问题。
- 回答：必填 Markdown 字符串；编辑和预览两种视图，桌面可并排。
- 编辑必须携带 `base_revision_id`，冲突时不覆盖新版本。
- 标题在 v0.5.0 仅创建时设置；若后端补充通用标题修改合同，统一从设置/更多菜单修改，不借 FAQ Revision 暗改 Document 标题。

### 11.2 保存行为

- 创建返回 Document、Revision 和 Job 后，进入该 FAQ 详情并显示 processing。
- 更新返回 accepted 后保留用户当前页面，显示“新版本正在建立索引”。
- 成功后刷新 FAQ、Document、KB summary、Document chunks、Generation summary 和相关检索 Query。
- `revision_conflict`：保留本地输入，提示“FAQ 已被他人更新”，允许打开最新版本并手动合并；不提供盲目覆盖。

## 12. 检索测试

### 12.1 交互目标

检索测试是证据调试器，不是聊天框：

- 输入一个查询并显式提交；不做输入即搜索。
- 默认使用 active Generation 的 retrieval config。
- “高级参数”允许本次覆盖 vector/keyword/final top K，但不修改知识库配置。
- 结果按融合排名展示，不生成摘要或答案。
- 记住当前 URL 中的 query 和参数，刷新可重放；不把查询历史持久化到后端。

### 12.2 结果解释

每个结果显示：

- 排名、Document 名称与类型。
- evidence `content`，完整内容可展开。
- RRF `score`、`vector_score`、`keyword_score` 原始数值。
- source anchor 的人类可读摘要。
- metadata 中已知、安全且可读的结构信息；不显示完整 JSON 或内部 ID。
- “查看来源”和“打开 Chunk”。

分数旁固定说明：“分数仅用于本次结果排序，不是相关度百分比或答案可信度。”不得乘以 100 显示为百分比。

### 12.3 来源锚点格式

| 来源 | 摘要示例 |
|---|---|
| Markdown/TXT | `第 12–18 行`，无行号时回退为 byte offset |
| CSV/XLSX | `Sheet1 · 第 3–8 行 · A–D 列` |
| DOCX | `第 4–6 段` 或 `表格 2` |
| FAQ | `FAQ · 问题组命中` |
| Web | 已有 anchor；没有 crawler 时不推导 DOM 路径 |

### 12.4 空、失败与不可用

- KB 没有可检索内容：展示“先添加内容”，不发搜索请求。
- active Generation 缺失或模型不可用：展示阻断原因和有权限的修复入口。
- 0 结果：保留查询和参数，建议换关键词或提高 top K；不建议“重新训练”。
- Provider 超时/限流/拒绝：使用稳定错误码映射成可行动文案，不暴露 credential 或第三方完整响应。

## 13. Chunk 查看、修订与启停

### 13.1 查看

- 原始 `source_content`，只读。
- 当前 active revision 的 context header、content、enabled、edit source、状态和时间。

### 13.2 编辑

## 14. 索引区

### 14.1 用户心智

页面主标题使用“索引版本”，副文案说明“系统内部称 Generation”。业务文案不用“训练”。

### 14.2 列表

每个 Generation 展示：

- `active` 标识由 KnowledgeBase 指针计算，不新增 `active` status。
- status：building/ready/stale/failed/retired。
- 模型、维度、chunker version、分块与检索配置。
- source/indexed content version。
- document/chunk/indexed/failed/manual edit/disabled chunk 计数。
- 创建、ready、激活、retired 时间。
- 失败分类与安全错误摘要。

列表默认按创建时间倒序。building 状态存在时仅轮询索引列表和 KB summary；页面隐藏或进入终态后停止。

### 14.3 构建新索引版本

admin/owner 使用三步表单：

1. 选择 Embedding Model。
2. 设置 chunk size/overlap。
3. 设置 FTS config、vector/keyword/final top K、RRF K，并确认配置差异。

初始值来自 active Generation，不来自可能已漂移的 KnowledgeBase 展示字段。提交 `POST index-generations` 后关闭表单，候选版本出现在列表顶部。

### 14.4 激活

- 只有 ready 且非 stale 的候选可激活。
- 对话框展示 active 与 candidate 的模型、分块、检索参数及计数差异。
- 若 `manual_edit_disposition=pending`，必须明确展示将归档的人工修订数量；用户勾选确认后才发送 `archive_manual_edits=true`。
- `generation_stale`：标记候选过期并提供“按当前内容重新构建”。
- `generation_not_ready`：保持页面状态，解释需等待构建完成。
- `generation_build_in_progress`：聚焦已有 building Generation，不重复创建。

## 15. 设置区

设置拆为两个清晰区域：

### 15.1 基本信息

- 名称、描述。
- admin/owner 可编辑；member 只读并看到权限说明。
- 使用新的 typed `PATCH knowledge-bases/:id`，不允许任意 metadata patch。

### 15.2 检索配置

- 只读展示当前 active Generation 的模型、分块和检索配置。
- admin/owner 的动作是“构建新索引版本”，跳转索引区并预填当前配置。
- 现有“更换 Embedding 模型”对话框从工作台移除。它只修改引用却不触发重建，容易让用户误以为检索已经切换模型。

设置页不展示 KnowledgeBase ID、Workspace ID、User ID、config hash 或完整 metadata。确需排障时提供单一“复制诊断信息”动作，把必要 ID、hash、版本和时间写入剪贴板中的结构化文本；页面本身仍只显示资源名称与可读配置。

## 16. 异步状态与反馈

### 16.1 统一状态展示

| 对象 | 真实状态 | UI 文案 |
|---|---|---|
| Document | pending | 等待处理 |
| Document | processing | 处理中 |
| Document | ready | 可检索 |
| Document | failed | 处理失败 |
| Document | deleting | 删除中 |
| Document | deleted | 已删除 |
| Job | pending/queued | 等待执行 |
| Job | running | 执行中 |
| Job | completed/succeeded | 已完成 |
| Job | failed | 失败 |
| Job | cancelled | 已取消 |
| Generation | building | 构建中 |
| Generation | ready | 待激活或可用 |
| Generation | stale | 已过期 |
| Generation | failed | 构建失败 |
| Generation | retired | 已退役 |

v0.5.0 的 Job API response schema 明确接受当前领域中已有的七个值：`pending/queued/running/completed/succeeded/failed/cancelled`。UI 将 `pending/queued` 统一显示为“等待执行”，将 `completed/succeeded` 统一显示为“已完成”；轮询终态包括 `completed/succeeded/failed/cancelled`。本版本不额外迁移数据库中的历史同义值，v1.0.0 冻结对外合同时再决定是否规范成单一枚举。

### 16.2 轮询规则

- 仅在对象处于非终态、页面可见且 Query 有观察者时轮询。
- 初始 2 秒；状态连续三次未变后 5 秒。
- `visibilitychange` 回到前台时立即 invalidate 一次。
- 成功后 invalidate 精确关联 Query，不做全局 cache 清空。
- 失败进入终态后停止轮询并展示恢复动作。

### 16.3 用户反馈

- mutation 提交成功：立即显示对象的真实 pending/building 状态，不用成功 toast 代替页面状态。
- 后台完成：页面内状态更新；只对用户仍停留在相关页面的关键动作显示一次简短 toast。
- 失败：展示错误摘要、受影响对象和下一步。v0.5.0 没有后端 retry 合同时不显示假的“重试”按钮。
- Document 失败可提供“查看任务”“重新导入文件”“删除内容”。
- 原始 payload 默认不展示；高级诊断只显示允许公开的 typed 字段。

## 17. Loading、空状态、错误与危险操作

### 17.1 Loading

- 每个路由提供与最终布局同构的 skeleton，不允许 `if (!data) return null` 白屏。
- 首次加载用 skeleton；后台刷新保留旧数据并显示局部更新状态，避免整页闪烁。
- 树节点展开时使用节点级 loading，不锁住整个内容区。

### 17.2 空状态

空状态必须说明“为什么为空 + 下一步”，并遵循权限：

- 无知识库：创建第一个知识库。
- 无内容：上传文件或创建 FAQ。
- 空文件夹：上传到此目录或新建子目录。
- 无检索结果：调整查询或本次 top K。
- 无索引历史：理论上 KB 有初始 Generation；若缺失则作为异常而非普通空状态。

### 17.3 错误映射

| 错误码 | 页面行为 |
|---|---|
| `revision_conflict` | 保留草稿并进入人工对比 |
| `generation_build_in_progress` | 聚焦已有构建任务 |
| `generation_stale` | 标记过期并建议重建 |
| `generation_not_ready` | 阻止激活并继续观察状态 |
| `manual_edit_confirmation_required` | 展示人工修订归档确认 |
| `faq_chunk_immutable` | 引导到 FAQ 编辑器 |
| `file_tree_name_conflict` | 在名称字段内联提示 |
| `file_tree_cycle` | 恢复移动前状态并解释不能移入自身后代 |
| `file_tree_not_empty` | 提示先处理子节点 |
| 401 | 导向登录并保留安全 return URL |
| 403 | 显示无权限页，不伪装 404 |
| 404 | 资源不存在或跨 Workspace 隐藏 |

### 17.4 危险操作

以下操作必须二次确认：删除 Document、删除非空风险明确的树节点、激活 Generation 并归档人工修订。

确认文案说出后果与恢复边界，不使用泛化的“确定吗”：

```text
删除「installation.md」？
它会立即从当前检索结果中移除，并进入后台软删除流程。
```

## 18. 后端查询与 API 合同

v0.5.0 复用现有写模型和 Repository 分层。新增能力是 application query/service 与薄 Repository，不允许 handler 直接拼 GORM 查询，也不为 UI 建第二套事实表。

API 继续用 UUID 做稳定寻址，但为页面服务的 summary/list DTO 必须同时提供权威可读名称。前端不得通过截断 UUID、显示 hash 或自行拼接内部类型名来替代名称。

### 18.1 复用的现有接口

| 能力 | 接口 |
|---|---|
| Document 列表/详情/删除 | `GET knowledge-bases/:id/documents`、`GET/DELETE documents/:document_id` |
| File 上传 | `POST knowledge-bases/:id/documents`，补齐 `parent_node_id/node_name` 前端接入 |
| FAQ | `POST documents/faq`、`GET/PUT documents/:document_id/faq` |
| File Tree | `GET file-tree`、`POST folders`、`PATCH/DELETE nodes/:node_id`；仅由 File 视图使用 |
| Chunk 详情/历史/修订 | `GET chunks/:chunk_id`、`GET/POST chunks/:chunk_id/revisions` |
| Generation | `GET/POST index-generations`、`POST :generation_id/activate` |
| 检索 | `POST search` |
| Job 详情 | `GET jobs/:id` |

### 18.2 新增 Workspace 准备状态查询

```http
GET /api/v1/workspaces/:workspace_slug/readiness
```

响应为 typed DTO：

```json
{
  "has_active_provider": true,
  "has_selectable_embedding_model": true,
  "knowledge_base_count": 2,
  "document_counts": {
    "total": 20,
    "ready": 18,
    "processing": 1,
    "failed": 1
  },
  "searchable_knowledge_base_count": 2,
  "recommended_action": "resolve_failed_document",
  "recommended_knowledge_base_id": "uuid-or-null",
  "recommended_knowledge_base_name": "产品文档",
  "recommended_document_id": "uuid-or-null",
  "recommended_document_name": "faq-import.csv"
}
```

`recommended_action` 固定枚举：

```text
configure_provider
create_embedding_model
create_knowledge_base
add_content
wait_for_processing
resolve_failed_document
test_retrieval

```

application service 决定优先级；前端只把 enum 映射为文案和路由。接口不得返回前端 URL。

### 18.3 新增 KnowledgeBase summary 查询

```http
GET /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/summary
```

响应包含：

- Document counts：total、file、faq、web、ready、processing、failed。
- 当前 active Generation 的精简 typed summary。
- active/candidate Generation summary 提供 `display_label`，格式由 application DTO 基于创建时间、模型显示名和状态生成，不让前端显示 Generation UUID。
- `sync_state`：`synced/updating/failed/candidate_ready`。
- 最近五条 Job summary，包含可读 `action_label` 与 `target_display_name`；不包含 payload、external provider 完整响应或 credential。
- 阻断项数组：稳定 `code`、resource type/id、`resource_display_name` 和 safe message。

`sync_state` 和 blocker 优先级由 application service 计算，前端不通过多个列表猜测。

### 18.4 新增知识库 Job 列表

```http
GET /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/jobs
  ?document_id=<uuid>
  &status=<status>
  &cursor=<opaque>
  &limit=20
```

返回 `{items, next_cursor}`。排序固定为 `created_at DESC, id DESC`。默认/最大 limit 为 20/100。该接口支撑概览“查看全部任务”和文档活动，不提供 retry mutation。

每个 Job item 除内部 lineage 外必须提供：

- `action_label`：如“导入文件”“更新 FAQ”“修订分块”“构建索引版本”。
- `target_type` 与 `target_display_name`：如 `document / installation.md`、`generation / 2026-08-01 11:08 · text-embedding-v4`。
- 页面用上述可读字段呈现任务，不展示 Job/Document/Generation UUID。

### 18.5 新增 Document 有效 Chunk 列表

```http
GET /api/v1/workspaces/:workspace_slug/knowledge-bases/:id/documents/:document_id/chunks
  ?enabled=true|false
  &cursor=<opaque>
  &limit=50
```

返回：

```json
{
  "generation_id": "uuid",
  "document_revision_id": "uuid",
  "chunk_set_id": "uuid",
  "items": [
    {
      "id": "uuid",
      "sequence": 0,
      "source_anchor": {},
      "metadata": {},
      "active_revision": {
        "id": "uuid",
        "revision_no": 1,
        "content": "...",
        "context_header": "...",
        "enabled": true,
        "status": "ready",
        "edit_source": "system"
      }
    }
  ],
  "next_cursor": null
}
```

语义：

- 返回 KB 当前 active Generation 配置对应、当前生效 Document Revision 的完整有效 ChunkSet，包括停用 Chunk；不能仅从可检索 `retrieval_entries` 反推，否则停用 Chunk 会消失。
- KnowledgeBase、Document 与 Workspace lineage 不一致时返回 404。
- v0.5.0 不支持用该接口浏览任意历史或候选 Generation 的 Document Chunk；索引区通过 Generation 自身的配置与计数完成候选检查，避免在没有 Generation-to-ChunkSet 完整快照映射时伪造历史视图。
- 默认 limit 50，最大 200；游标按 `sequence, id` 稳定分页。
- FAQ 同样可读，但其 Chunk mutation 仍由现有后端拒绝。

### 18.6 新增知识库基本信息更新

```http
PATCH /api/v1/workspaces/:workspace_slug/knowledge-bases/:id
Content-Type: application/json

{
  "name": "产品文档",
  "description": "面向产品与交付"
}
```

- admin/owner 可用。
- strict JSON；至少提供一个字段。
- 只更新 typed 基本信息，不接受任意 metadata。
- 不改变 content version，不创建 Generation。
- Embedding、chunking 和 retrieval 设置继续通过 Generation create/activate 修改。

### 18.7 不新增的接口

- 不新增“训练”“重新训练”接口。
- 不新增 FAQ Chunk 通用更新接口。
- 不新增虚假的 Job step/percentage 字段。
- 不新增 retry mutation；留给 v0.8.0 的可靠性设计。
- 不新增前端专用持久化表或 tutorial completion 表。

### 18.8 既有 DTO 的可读展示字段

现有 DTO 可以保留内部 ID，但 UI 需要展示人员或资源身份时必须有可读字段：

- Chunk Revision history 为人工修订提供 `editor_display_name`。system revision 显示“系统”；历史用户不可解析时显示“已删除用户”，不得回退显示 `editor_user_id`。
- Generation 使用模型快照中的 `model_name`、创建时间和状态生成 `display_label`；不依赖可能已删除的当前 Model，也不展示 Generation ID。
- File 使用 File Tree node name，FAQ/Web 使用 Document title；Job 使用前述 `action_label + target_display_name`。
- API response 中保留的 Workspace/User/Document/Job/Generation UUID 只用于请求、缓存和 deep link，不进入普通页面 DOM。

## 19. 前端结构与数据流

### 19.1 Route 与 Outlet 文件边界

目标文件结构：

```text
web/src/routes/_authenticated/workspaces/$workspaceSlug/kb/$kbId/
  route.tsx                         # KB workbench layout + <Outlet />
  index.tsx                         # 概览
  search.tsx                        # 检索测试
  indexes.tsx                       # 索引版本
  settings.tsx                      # 设置
  content/
    route.tsx                       # 类型导航 + <Outlet />
    index.tsx                       # replace redirect -> ./all
    all.tsx                         # 全部内容表格/卡片
    files/
      route.tsx                     # File Tree + <Outlet />
      index.tsx                     # 未选择文件提示
      $documentId.tsx               # File 预览 + Chunk
    faq/
      index.tsx                     # FAQ 表格/卡片
      new.tsx                       # FAQ 创建
      $documentId/
        index.tsx                   # FAQ 详情
        edit.tsx                    # FAQ 编辑
    web/
      index.tsx                     # Web 表格/卡片
      $documentId.tsx               # Web 详情
```

实现规则：

- 将当前 `$kbId/index.tsx` 中的公共 KB 页头拆到新建的 `$kbId/route.tsx`；`index.tsx` 只保留概览内容。
- route layout 和 leaf page 分文件，layout 渲染 `<Outlet />`。不得在一个 `KnowledgeBaseDetail` 组件中根据 pathname、Tab state 或条件分支切换所有页面。
- `<Link>` 是桌面 Tabs 的交互基元；移动端 Select 的 change 事件执行 router navigation 到同一目标。active 状态从 router match 计算。
- loader 数据只包含该路由首屏所需的查询；父 loader 提供名称和公共上下文，叶子 loader 独立加载内容。F5 时按父到子顺序重建，不读取组件内存状态。
- 所有 mutation 完成后的跳转使用 canonical route；例如 FAQ 创建后进入 `/content/faq/:documentId`，File 上传后进入 `/content/files/:documentId`。

### 19.2 Feature 边界

建议在现有 package 内按职责拆分，不创建上帝组件：

```text
web/src/features/
  workspace-readiness/
  knowledge-bases/
    workbench/
    overview/
    settings/
  content/
    lists/                  # 全部/FAQ/Web 表格与移动端卡片
    file-tree/
    document-preview/
    faq-editor/
  chunks/
    inspector/
    revision-editor/
  retrieval/
  index-generations/
  jobs/
```

可根据实现规模保留现有 `documents/` 目录，但组件文件必须按职责命名。不要把工作台继续堆进单个 `knowledge-base-detail.tsx`。

### 19.3 Query key 与 loader 所有权

示例：

```text
['workspace-readiness', workspaceSlug]
['knowledge-base-summary', workspaceSlug, kbId]
['content', workspaceSlug, kbId, filters]
['file-tree', workspaceSlug, kbId]
['document', workspaceSlug, documentId]
['document-chunks', workspaceSlug, kbId, documentId, activeGenerationId, filters]
['chunk', workspaceSlug, kbId, chunkId]
['chunk-revisions', workspaceSlug, kbId, chunkId]
['retrieval-test', workspaceSlug, kbId, request]
['index-generations', workspaceSlug, kbId]
['jobs', workspaceSlug, kbId, filters]
```

mutation 成功后集中声明受影响 key，避免组件手工修改多份本地状态。

loader 所有权：

| 叶子/布局路由 | F5 首屏必须确保的 Query |
|---|---|
| KB layout | KnowledgeBase、当前 membership/权限 |
| Overview | KnowledgeBase summary |
| Content all/FAQ/Web | Document list + 当前筛选所需详情 |
| Files layout | File Tree |
| File detail | Document + active Generation Chunk list |
| FAQ detail/edit | FAQ Document + active revision |
| Web detail | Web Document |
| Search | KnowledgeBase summary；URL 有 query 时重放 retrieval Query |
| Indexes | Generation list |
| Settings | KnowledgeBase + 可选择模型（有写权限时） |

组件中的 `useQuery` 可以复用 loader 已填充的 cache，但不能成为直达/F5 后唯一的数据启动路径。

### 19.4 表单与校验

- FAQ、Generation、KB 设置、文件夹操作继续使用 RHF + Zod。
- API response 都使用 Zod 解析；Job 不再用未经校验的 TypeScript type 直接信任响应。
- `unknown` metadata 必须显式收窄；禁止 `any`。
- FAQ 回答使用普通多行 textarea 编辑 Markdown，不引入会改变持久化格式的富文本编辑器。
- Markdown 预览统一使用 `react-markdown + remark-gfm + rehype-sanitize`；不启用 `rehype-raw`，原始 HTML 按纯文本/忽略策略处理，不允许脚本、事件属性或危险 URL。File/Web/FAQ 共用同一安全渲染组件。

## 20. 响应式与无障碍

### 20.1 键盘

- 全局 skip link 跳到主内容。
- Tabs/Select、树、列表、菜单和 Dialog 遵守 Radix/shadcn 键盘语义。
- File Tree 支持方向键导航、Enter 打开、F2 或显式菜单重命名；不能只支持右键或拖拽。
- Chunk deep link 打开 Inspector 后，焦点进入标题；关闭后回到触发项。
- mutation 失败摘要获得焦点，字段错误通过 `aria-describedby` 关联。

### 20.2 语义与视觉

- 所有 authenticated 全页面路由必须渲染在现有 `AuthenticatedLayout` 内；桌面复用 `AppSidebar + SidebarInset(AppHeader + main Outlet)`，移动端由同一个 `AppSidebar` 进入 Sheet 导航抽屉。功能页面不得重画 Logo 顶栏、重复 Workspace 切换器、另建“个人”导航组，或以脱离导航上下文的孤立画布交付。
- 状态不能只靠颜色；图标、文字和 tone 同时表达。
- 焦点环在浅色/深色主题下均可见。
- 触控目标不小于 44x44 CSS px。
- 表格仅用于真正的二维数据；移动端内容列表改卡片，不给用户一个缩小的宽表格。
- 支持 `prefers-reduced-motion`；状态更新不依赖动画才能察觉。

## 21. 安全与隐私

- 所有新增查询显式带 Workspace scope，并在 Repository 查询中使用 `workspace_id`；跨 Workspace 仍返回 404。
- Web 不展示 Provider credential、raw storage key、完整第三方响应或未经筛选的 Job payload。
- 错误日志附 workspace/document/job/generation ID，不记录完整查询文本、完整 Chunk/FAQ 内容或 API key。
- Markdown 渲染采用 allowlist sanitize；外链增加安全属性，危险 scheme 被拒绝。
- return URL 只能是同源允许路由，避免开放重定向。
- Document 删除、Generation 激活和 Chunk 修订继续由后端事务与乐观并发约束保证，前端确认框不是安全边界。

## 22. 测试与验收

### 22.1 后端

- Workspace readiness 推荐动作的表驱动测试，覆盖无 Provider、无 Model、无 KB、无内容、processing、failed、ready。
- KB summary 状态优先级、active/candidate、最近 Job 与安全字段测试。
- Document Chunk 列表覆盖 active Generation、停用 Chunk、FAQ、分页和跨 Workspace 404。
- KB 基本信息更新覆盖 admin/owner 成功、member 403、名称冲突、strict JSON。
- Repository/HTTP 集成测试只使用测试运行时 testcontainers 启动的 `pgvector/pgvector:pg16`；执行真实迁移；不得读取 `config.yaml` 或本机 PostgreSQL。

### 22.2 前端组件与交互

- Workspace readiness 每个状态与 CTA。
- `AuthenticatedLayout` 保持 `AppSidebar + SidebarInset(AppHeader + main Outlet)` 结构；知识库父子路由不得挂载第二套全局 Header 或 Sidebar。
- `AppSidebar` 结构测试固定验证：Header 为 `WorkspaceSwitcher`，Content 先渲染 `Workspace` 组，Footer 为 `NavUser`，并保留 `collapsible="icon"` 与 `variant="sidebar"`。
- 导航权限测试固定验证：所有 Workspace 角色均见“概览 / 知识库 / 模型 / 成员”；仅 admin/owner 见“邀请”；仅 platform_admin 见独立“平台管理 / 平台模型”组；任何角色都不出现“个人 / 个人设置”侧栏组。
- `AppHeader` 顺序保持 `SidebarTrigger / breadcrumbs / spacer / search / theme / profile`；移动端隐藏全局搜索并由 trigger 打开同一个 `AppSidebar` Sheet。
- 工作台每个 Tabs/Select 项使用独立 route，active 状态、前进后退和 URL search params 一致。
- 在空 Query Cache 下直接挂载 Overview、All、Files、File detail、FAQ、Web、Search、Indexes、Settings 叶子路由，验证 loader 能独立恢复首屏内容。
- KB/Content/Files 三层 layout 均渲染 `<Outlet />`，子页面切换不丢失 AppShell、KB 页头或 File Tree 上下文。
- 页面级渲染测试覆盖完整 AppShell、Workspace 名称、用户 `nickname` 和资源可读名称；普通 DOM 中不得出现资源 UUID 或 config hash。
- File Tree 键盘、移动、冲突和非空删除反馈。
- File Tree 组件只接收 File 节点，FAQ/Web 不进入树；全部/FAQ/Web 在桌面表格和移动端卡片间切换。
- FAQ 多问题校验、Markdown 预览、409 草稿保留。
- 检索参数、0 结果、分数说明、anchor 格式和 deep link。
- Chunk Inspector、权限、FAQ 只读、revision conflict。
- Generation create/activate、manual edit confirmation、stale/building/failed。
- pending/completed Job 状态兼容与轮询终止。
- desktop/tablet/mobile 关键布局与焦点恢复。

### 22.3 浏览器 E2E

至少覆盖：

1. owner 完整主链路。
2. member 可管理内容和检索，但看不到 Chunk/Generation mutation。
3. admin 的 Chunk revision conflict 恢复。
4. ready Generation 激活和 stale Generation 拒绝。
5. File Tree 重命名/移动/非空删除失败。
6. FAQ 创建、编辑、检索命中和来源跳转。
7. 页面刷新与复制 deep link 后仍定位到 Document/Chunk。
8. 真实 `web_embed` 单二进制 SPA fallback、API namespace 和认证 smoke。
9. 桌面核心页面保留左侧栏，移动端导航抽屉可打开；页面只显示可读名称，“复制诊断信息”前不渲染 UUID/hash。
10. 分别直达并 F5 刷新 overview、all、files、File detail、FAQ list/new/detail/edit、Web list/detail、search、indexes、settings，页面不能空白或退回默认 Tab；`/content` 刷新后稳定 replace 到 `/content/all`。
11. 对上述嵌套路由直接发起浏览器 GET，Vite 与 `web_embed` 均返回 SPA；`/api/v1/*` 和 `/mcp` 仍不得落入 SPA fallback。

## 23. 交付分片与版本边界

v0.5.0 是一个产品闭环，但实现应按可验证竖切推进：

1. Workspace readiness、工作台路由与公共状态系统。
2. 内容分类型视图、File Tree、Document canonical route 与删除。
3. FAQ 完整页面编辑。
4. Document Chunk 列表、Inspector、Revision 编辑与冲突处理。
5. 检索测试与来源 deep link。
6. Generation 历史、构建、差异和激活；移除误导性的直接换模型入口。
7. 概览聚合、Job 列表、响应式、无障碍和全链路 E2E 收口。

每个分片都必须使用真实 API，不允许长期保留 mock dashboard。只有完整主链路、角色矩阵和单二进制 E2E 全部通过，才能宣称 v0.5.0 完成。
