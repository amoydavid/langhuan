# 琅嬛 v0.2.1 多租户与认证设计规格

## 1. 背景

v0.2.0 建立了 workspace 作为顶层资源作用域，但 workspace 只是「数据归属 + 查询过滤」边界，不是租户隔离的安全边界。HTTP 全链路无鉴权：路由只挂 `gin.Recovery()`，`workspace_id` 由客户端在 URL 直接提供，谁拿到 workspace UUID 就能任意操作该 workspace 下所有资源。跨 workspace 访问仅表现为返回 `404` 的查询过滤，而非身份认证 + 授权。workspace 成员、角色、API token 签发与鉴权中间件全部是 v0.2.0 的显式非目标。

v0.2.1 在不破坏 v0.2.0 既有 worker 与文档导入链路的前提下，交付首个真正的租户隔离 + 身份认证能力：**workspace 即租户**，每个 workspace 有自己的用户与角色；一个 email 用户可以同时属于多个 workspace；用户通过 email + password 登录，session 由琅嬛自管。

> 早期讨论曾考虑对接 OIDC（例如 Dex）。本版本确认放弃 OIDC：OIDC 涉及通讯录同步问题，且国内 IdP（如飞书）未必能稳定拿到 email。v0.2.1 改用琅嬛自建的 email + password 用户体系，把认证完全收敛到琅嬛进程内部。API token（供程序调用 REST/MCP）留到 v0.6.0 对外提供检索能力时再做。

## 2. 目标

v0.2.1 交付以下能力：

- 实现 email + password + 昵称的自建用户体系，密码使用 argon2id 哈希。
- 实现 session 机制：登录后由琅嬛签发 session 并写入 httpOnly cookie，session 数据持久化到 PostgreSQL。
- 把 workspace 确立为租户边界：用户与 workspace 是 N:N 关系，通过 membership 关联。
- 在 workspace 内引入三档角色：owner / admin / member。
- 引入 platform_admin（全局管理员）：唯一能创建 workspace 的身份，由 `users.is_platform_admin` 字段标识。
- 引入「邀请即注册即加入」流程：所有普通用户都通过 workspace 邀请进入平台并加入对应 workspace，不存在「平台用户但不在任何 workspace」的中间态。
- 给 workspace 增加 slug：全平台唯一、必填、进入 URL。
- 通过 Gin 中间件链把鉴权收敛到统一入口，handler 只从认证上下文读取身份，不再自己解析 workspace 参数或判断归属。
- 跨 workspace 资源访问由中间件统一拦截为 `404`，不暴露资源存在性。
- platform_admin 可重置任意用户密码；重置后吊销该用户全部 session。
- 登录失败限流，状态存 Redis，按 email 维度在时间窗口内累计失败次数。

## 3. 非目标

v0.2.1 明确不做：

- OIDC / SSO / 外部身份提供者对接（已确认放弃，留待未来按需评估）。
- workspace API token 的签发、校验与鉴权（按当前 ROADMAP 留到 v0.5.0，原编号 v0.6.0）。
- 密码重置邮件自助流程（v0.2.1 由 platform_admin 手动重置；基于 email 的自助重置留待后续引入邮件发送能力后补）。
- 细粒度 RBAC（resource-based permission，例如可读不可写、只读某个 KB）。v0.2.1 角色粒度停在 owner/admin/member 三档。
- 平台级独立「用户注册」入口。普通用户只能通过邀请进入；唯一例外是平台首次启动时的首个注册者。
- 成员角色变更的完整审计日志表（v0.2.1 只记录 `updated_at`；详细升降级审计留待后续）。
- 真实 PDF 解析、分块、embedding、检索（按当前 ROADMAP 分别属于 v0.8.0/v0.3.0/v0.4.0/v0.5.0）。
- 前端管理台。v0.2.1 只交付 REST API，前端另行实现。

## 4. 架构增量

```text
HTTP 请求
  -> SessionAuth 中间件      cookie 取 session_id -> 查 sessions 未过期 -> 加载 user
  -> RequirePlatformAdmin    平台级操作校验 is_platform_admin
  -> RequireWorkspace        URL 的 :workspace_slug -> 解析 workspace -> 校验 membership
                             -> 写入 AuthContext{UserID, WorkspaceID, Role}
  -> RequireWorkspaceRole    按 owner/admin/member 校验当前路由所需最低角色
  -> handler                 从 AuthContext 取身份，业务零鉴权
```

worker 链路完全不经过 HTTP 中间件。worker 从 asynq 任务 payload 拿 workspace UUID，与认证体系无关；v0.2.0 既有 worker 与文档导入链路零改动。

依赖约束：

- `domain/model` 不依赖 HTTP、数据库、Redis、argon2 实现。
- `application/service` 面向 `ports/auth` 抽象（password hasher、session store、rate limiter），不直接依赖 argon2 或 Redis SDK。
- HTTP handler 不直接访问数据库或 Redis；只通过 service 与 `AuthContext`。
- 中间件只做身份与归属解析，不含业务逻辑。

## 5. 认证流程

### 5.1 首个管理员的引导

平台首次启动时 `users` 表为空。注册接口 `/auth/register` 检测到无任何用户时：

- 跳过邀请 token 校验。
- 创建该用户，`is_platform_admin = true`。
- 不创建任何 membership（首个管理员尚未归属 workspace；他需要随后自己创建 workspace 并成为其 owner）。

这是唯一绕过邀请的注册路径。此后所有注册必须携带有效且未消费的邀请 token。

### 5.2 创建 workspace

仅 platform_admin 可调用 `POST /api/v1/workspaces`，请求体需提供 `name` 与 `slug`：

- `slug` 全平台唯一、必填，校验格式（小写字母、数字、连字符，首尾非连字符，长度 3–64）。`slug` 冲突返回 `409`。
- workspace 创建后，自动为发起者创建一条 `role = owner` 的 membership（即便是 platform_admin 创建的 workspace，也必须通过 owner membership 关联，保证 workspace 始终有主）。

### 5.3 邀请即注册即加入

workspace owner/admin 创建邀请（`POST /api/v1/workspaces/:workspace_slug/invitations`），指定 `invited_email` 与 `role`（admin 创建时只能指定 member/admin，不可指定 owner；owner 可指定任意角色）：

1. 校验当前用户对该 workspace 的角色满足「创建邀请」门槛（admin+）。
2. 校验 `invited_email` 在该 workspace 没有未接受的邀请，且不是该 workspace 现有成员（唯一约束 `(workspace_id, invited_email)` 兜底）。
3. 生成高熵随机 token（crypto/rand，≥32 字节，base64url 编码），计算 `token_hash = sha256(token)`（确定性、可索引），保存 invitation 行，`token_prefix` 取明文 token 前 8 位用于展示。

   > 注意：邀请 token 与密码的安全模型不同。密码是低熵输入，必须用 argon2id 慢哈希抵御爆破；邀请 token 是高熵随机值（256 位熵），单次 SHA256 即足以防还原，且必须可索引以支持 `WHERE token_hash = ?` 直接定位，不能用 argon2id 的随机盐（否则只能全表扫描逐个比对）。session_id 同理。

4. 返回完整邀请链接 `https://<host>/invitations/<token>`（链接由调用方/前端展示与分发；琅嬛不发送邮件）。

被邀者接受邀请（`POST /auth/register`，body 带 invitation token + email + nickname + password）：

1. 定位 invitation：`token_hash = sha256(请求中的 token)`，`WHERE token_hash = ? AND accepted_at IS NULL AND revoked_at IS NULL AND expires_at > now()`。无匹配则拒绝。
2. 校验请求体 `email == invitation.invited_email`，否则拒绝（防止 A 的邀请被 B 顶用）。
3. argon2id 哈希密码，创建 user（`is_platform_admin = false`，唯一例外见 5.1）。
4. 创建 membership，`workspace_id` 与 `role` 取自 invitation。
5. 置 invitation `accepted_at` 与 `accepted_user_id`，token 此后不可再用。
6. 创建 session，写 cookie。

邀请状态机：

```text
[pending] 创建后生效
   │  GET  /invitations/:token   展示邀请详情（workspace 名、角色、锁定 email）
   │  POST /auth/register         接受
   ▼
[accepted] accepted_at / accepted_user_id 置位，token 失效
[expired]  超过 expires_at 未接受 → 自动失效
[revoked]  创建者或 platform_admin 主动撤销
```

### 5.4 登录

`POST /auth/login`（email + password）：

1. 登录限流：以 email 为 key，检查 Redis 在窗口内失败次数。超过阈值（默认 5 次 / 15 分钟）直接返回 `429`，不查库不哈希。
2. 查 user by email。不存在时仍执行一次 dummy argon2id（恒定时间，避免用户枚举时序攻击），统一返回 `401`。
3. argon2id 比对密码。失败：Redis 计数 +1，返回 `401`（错误信息不区分「用户不存在」与「密码错误」）。
4. 成功：清零该 email 的失败计数，创建 session 行，写 httpOnly + Secure + SameSite=Lax cookie，更新 `users.last_login_at`。

### 5.5 登出

`POST /auth/logout`：删除当前 session 行，清 cookie。

### 5.6 当前身份

`GET /auth/me`：返回当前 user（id、email、nickname、is_platform_admin）及该 user 所属的全部 workspace 列表（slug、name、role）。

### 5.7 密码重置（仅 platform_admin）

`POST /admin/users/:user_id/password-reset`：

1. 校验 `is_platform_admin`（中间件 `RequirePlatformAdmin`）。
2. 设置目标 user 的新密码（argon2id 重新哈希）。
3. 吊销该 user 全部 session（删除其所有 sessions 行），强制重新登录。

## 6. 中间件与认证上下文

### 6.1 AuthContext

通过 `gin.Context` 注入：

```go
type AuthContext struct {
    UserID          uuid.UUID
    IsPlatformAdmin bool
    WorkspaceID     uuid.UUID // 仅 workspace-scoped 路由填充
    Role            string    // owner|admin|member，仅 workspace-scoped 路由填充
}
```

handler 通过 `c.MustGet("auth").(AuthContext)` 取值，不再自行解析 workspace 参数。

### 6.2 中间件链

- **SessionAuth**：从 cookie 读 session_id → 查 `sessions` 未过期行 → 加载 user。失败或缺失返回 `401`。成功把 `UserID`、`IsPlatformAdmin` 写入 `AuthContext`。健康检查、登录、注册、邀请查询等公开路由不挂此中间件。
- **RequirePlatformAdmin**：校验 `AuthContext.IsPlatformAdmin`，否则 `403`。
- **RequireWorkspace**：从 URL `:workspace_slug` 解析 workspace（查 `workspaces` 表）。workspace 不存在 → `404`。再校验当前 user 在该 workspace 是否有 membership：无 → `404`（不暴露 workspace 存在性）。有 → 把 `WorkspaceID`、`Role` 写入 `AuthContext`。
- **RequireWorkspaceRole(minRole)**：按角色等级（member < admin < owner）校验当前路由所需最低角色，不满足 → `403`。

### 6.3 slug 与 UUID 的边界

- HTTP 入口层用 slug（URL 可读）。
- 中间件 `RequireWorkspace` 把 slug 解析为 workspace UUID，此后 handler、service、repository、worker 全部使用 UUID。
- worker / asynq payload 继续用 workspace UUID，零改动。现有 repository 已带 `workspace_id` 过滤，中间件解析出 UUID 后直接复用。

## 7. 数据模型

数据库迁移走 golang-migrate 手写 SQL（本项目既定策略，非 GORM AutoMigrate）。v0.2.1 新增迁移文件 `000002_multi_tenant_auth.up.sql` / `.down.sql`。

### 7.1 users

```sql
CREATE TABLE users (
    id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    email             text NOT NULL UNIQUE,
    nickname          text NOT NULL,
    password_hash     text NOT NULL,            -- argon2id 编码串，自带 salt，无需单独 salt 列
    is_platform_admin boolean NOT NULL DEFAULT false,
    last_login_at     timestamptz,
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now()
);
```

### 7.2 sessions

```sql
CREATE TABLE sessions (
    id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at   timestamptz NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    last_seen_at timestamptz NOT NULL DEFAULT now(),
    user_agent   text NOT NULL DEFAULT '',
    ip_addr      inet,
    revoked_at   timestamptz
);
CREATE INDEX idx_sessions_user_id ON sessions(user_id);
CREATE INDEX idx_sessions_expires_at ON sessions(expires_at);
```

`id` 即写入 cookie 的 session_id。`expires_at` 索引用于周期性清理过期 session。

### 7.3 workspace_memberships

```sql
CREATE TABLE workspace_memberships (
    id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    user_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role         text NOT NULL,                 -- owner | admin | member
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, user_id),
    CONSTRAINT workspace_memberships_role_check CHECK (role IN ('owner','admin','member'))
);
CREATE INDEX idx_memberships_user_id ON workspace_memberships(user_id);
CREATE INDEX idx_memberships_workspace_id ON workspace_memberships(workspace_id);
```

### 7.4 workspace_invitations

```sql
CREATE TABLE workspace_invitations (
    id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id     uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
    invited_email    text NOT NULL,
    role             text NOT NULL DEFAULT 'member',
    token_hash       text NOT NULL,
    token_prefix     text NOT NULL,
    expires_at       timestamptz NOT NULL,
    accepted_at      timestamptz,
    accepted_user_id uuid REFERENCES users(id),
    revoked_at       timestamptz,
    created_by       uuid NOT NULL REFERENCES users(id),
    created_at       timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, invited_email),
    CONSTRAINT workspace_invitations_role_check CHECK (role IN ('owner','admin','member'))
);
CREATE INDEX idx_invitations_token_hash ON workspace_invitations(token_hash);
```

### 7.5 workspaces 增列

```sql
ALTER TABLE workspaces ADD COLUMN slug text NOT NULL;
CREATE UNIQUE INDEX idx_workspaces_slug ON workspaces(slug);
```

`slug` 必填且全平台唯一。对既有 workspace（含 `EnsureDefaultWorkspace` 创建的默认 workspace）需在迁移中回填一个合法 slug（例如 `default`），回填冲突时追加随机后缀。

### 7.6 workspace_api_tokens

v0.2.0 已预留此表。v0.2.1 不实现 token 签发/校验，保持现状。

## 8. 角色与权限矩阵

| 操作 | 最低角色 |
|---|---|
| 创建 workspace | platform_admin |
| 列出自己的 workspace | 任意已登录用户（基于自身 membership） |
| 读取 workspace / KB / document / job | member |
| 创建 KB / 导入文档 | member |
| 创建邀请 | admin |
| 列出 workspace 成员 | member |
| 移除成员、修改成员角色 | owner |
| 重置任意用户密码 | platform_admin |

### 8.1 owner 唯一性约束

- 一个 workspace 至少保留一个 owner。
- 移除或降级最后一个 owner 的操作（移除成员、把 owner 改成 admin/member）被拒绝，返回 `409`。
- 转移所有权场景：owner 先把另一个成员提升为 owner（此时有两个 owner），再降级/移除自己。

## 9. 配置

新增 `auth` 配置块（YAML 只保存非敏感运行参数）：

```yaml
auth:
  session:
    cookie_name: "langhuan_session"
    lifetime_seconds: 604800          # 7 天
    secure_cookie: true               # 生产必须 true；本地 http 开发可在本地 config.yaml 设 false
    domain: ""                        # 可选，cookie domain
  password:
    argon2_memory_kib: 65536          # 64 MiB
    argon2_iterations: 3
    argon2_parallelism: 2
  rate_limit:
    login_max_attempts: 5
    login_window_seconds: 900         # 15 分钟
  invitation:
    lifetime_seconds: 604800          # 7 天
```

配置边界：

- argon2 参数允许在本地 `config.yaml` 调整；`config.example.yaml` 给出推荐默认值。
- cookie `secure` 在本地 http 调试时可设 false（仅本地 config.yaml，不入示例默认）。
- 不在 YAML 存放任何明文密码、token 或 session secret。

## 10. 安全约束

- 密码仅以 argon2id 哈希存储，明文密码不进日志、错误消息、响应体、commit。
- 登录错误统一返回 `401`，不区分「用户不存在」与「密码错误」；用户不存在时执行 dummy argon2id 抵御时序枚举。
- session cookie 设置 httpOnly、Secure（生产）、SameSite=Lax。
- session_id 是足够长的随机值（UUIDv7 + 额外熵或 crypto/rand）；session_id 不出现在 URL。
- 邀请 token 用 sha256 存储（高熵随机值无需慢哈希，且必须可索引）；URL 中的明文 token 不入库、不进日志。
- 跨 workspace 访问统一返回 `404`，不返回 `403`，避免泄露 workspace 存在性。
- 密码重置仅 platform_admin 可发起；重置后立即吊销目标用户全部 session。
- 登录限流以 email 为 key 存 Redis，窗口内超阈值返回 `429`；限流 key 与计数不包含密码。

- worker 链路（`internal/interfaces/worker/`）零改动。
- v0.2.0 既有 repository 的 workspace 过滤逻辑不变（`repository.go` 已带 `workspace_id` 条件），中间件解析出 UUID 后直接复用。
- `domain/model` 既有 workspace/kb/document/job 模型不引入鉴权概念。

### 11.3 对 MinerU PDF 解析版本（现编号 v0.8.0）的影响

> 本节撰写时 MinerU PDF 解析是紧接 v0.2.1 之后的下一个版本、编号 v0.3.0；ROADMAP 调整后该版本改为 v0.8.0（排在多格式解析 v0.3.0、embedding/索引 v0.4.0、REST 检索 v0.5.0 之后），但以下鉴权衔接结论不受顺序调整影响，仍然适用。

v0.8.0（MinerU PDF 解析）开工时鉴权框架已就位：

- v0.8.0 的 HTTP handler（PDF 上传等）直接复用既有 `AuthContext`，无需自建鉴权。
- v0.8.0 worker 链路无影响。
- v0.8.0 的 `parser_provider_credentials.workspace_id` 字段语义可在 v0.8.0 设计时重新评估：有了真实 membership/role 体系，credential 可由该 workspace 的 admin 管理，而非仅「全局回退」。该决策属 v0.8.0 范围，本规格不锁定。
- v0.8.0 原计划 credential 写入走本地 operator CLI（因当时无鉴权）。v0.2.1 后可评估改为 platform_admin/workspace admin HTTP API，但同样属 v0.8.0 范围决策。

## 12. 测试策略

单元测试：

- argon2id password hasher：哈希/校验往返；错误密码返回 false；不同密码哈希不同。
- 注册：首个用户自动成为 platform_admin；非首个用户无邀请 token 拒绝；email 与邀请不匹配拒绝；过期/已接受/已撤销 token 拒绝。
- 登录：正确密码成功并创建 session；错误密码返回 401；用户不存在走 dummy 哈希且返回 401；限流超阈值返回 429。
- 邀请：admin 不能创建 owner 邀请；owner 可创建任意角色邀请；`(workspace_id, invited_email)` 唯一约束；接受后 token 不可复用。
- membership：owner 唯一性约束（最后一个 owner 不可移除/降级）；角色变更权限矩阵。
- slug：格式校验；全平台唯一；冲突返回 409。
- 密码重置：仅 platform_admin 可调用；重置后目标用户 session 全部失效。

中间件测试：

- SessionAuth：无 cookie / 过期 session / 已吊销 session → 401；有效 session → AuthContext.UserID 正确。
- RequireWorkspace：slug 不存在 → 404；无 membership → 404；有 membership → AuthContext.WorkspaceID/Role 正确。
- RequireWorkspaceRole：member 访问 admin 路由 → 403。
- 跨 workspace：用户 A 对 workspace Y 无 membership，访问 Y 资源 → 404（不泄露存在性）。

集成测试：

- 端到端「首个管理员注册 → 创建 workspace（自动 owner）→ 邀请用户 → 用户接受邀请注册加入 → 登录 → 访问 workspace 资源 → 登出」全链路。
- 密码重置后旧 session 失效，新密码可登录。
- 限流窗口过期后可再次尝试登录。

Redis 限流器使用 miniredis 或真实本地 Redis 测试；argon2 测试参数可调低以加速。

## 13. 验收标准

- 平台首次启动，无 invitation 可注册首个用户，该用户 `is_platform_admin = true`。
- 非首个用户无有效邀请 token 无法注册。
- platform_admin 可创建带 slug 的 workspace，创建后自动成为该 workspace owner。
- workspace owner/admin 可创建邀请；被邀者通过邀请链接注册后自动加入对应 workspace 并获得指定角色。
- 用户登录后获得 session cookie，可访问其所属 workspace 的 KB/document/job；访问无 membership 的 workspace 返回 `404`。
- owner/admin/member 三档角色权限矩阵符合第 8 节。
- workspace 始终至少保留一个 owner；移除/降级最后一个 owner 被拒绝。
- 登录失败连续超阈值后返回 `429`，窗口过期后恢复。
- platform_admin 可重置任意用户密码，重置后该用户旧 session 全部失效。
- 跨 workspace 访问统一 `404`，不泄露资源存在性。
- worker 与 v0.2.0 既有文档导入链路回归测试通过。
- `go test ./...` 通过。
- 明文密码、明文邀请 token、session_id 不出现在日志、错误消息与 commit。
