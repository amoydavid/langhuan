# 琅嬛 v0.5.0 Web Console 整体使用体验 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 完整实现 v0.5.0 spec，使用户能在现有 App Shell 内完成 Workspace 准备、知识库内容管理、FAQ、检索验证、Chunk 修订和索引版本管理闭环。

**Architecture:** 后端复用 v0.4.0 事实模型，以 application query service + Workspace-scoped 薄 Repository 提供 readiness/summary/jobs/chunks 投影，并保留现有写模型。前端使用 TanStack Router 文件路由和嵌套 `<Outlet />`，每个叶子 loader 独立填充 TanStack Query；File Tree 仅服务 `kind=file`，FAQ/Web 使用表格与移动卡片。

**Tech Stack:** Go 1.26、Gin、GORM、PostgreSQL + pgvector、asynq/Redis、React 19、TypeScript 7、TanStack Router/Query、RHF + Zod、Tailwind CSS v4、shadcn/ui、Vitest Browser、Biome。

## Global Constraints

- 所有数据库测试只允许使用测试运行时临时启动的 `pgvector/pgvector:pg16`，不得读取 `config.yaml` 或连接本机长期数据库。
- 所有新行为严格 Red → Green → Refactor；先运行会因能力缺失而失败的测试，再写生产代码。
- 普通页面只展示 Workspace name、User nickname/email、KB name、Document name/title 和可读 Job/Generation label，不展示裸 UUID 或 config hash。
- File Tree 只接收和展示 File 节点；FAQ/Web 只使用桌面表格和移动端卡片。
- authenticated 页面必须复用现有 `AuthenticatedLayout -> AppSidebar + SidebarInset(AppHeader + main Outlet)`。
- KB、Content、Files 使用独立 route layout + `<Outlet />`；F5、地址栏直达、前进后退和复制链接均恢复相同上下文。
- 异步 UI 只展示真实 Document/Job/Generation 状态，不伪造阶段、百分比或 retry mutation。
- 前端请求统一走 `src/lib/api/client.ts` 与 TanStack Query；表单使用 RHF + Zod；禁止 `any`。
- Markdown 使用 `react-markdown + remark-gfm + rehype-sanitize`，不启用 `rehype-raw`。
- 每个任务完成后先更新本文件 checkbox，再将计划与实现放在同一个 commit 中。

func recommendedReadinessAction(f WorkspaceReadinessFacts) dto.ReadinessAction {
    switch {
    case !f.HasActiveProvider:
        return dto.ReadinessConfigureProvider
    case !f.HasSelectableEmbeddingModel:
        return dto.ReadinessCreateEmbeddingModel
    case f.KnowledgeBaseCount == 0:
        return dto.ReadinessCreateKnowledgeBase
    case f.TotalDocuments == 0:
        return dto.ReadinessAddContent
    case f.FailedDocuments > 0:
        return dto.ReadinessResolveFailedDocument
    case f.ProcessingDocuments > 0 && f.ReadyDocuments == 0:
        return dto.ReadinessWaitForProcessing
    case f.SearchableKnowledgeBaseCount > 0:
        return dto.ReadinessTestRetrieval
    default:
        return dto.ReadinessNone
    }
}
